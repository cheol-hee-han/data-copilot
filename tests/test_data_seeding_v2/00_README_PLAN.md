# 은행 정보계 ADW Synthetic 설계 v2 — 재설계 계획

## v1의 한계 (125 테이블)

- **규모 부족:** 실제 은행 정보계는 1,800~3,500개 테이블 규모. 125개는 NL-to-SQL이 풀어야 할 "수천 개 중에서 정확한 5개 찾기" 문제를 재현 못 함.
- **포맷 상이:** 평문 1줄 설명. 실제 은행은 `[엔티티정의]/[대상내]/[대상외]/[특이사항]` + `[공통정의]/[상세정의]` 태그 구조.
- **쌍둥이 테이블 없음:** 실무는 `*003P/*003S/*003H/*003T` 같이 유형 코드만 바뀌는 쌍둥이가 흔한데 v1은 이런 모호성이 없어 NL-to-SQL 실패 케이스를 못 만듦.

## v2 목표

- **1,441 테이블** 17개 주제영역

## 주요 설계 원칙 (v1에서 계승)

- **명명규칙:** `TB_ADW_<주제3><일련3><유형1>` 14자 고정
- **유형 코드:** M(Master)/L(Log 거래)/H(History 이력)/S(Summary 집계)/P(snaP샷)/C(Code)/T(Task/작업)/G(loG)/D(Detail)
- **한글명:** `<도메인약어3>_<한글설명>` 예: `DEP_예금계좌기본`
- **합성 ID:** 고객 99 prefix, 카드 BIN 9999, 사업자 9 prefix, 실명번호 A+12자리
- **3년 시계열:** 2023-01-01 ~ 2026-03-31
- **품질 이슈 주입:** 2~5% (전화번호 포맷 혼재, 기타코드 과다, 이중소스 불일치 등)

## 실 은행 포맷 재현 요소 (v2 신규)

1. **태그 기반 설명문**
   - 테이블 설명: `[엔티티정의]` / `[대상내]` / `[대상외]` / `[특이사항]`
   - 컬럼 설명: `[공통정의]` / `[상세정의]`
   - `[상동]` 관용어 재현 (70~80% 컬럼에서 `[상세정의] 상동`)
   - `[대상내]` `[대상외]` 의도적 빈칸 (실 데이터에서도 미작성이 많음)

2. **인라인 Enum 패턴**
   - `[공통정의] ... 1:정상 2:취소 3:정정` 형식
   - 별도 코드 테이블(CMI 코드마스터)과 **고의적 불일치** 2% 주입 (값 누락/추가)

3. **쌍둥이 테이블 패턴**
   - 같은 번호 다른 유형: `DPG003P`(일별잔액) vs `DPG003S`(일별집계) vs `DPG003H`(일별이력)
   - 원장과 마트 중복: `DPG004P`(원장 월말스냅샷) vs `MVP014S`(마트 월말집계) — 값은 동일하지만 쓰임새 다름
   - Legacy vs 신규: `LNB001M` (신규) vs `LNX001M` (legacy, 일부 고객만 잔존)

4. **이중 소스 표현**
   - ODS 적재 `TB_ODS_APB_DPACCT` + ADW 원장 `TB_ADW_DPG001M` (동일 개념, 스키마 다름)
   - 단, 본 설계는 ADW(.TB_ADW_*)만 포함. ODS는 언급만.
