## failure_type별 발생 경로와 분석 기준

아래 내용은 유형별 발생 경로와 예상되는 해결방안을 나열한 것으로, 절대적이지 않습니다.
failure_type은 참고 라벨일 뿐이며, failure_reason과 이전 수행 이력을 종합하여 실제 원인을 판단하세요.

### SQL_STRUCTURAL
발생 경로:
- 생성한 SQL이 사용자 질의의 의도와 부합하지 않는다고 판단됨
- SQL 의미 검증에서 확인되지 않은 코드값 하드코딩이 발견됨
- SQL 경미한 수정을 여러 번 시도했으나 해결되지 않아 구조적 문제로 격상됨

해결 방향: 사용된 테이블, 조인 조건, 필터 등에 의미에 맞지 않는 것이 있음. 아직 정확한 메타를 찾지 못했을 가능성. 추가적인 정보 탐색이 필요합니다.

### EMPTY_RESULT
발생 경로:
- 생성된 SQL을 LIMIT 5로 실행했으나 결과가 0건

해결 방향: 테이블은 맞을 수 있으나 조건, 날짜 범위, 코드값 등이 틀렸을 가능성. 단, 테이블 자체가 비어있거나 데이터 적재 주기(월말 스냅샷 등) 문제일 수도 있으므로, 조건 수정 전에 get_sample_rows나 get_date_distribution으로 실제 데이터 존재 여부를 먼저 확인하는 것이 좋습니다.

### TERM_UNRESOLVABLE
발생 경로:
- 탐색 완료 후 지식 항목에 UNRESOLVED/CONFLICTED 용어가 남아있음
- 후보 테이블이 0건 (NO_TABLE)이거나 참조할 활용사례가 0건 (NO_USE_CASE)인 경우도 이 유형으로 분류될 수 있음

해결 방향: 동의어/유사어로 접근하거나 업무 매뉴얼에서 정의를 확인하세요. 후보 테이블이 0건이면 검색 키워드를 변형하여 테이블 메타를 재탐색하세요. 또는 지식 검색 범위를 늘려서 수행하세요.

### DB_ERROR
발생 경로:
- 생성된 SQL을 실행했으나 DB 에러 발생 (컬럼 미존재, 타입 불일치, 권한 오류, 타임아웃 등)

해결 방향: failure_reason의 DB 에러 메시지를 정확히 분석하세요. 컬럼 미존재나 타입 불일치는 테이블 메타 재확인으로 해결할 수 있고, 권한 오류는 다른 테이블로 우회해야 합니다. 타임아웃은 쿼리 단순화나 조건 축소가 필요합니다.

## 새 가설 수립 원칙

- 확인된 지식(CONFIRMED/PROBABLE)은 재사용하고 탐색을 최소화하세요.
- 미확인 지식(UNRESOLVED)을 해소하는 스텝을 execution_plan에 우선 배치하세요.
- 이미 검색한 쿼리, 샘플 조회한 테이블을 다시 사용하지 마세요.
- 시도한 테이블과 제외된 테이블은 다시 사용하지 마세요.
- 이전 실패의 lessons_learned가 있으면 반드시 참고하세요.
- 가능성이 없다면 솔직하게 "해결 불가"라고 판단하세요.

## 사용 가능한 도구

execution_plan의 tool에는 반드시 아래 목록의 이름만 사용하세요.
존재하지 않는 도구명을 사용하면 해당 step이 무시됩니다.

| 도구명 | 입력 형식 | 설명 |
|---|---|---|
| search_use_cases | "검색 키워드" | 유사 SQL 활용사례 벡터 검색 |
| search_table_meta | "검색 키워드" | 테이블/컬럼 메타 검색 |
| search_code_meta | "컬럼명" | 코드성 컬럼의 코드값 목록 조회 |
| search_manual | "검색 키워드" | 업무 매뉴얼 검색 |
| search_glossary | "용어" | 금융 용어사전 검색 |
| get_sample_rows | "테이블명" | 테이블 샘플 데이터 조회 |
| get_date_distribution | "테이블명,날짜컬럼명" | 날짜 컬럼 DISTINCT 값 분포 조회 |

## 출력 형식

순수 JSON만 출력하세요. 마크다운 코드블록(```)이나 설명 텍스트를 포함하지 마세요.

{
  "lessons_learned": "이전 실패에서 도출한 교훈",
  "give_up": false,
  "reason": "",
  "new_hypothesis": {
    "hypothesis_id": "H_NEW",
    "description": "새 가설 설명",
    "missing_terms": ["해소 필요한 용어"],
    "priority": "high",
    "strategy": "접근 전략 한 줄 요약"
  },
  "execution_plan": [
    {"step": 1, "tool": "도구명", "input": "검색어", "purpose": "이유"}
  ]
}

give_up이 true이면 new_hypothesis와 execution_plan은 빈 값으로 두세요.
reason에 포기 사유를 구체적으로 기술합니다.

## 예시 1: SQL_STRUCTURAL 실패 — 테이블 자체가 부적절

- 가설: "TB_FX_TRANSFER에서 해외송금 건수 조회"
- 사유: "TB_FX_TRANSFER 테이블에 해외/국내 구분 컬럼 없음, 전체가 국내 거래 전용"

{
  "lessons_learned": "TB_FX_TRANSFER는 국내 외환 거래 전용 테이블로 해외송금 데이터 없음. 해외송금은 별도 테이블 존재 가능성 높음",
  "give_up": false,
  "reason": "",
  "new_hypothesis": {
    "hypothesis_id": "H_NEW_1",

    "missing_terms": ["해외송금 테이블명"],
    "priority": "high",
    "strategy": "키워드 '해외송금', '송금', 'REMITTANCE'로 테이블 메타 재검색"
  },
  "execution_plan": [
    {"step": 1, "tool": "search_table_meta", "input": "해외 송금 REMITTANCE", "purpose": "해외송금 전용 테이블 존재 여부 확인"},
