생성된 SQL이 사용자의 질의 의도를 정확하게 반영하는지 검증하세요.

## 검증 기준 (8개)

1. **measure 반영**: 측정값이 SQL에 적절한 집계함수로 표현되었는가?
2. **filter 반영**: 조건이 WHERE 절에 반영되었는가?
3. **group_by 반영**: 그룹핑 기준이 GROUP BY/PARTITION BY/DISTINCT에 반영되었는가?
4. **order_limit 반영**: 정렬/제한이 ORDER BY / LIMIT에 반영되었는가?
5. **미확인 값 사용**: CONFIRMED되지 않은 코드값이나 컬럼명을 사용하지 않았는가?
6. **dead_end 반복**: 실패한 접근 패턴을 반복하지 않았는가?
7. **논리적 정합성**: SQL의 전체 로직이 사용자 질의의 의도와 부합하는가? 0건 반환은 질의 의도에 따라 유효할 수 있음(존재 여부 확인, 조건에 해당하는 데이터가 실제로 없는 경우 등). 0건 자체를 실패로 판정하지 말고 의도 부합 여부로 판단하라.
8. **DB 실행 결과**: DB 실행 에러가 있을 경우, 테이블 스키마(컬럼 타입)를 참고하여 원인을 분석하고 수정 방법을 제시하라. DB 실행이 성공(PASS)이면 pass=true.

## failure_classification 기준

verdict가 FAIL일 때, 아래 기준에 따라 failure_classification을 판정하라.

- "local_fix": SQL 표현만 수정하면 해결되는 문제. 테이블 선택과 전체 접근 방식은 유지.
  - 타입 불일치 (예: DATE 컬럼에 문자열 비교 → EXTRACT 또는 TO_CHAR로 변환)
  - 함수 오용 (예: LIKE를 DATE 컬럼에 사용 → 날짜 함수로 교체)
  - 컬럼명 오타/유사 컬럼 혼동 (예: LOAN_TYPE_CD → confirmed의 LOAN_DCD)
  - dialect 문법 오류 (예: PostgreSQL에서 TOP 사용 → LIMIT으로 변경)
  - 집계/GROUP BY 누락 등 SQL 구조 보완
  - DB 실행 에러 중 타입 캐스팅, 함수 변경 등으로 해결 가능한 경우

- "structural": SQL 표현 수정만으로는 해결 불가. 테이블 재선택이나 접근 방식 변경 필요.
  - 테이블에 필요한 데이터 자체가 없음 (0건 반환이 반복)
  - confirmed_terms에 없는 테이블/코드값을 사용해야만 질의 충족 가능
  - dead_end와 동일한 패턴 반복
  - 조인 경로가 존재하지 않음

## 출력 형식

순수 JSON만 출력하세요. 마크다운 코드블록(```)이나 설명 텍스트를 포함하지 마세요.

{
  "verdict": "PASS",
  "failure_classification": "",
  "checks": {
    "measure_reflected": {"pass": true, "detail": ""},
    "filters_reflected": {"pass": true, "detail": ""},
    "group_by_reflected": {"pass": true, "detail": ""},
    "order_limit_reflected": {"pass": true, "detail": ""},
    "no_unconfirmed_values": {"pass": true, "detail": ""},
    "no_dead_end_repeat": {"pass": true, "detail": ""},
    "logical_consistency": {"pass": true, "detail": ""},
    "db_execution": {"pass": true, "detail": ""}
  },
  "fix_instruction": ""
}

verdict는 "PASS" 또는 "FAIL" 중 하나.
하나라도 pass=false이면 verdict는 반드시 "FAIL"이어야 합니다.
failure_classification은 FAIL일 때만 "local_fix" 또는 "structural" 중 하나를 기재합니다. PASS이면 빈 문자열.
fix_instruction은 FAIL일 때만 작성하세요 — SQL 생성자가 즉시 수정할 수 있도록 구체적으로 기술합니다.

## 예시 1: PASS — 모든 체크 통과

사용자 질의: "지점별 이번 달 신규 대출 건수"
질의 분해: measures=[{term: "건수", agg: "COUNT"}], group_by=["지점"], filters=[{term: "기간", value: "이번 달"}, {term: "신규", value: ""}]
DB 실행 결과: PASS (5건 반환)
생성된 SQL:
```sql
SELECT B.BRANCH_NM AS 지점명, COUNT(*) AS 신규대출건수
FROM TB_LOAN_EXEC A
INNER JOIN TB_BRANCH B ON A.BRANCH_CD = B.BRANCH_CD
WHERE A.EXEC_DT >= DATE_TRUNC('month', CURRENT_DATE)
GROUP BY B.BRANCH_NM
ORDER BY 신규대출건수 DESC
LIMIT 1000
```

