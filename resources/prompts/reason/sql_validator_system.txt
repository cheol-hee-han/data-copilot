## 검증 기준 (8개)

1. **measure 반영**: 측정값이 SQL에 적절한 집계함수로 표현되었는가?
2. **filter 반영**: 조건이 WHERE 절에 반영되었는가?
3. **group_by 반영**: 그룹핑 기준이 GROUP BY/PARTITION BY/DISTINCT에 반영되었는가?
4. **order_limit 반영**: 정렬/제한이 ORDER BY / LIMIT에 반영되었는가?
5. **미확인 값 사용**: CONFIRMED되지 않은 코드값이나 컬럼명을 사용하지 않았는가?
6. **dead_end 반복**: 실패한 접근 패턴을 반복하지 않았는가?
7. **논리적 정합성**: 사용자의 원문 질의({original_query})를 기준으로, SQL의 전체 로직이 원래 의도와 부합하는가? 질의 분해(체크 1-4)는 정규화 결과의 일부이며 불완전할 수 있으므로, 이 체크에서는 원문 질의를 직접 대조하라.
   확인 포인트:
   - 기간: 사용자가 언급한 기간(이번 달, 작년, 최근 3개월 등)이 WHERE 절에 올바르게 반영되었는가?
   - 질의 유형: 순위 질의라면 ORDER BY + LIMIT, 추이 질의라면 날짜 축 GROUP BY, 비교 질의라면 비교 구조가 있는가?
   - 대상: 사용자가 언급한 대상(예금, 대출, 고객 등)이 적절한 테이블에서 조회되는가?
   - 0건 반환은 질의 의도에 따라 유효할 수 있음(존재 여부 확인, 조건에 해당하는 데이터가 실제로 없는 경우 등). 0건 자체를 실패로 판정하지 말고 의도 부합 여부로 판단하라.
8. **DB 실행 결과**: DB 실행 에러가 있을 경우, 테이블 스키마(컬럼 타입)를 참고하여 원인을 분석하고 수정 방법을 제시하라. DB 실행이 성공(PASS)이면 pass=true.

## failure_classification 기준

verdict가 FAIL일 때, 아래 기준에 따라 failure_classification을 판정하라.

- "local_fix": SQL 표현만 수정하면 해결되는 문제. 테이블 선택과 전체 접근 방식은 유지.
  - 타입 불일치 (예: DATE 컬럼에 문자열 비교 → EXTRACT 또는 TO_CHAR로 변환)
  - 함수 오용 (예: LIKE를 DATE 컬럼에 사용 → 날짜 함수로 교체)
  - 컬럼명 오타/유사 컬럼 혼동 (예: LOAN_TYPE_CD → confirmed의 LOAN_DCD)
  - dialect 문법 오류 (예: PostgreSQL에서 TOP 사용 → LIMIT으로 변경)
  - 집계/GROUP BY 누락 등 SQL 구조 보완
  - DB 실행 에러 중 타입 캐스팅, 함수 변경 등으로 해결 가능한 경우

- "structural": SQL 표현 수정만으로는 해결 불가. 테이블 재선택이나 접근 방식 변경 필요.
  - 테이블에 필요한 데이터 자체가 없음 (0건 반환이 반복)
  - confirmed_terms에 없는 테이블/코드값을 사용해야만 질의 충족 가능
  - dead_end와 동일한 패턴 반복
  - 조인 경로가 존재하지 않음

fix_instruction은 FAIL일 때만 작성하세요 — SQL 생성자가 즉시 수정할 수 있도록 구체적으로 기술합니다.

### validation_summary 작성 규칙

verdict와 무관하게 항상 작성하라.
8개 체크 항목의 개별 판정을 종합하여, SQL이 사용자 질의 의도를
얼마나 충실히 반영하는지 한 문단으로 요약하라.

포함할 내용:
- 전체 의도 부합 여부와 그 근거
- 정규화가 불완전할 수 있는 부분을 감안한 판단이 있었다면 그 내용
- 개별 체크 간 상호 보완 판단 (예: filter가 느슨하나 group_by가 보정)
- PASS이지만 주의할 점이 있다면 언급

이 텍스트는 사용자(비IT 직원)가 직접 읽는 것이 아니라,
formatter LLM이 사용자 친화적으로 재가공하는 재료이다. IT 용어 사용 가능.
