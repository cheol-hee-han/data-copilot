# 전체 관점 사고 원칙 (Holistic Thinking)

> **최상위 작업 원칙.** 모든 설계·구현·수정·보완 작업에 예외 없이 적용한다.
> 다른 규칙(code-style, data-security, financial-domain 등)과 충돌하지 않으며, 작업 접근 방식의 상위 가드레일이다.

## 왜 필요한가

좁은 시야로 "눈앞의 문제만" 해결하려 하면 다음과 같은 결과가 축적된다.

- 국소 해결책이 덧붙으며 **불필요한 복잡성**이 증가한다 (조건 분기, 예외 케이스, 플래그)
- **전체 구조·일관성**이 무너진다 (유사 책임이 여러 위치에 흩어짐, 네이밍 불일치, API 비대칭)
- **죽은 코드·중복 로직**이 정리되지 않고 잔존한다
- 한 번 더 생각하면 **근본적으로 더 나은 대안**이 있었음에도 섣부른 결정으로 품질이 저하된다
- 개별로는 맞지만 **전체 관점에서는 잘못된 최적화**가 이루어진다

## 작업 시 반드시 점검할 6가지 관점

어떤 작업이든(작은 버그 수정이라도) 결론을 내리기 전 아래 6가지를 한 번 더 점검한다.

1. **디자인(Design)** — 이 변경이 전체 아키텍처·책임 분배와 정합적인가? 책임이 이 위치에 있는 게 맞는가?
2. **일관성(Consistency)** — 기존 패턴·네이밍·인터페이스와 어긋나지 않는가? 유사 기능이 이미 존재하는가?
3. **유지보수성(Maintainability)** — 6개월 뒤 다른 사람이 읽고 고치기 쉬운 형태인가? 숨은 결합·암묵적 가정을 만들지 않는가?
4. **효율성(Efficiency)** — 중복 구현·불필요한 추상화·과도한 계층을 만들지 않는가? 기존 코드로 해결 가능한가?
5. **기능(Functionality)** — 요구된 기능을 정확히 달성하는가? 누락된 엣지케이스·회귀 위험이 없는가?
6. **성능(Performance)** — 호출 빈도·데이터 규모를 고려했을 때 실용적 성능인가? 조기 최적화가 아닌가?

## 작업 절차

### Step 1. 문제 범위 확장

"이 문제가 왜 발생했는가"를 질문하고, **동일한 근본 원인을 공유하는 다른 증상**이 없는지 주변을 둘러본다.
- 같은 패턴이 다른 파일·모듈에서도 반복되는가?
- 이 수정으로 다른 코드의 가정이 깨지지 않는가?

### Step 2. 최소 2개의 대안 비교

결론을 내리기 전 **적어도 2가지 접근 방식**을 떠올려본다.
- A안: 국소 수정 (patch 덧붙이기)
- B안: 근본 수정 (구조·책임 재배치)
- 두 안의 트레이드오프를 명시하고 선택 근거를 설명한다. A안을 선택하더라도 "왜 지금은 A가 맞는가"를 명확히 한다.

### Step 3. 정리(cleanup) 기회 탐색

이번 변경으로 **죽은 코드·중복·사용 안 되는 분기**가 드러나는지 확인한다.
- 이 변경으로 무엇이 쓸모없어지는가?
- 남겨두면 혼란을 줄 코드·주석·플래그가 있는가?
- 정리가 변경 범위를 과도하게 넓히지 않는다면 **같이 정리**한다. 넓어진다면 **별도 작업으로 명시적으로 제안**한다.

### Step 4. 확신보다 재검토

결론에 확신이 들더라도, 제출 전 **"전체 관점에서 최적인가"**를 한 번 더 자문한다.
- 사용자가 "이게 최선이야?"라고 물을 때 방어 대신 구조적 smell 을 정직하게 탐색할 수 있는가?
- 확신은 재검토의 적이다. 한 번 더 본다.

## 하지 말아야 할 것 (Anti-patterns)

- ❌ "일단 동작하게" 수준의 우회책을 근본 수정처럼 제시
- ❌ 독립적인 2개 축을 하나로 결합(예: format ↔ delivery, 모델 선택 ↔ 프롬프트 버전)
- ❌ 기존에 동일/유사 기능이 있는지 확인하지 않고 새로 구현
- ❌ 주변의 명백한 죽은 코드·중복을 보고도 "이번 업무 범위 아님"으로 넘김
- ❌ 단일 케이스 대응을 위한 특수 분기를 근본 구조에 삽입
- ❌ "나중에 정리하면 된다"는 전제로 부분 최적화 누적
