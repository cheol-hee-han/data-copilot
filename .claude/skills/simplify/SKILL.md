# 역할

코드 간결화 전문가. 동작은 유지하면서 코드를 더 단순하고 일관되게 만드는 것이 목표.
"작동하는 코드"를 "잘 작성된 코드"로 개선한다.

# 사용법

```
/simplify                        # 현재 구현된 모든 파일 전체 검토 + 자동 수정
/simplify src/agents/nodes/      # 특정 디렉토리 검토 + 자동 수정
/simplify src/services/foo.py    # 특정 파일 검토 + 자동 수정
/simplify --check-only           # 수정 없이 개선 포인트만 리스트업
/simplify --this                 # 현재 열린 파일 검토 + 자동 수정
```

# 검토 관점 (우선순위 순)

## 1. 기존 구현 재사용 (최우선)

새로 작성한 코드가 프로젝트에 이미 존재하는 기능을 중복 구현하고 있지 않은지 확인한다.

- `src/utils/` 의 공통 유틸리티와 중복되는 로직이 있는가?
- `src/services/` 에 이미 같은 역할의 서비스가 있는가?
- 같은 패턴의 코드가 다른 노드/서비스에 이미 구현되어 있는가?
- 기존 헬퍼 함수를 호출하면 되는데 인라인으로 다시 작성했는가?

**조치**: 중복 발견 시 기존 구현을 import하여 재사용하도록 수정한다.

## 2. 설계 원칙 및 패턴 준수

### 명확한 계층 분리

프로젝트에서 확립된 구체적 계층과 패턴이 있다면 준수하는지 확인한다. 
새 코드를 작성하기 전에 같은 계층의 기존 모듈에서 패턴을 먼저 파악한다.

- **추상화 계층 사용**: 외부 시스템(LLM, DB, ES, Qdrant) 호출은 반드시 추상화 계층(`utils/`, `connectors/`)을 통한다. SDK나 드라이버를 노드/서비스에서 직접 참조하지 않는다.
- **계층 책임 분리**: `nodes/`는 상태 전환과 위임만, 비즈니스 로직은 `services/`, 외부 통신은 `connectors/`, 공통 유틸은 `utils/`, graph state 외 모델은 `models/`. 의존 방향: nodes → services → connectors (역방향 금지)
- **프롬프트 관리**: 프롬프트는 `resources/prompts/` 외부 파일로 분리, 코드 내 하드코딩 금지

### 그 외 원칙

- **상태 관리**: Pydantic 모델의 deep copy 후 수정, 직접 mutation 금지. 정의된 Enum 멤버 사용 (raw string 금지)
- **설정 외부화**: 임계값·제한값 등 매직 넘버는 모듈 상단 상수 또는 `config.settings`로 분리
- **LangGraph 노드 반환**: 노드 함수는 변경된 필드만 `dict`로 반환, state 객체 전체를 반환하지 않는다

**조치**: 원칙/패턴 불일치 발견 시 프로젝트 표준으로 교정한다.

## 3. 불필요한 복잡도 제거

동작에 기여하지 않는 코드를 제거한다.

- 사용되지 않는 import, 변수, 함수, 클래스
- 도달 불가능한 코드 (dead code)
- 과도한 방어적 코딩 (내부 코드 간에 불필요한 검증)
- 한 번만 쓰이는 불필요한 추상화 (헬퍼, 래퍼)
- 가설적 미래 요구사항을 위한 코드 (YAGNI)

**조치**: 불필요한 코드를 삭제하거나 단순화한다.

## 4. 명명 일관성

프로젝트 명명 규칙을 따르는지 확인한다.

- 변수: 영어 snake_case, 의미가 명확한 이름
- 함수: 영어 snake_case, 동사로 시작, 의미가 명확한 이름 (예: `generate_sql()`, `fetch_user_data()`)
- 클래스: 영어 PascalCase
- Service 클래스: `XService` (예: `QueryPlanningService`)
- Node 클래스: `XNode` (예: `SQLGeneratorNode`)
- 상수: UPPER_SNAKE_CASE
- 파일명: snake_case, 의미가 명확한 이름
- Prompt 파일명: snake_case, 가능하다면 노드명과 일치, 노드와 1:1 아닌 경우 역할과 의도가 반영된 이름, 시스템 프롬프트와 유저 프롬프트를 `.txt` 앞에 구분 (예: `sql_generator_system.txt`)
- Node 파일명: snake_case, 노드 클래스명에서 Node를 제거한 이름과 일치 (예: `sql_generator.py`)
- Service 파일명: snake_case, 역할과 의미가 명확한 이름, 가능하다면 노드파일명과 일치 (예: `sql_generator.py`)
- 같은 개념에는 같은 이름으로 사용하고, 다른 이름 사용하지 않기 (예: `query` vs `input` vs `text`를 혼용)
- Enum 멤버: UPPER_SNAKE_CASE, 의미가 명확한 이름, 같은 개념에는 같은 이름으로 사용하고 다른 이름 사용하지 않기 (예: `CONFIRMED` vs `VERIFIED` vs `TRUE`를 혼용)

**조치**: 불일치하는 명명을 프로젝트 표준에 맞게 교정한다.

## 5. 타입 안전성

- 타입 힌트 누락 (함수 시그니처, 반환 타입)
- `Any` 타입의 불필요한 사용
- `Optional` 대신 `X | None` 사용 (Python 3.12)
- Pydantic 모델 필드의 타입과 실제 할당 값 불일치

**조치**: 타입 힌트를 추가하거나 교정한다.

# 작업 절차

1. **대상 파악**: 인자가 없으면 전체 src/, resources/ 파일 목록 확보
2. **기존 코드 탐색**: 변경된 코드가 참조하는 모듈과 같은 계층의 다른 모듈을 Read로 확인하여 패턴 파악
3. **검토 관점 순차 적용**: 위 우선순위대로 검토
4. **`--check-only`면 리포트만 출력**, 아니면 Edit으로 직접 수정
5. **수정 후 요약**: 무엇을 왜 바꿨는지 간결하게 설명

# 판단 기준

| 등급 | 기준 | 조치 |
|------|------|------|
| 즉시 수정 | 기존 구현과 중복 | 기존 코드 재사용으로 교체 |
| 즉시 수정 | 계층 분리 위반 (역방향 의존, SDK 직접 참조) | 추상화 계층 통해 호출하도록 교정 |
| 즉시 수정 | Enum 대신 raw string 사용 | Enum 멤버로 교체 |
| 즉시 수정 | 상태 직접 mutation / 노드 반환 패턴 위반 | deep copy + dict 반환으로 교정 |
| 권장 수정 | 불필요한 복잡도 | 단순화 |
| 권장 수정 | 명명 불일치 | 프로젝트 표준으로 교정 |
| 권장 수정 | 매직 넘버 하드코딩 | 모듈 상단 상수 또는 설정으로 분리 |
| 정보 | 타입 힌트 보강 가능 | 추가 |

# 수정하지 않는 것

- 동작 변경 (기능 추가/제거/수정)
- docstring 작성 (→ `/annotate` 스킬 사용)
- 보안 검토 (→ `@code-reviewer` 에이전트 사용)
- 성능 최적화 (프로파일링 근거 없는 추측 최적화 금지)
- 테스트 코드의 중복 (테스트는 명시적이어야 하므로 DRY보다 가독성 우선)
