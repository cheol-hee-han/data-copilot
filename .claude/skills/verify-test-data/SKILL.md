# 역할

테스트 데이터 품질 검증 전문가. 적재된 데이터가 요구사항 명세의 불완전성 요건을 모두 만족하는지 체계적으로 점검하고 결과를 보고.

# 핵심 원칙

- **요구사항 문서가 단일 진실 소스(Single Source of Truth)**
  - 테이블명, 컬럼명, 건수 기준, TYPE별 상세 요건, 품질 분포 비율 등 모든 구체적 수치는 요구사항 문서를 참조
  - SKILL.md에는 검증 절차와 판정 기준만 기술하고, 구체적 데이터 상세는 하드코딩하지 않음
- `docs/agent-guides/test-data-requirements.md`를 검증 기준으로 사용
  - 섹션 4: TYPE-1~4 불완전성 상세 요건 (테이블·컬럼·코드값·이중화 쌍)
  - 섹션 5: 테이블 카탈로그 (★ 테이블 목록, 테이블명, PK)
  - 섹션 6: 테이블 규모 요약 (총 수, ★ 수, ES 메타 수)
  - 섹션 7: ES 인덱스 명세 (인덱스별 목표 건수)
  - 섹션 8: Qdrant 컬렉션 명세 (목표 건수, 분포 비율)
- 각 TYPE(1~4) 별로 PASS/FAIL 판정
- FAIL 항목에는 원인과 보완 방법 제시
- 검증은 **읽기 전용** 쿼리만 사용 (데이터 수정 금지)

# 검증 항목

## 1. 연결 상태 점검

| 대상 | 확인 내용 |
|------|----------|
| PostgreSQL (정보계) | 연결 성공, `biz_schema` 존재 |
| PostgreSQL (이력) | 연결 성공, `sql_exec_log` 존재 |
| ElasticSearch | 연결 성공, 클러스터 상태 |
| Qdrant | 연결 성공, 컬렉션 목록 |

## 2. 데이터 건수 검증

**요구사항 문서 섹션 5/6/7/8에서 최신 기준값을 읽고 비교합니다.**

### PG 검증
- `biz_schema` 내 테이블 수가 섹션 6 합계와 일치하는지 (`information_schema.tables`)
- 각 ★ 테이블 행 수가 최소 건수 이상인지 (★ 목록은 섹션 5에서 확인)

### ES 검증
- 각 인덱스 문서 수가 섹션 7의 목표 건수 이상인지 (`_count`)

### Qdrant 검증
- 각 컬렉션 포인트 수가 섹션 8의 목표 건수 이상인지

## 3. TYPE-1 검증: 테이블 선택 모호성

**요구사항 문서 섹션 4 TYPE-1의 핵심 재현 위치 테이블에서:**

- 유사 테이블 쌍이 모두 PG에 존재하는지
- 공통 키(EDPS_CSN, ACN, LN_NO 등)로 실제 매칭되는지
- 동일 키에 대해 값이 다른 행이 존재하는지 (TYPE-4와 연계)

**PASS 기준**: 유사 테이블 쌍이 모두 존재하고, 공통 키로 매칭되며, 값 차이가 있는 행이 존재

## 4. TYPE-2 검증: 코드값 불일치

**요구사항 문서 섹션 4 TYPE-2의 핵심 재현 목록에서:**

- PG 실데이터에 ES `code_meta`에 없는 미정의 코드가 존재하는지
- ES `code_meta`에 미정의 코드가 잘못 포함되어 있지 않은지 (공식 코드만 정의되어야 함)
- 각 테이블·컬럼에 대해 미정의 코드가 1건 이상 존재하는지

**PASS 기준**: 요구사항 문서의 모든 TYPE-2 케이스에서 미정의 코드가 PG에 존재하고, ES에는 미포함

## 5. TYPE-3 검증: 메타 설명 부실

**요구사항 문서 섹션 4 TYPE-3의 품질 분포 비율에서:**

- ES `table_meta`/`column_meta`의 설명 품질 분포가 요구사항의 목표 비율과 일치하는지
- 필수 POOR/MISSING 케이스가 모두 반영되어 있는지

**PASS 기준**: POOR + MISSING 비율이 요구사항 목표 이상이고, 필수 케이스가 모두 존재

## 6. TYPE-4 검증: 데이터 이중화

**요구사항 문서 섹션 4 TYPE-4의 핵심 재현 목록에서:**

- 이중화 테이블 쌍이 모두 PG에 존재하는지
- 동일 키에 대해 값이 다른 행이 존재하는지

**PASS 기준**: 각 이중화 쌍에서 값이 다른 행이 존재

## 7. Qdrant 컬렉션 검증

- `biz_manual`: 요구사항 섹션 8의 필수 주제(계수산출식 등) 포함 확인
- `sql_history`: 페이로드 구조 (`description`, `sql`, `tables_used`, `complexity`, `domain`) 확인
- `sql_history`: 복잡도/도메인 분포가 요구사항의 비율 ±5% 이내인지
- 벡터 차원 = `EMBEDDING_DIM` (384) 일치 확인

## 8. 교차 정합성 검증

- PG 테이블 목록 ↔ ES `table_meta` 문서 목록 일치
- PG 코드 컬럼 ↔ ES `code_meta` 코드 그룹 매핑 확인
- ES `term_dict` 용어 ↔ 실제 컬럼명 매칭 확인

# 작업 절차

1. `test-data-requirements.md`의 **최신** 요구사항을 읽고 검증 기준값 파악
2. `.env`에서 모든 저장소 연결 정보 확인
3. 각 저장소 연결 테스트
4. 데이터 건수 검증 (요구사항 문서 기준값 대비)
5. TYPE-1 ~ TYPE-4 순차 검증 (요구사항 문서 섹션 4 기준)
6. Qdrant 컬렉션 검증 (요구사항 문서 섹션 8 기준)
7. 교차 정합성 검증
8. 검증 보고서 출력
9. FAIL 항목에 대한 보완 방법 제시

# 산출물 위치

- 검증 스크립트: `standalone/scripts/verify_test_data.py`
- 검증 보고서: `docs/reports/data-verification-report.md`

# 인자 사용법

- `$ARGUMENTS` 없이 호출: 전체 검증
- `$ARGUMENTS`에 저장소명 지정: 해당 저장소만 검증 (예: `/verify-test-data pg`)
- `$ARGUMENTS`에 TYPE 지정: 해당 유형만 검증 (예: `/verify-test-data type-2`)
