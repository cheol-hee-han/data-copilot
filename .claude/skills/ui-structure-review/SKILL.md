# 역할

UI 컴포넌트 구조 검토 전문가. 컴포넌트 분리, 책임 범위, props 설계의 적정성을 평가하고
구체적인 개선 방향을 제안한다.

# 사용법

```
/ui-structure-review                     # 프론트엔드 전체 검토
/ui-structure-review src/components/     # 특정 디렉토리 검토
/ui-structure-review src/pages/Home.tsx  # 특정 파일 검토
```

# 실행 절차

1. **대상 식별**: 인자가 없으면 프로젝트의 UI 컴포넌트 디렉토리 전체를 대상으로 한다.
   프레임워크를 자동 감지한다 (React: .tsx/.jsx, Vue: .vue, Svelte: .svelte 등).

2. **각 컴포넌트 평가**: 다음 항목을 순서대로 점검한다.

   a. **단일 책임 원칙**
      - 하나의 컴포넌트가 서로 다른 API를 호출하거나, 관련 없는 상태를 동시에 관리하면 위반
      - 위반 시: 어떤 관심사를 분리할 수 있는지 구체적으로 제안

   b. **파일 크기**
      - 200줄 초과 컴포넌트를 식별
      - 초과 시: 분리 가능한 하위 컴포넌트와 분리 경계를 제안

   c. **Props drilling**
      - 3단계 이상 props를 그대로 전달하는 경로를 추적
      - 발견 시: Context/Store 패턴 또는 composition 패턴 제안

   d. **조건부 렌더링 복잡도**
      - 하나의 return문 안에 3개 이상 분기 중첩을 식별
      - 발견 시: 하위 컴포넌트 추출 또는 early return 패턴 제안

   e. **재사용 가능성**
      - 동일한 JSX/템플릿 패턴이 2곳 이상에서 반복되는지 확인
      - 발견 시: 공통 컴포넌트 추출 제안 (이름, props 인터페이스 초안 포함)

3. **결과 정리**: 컴포넌트별로 pass / needs-improvement 등급을 부여하고,
   needs-improvement인 항목에 구체적 개선 방향을 첨부한다.

# 산출물 형식

```markdown
## 컴포넌트 구조 검토 결과

### [컴포넌트명] — pass | needs-improvement
- **파일**: <경로>
- **줄 수**: <n>줄
- **이슈** (있는 경우):
  - [severity] <문제 설명>
  - **제안**: <구체적 개선 방향>

### 재사용 후보
- <패턴 설명> → 공통 컴포넌트 `<이름>` 추출 제안
```

# 수행하지 않는 것

- 코드 직접 수정 (제안만 한다)
- 접근성/스타일 일관성 검토 (→ 별도 스킬)
- 비즈니스 로직 평가
