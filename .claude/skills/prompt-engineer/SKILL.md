# Qwen3.5-397B-A17B 프롬프트 엔지니어링 스킬

이 스킬은 Qwen3.5-397B-A17B 모델 전용 프롬프트를 생성하거나 수정하는 규칙을 정의한다.
사용자의 지시를 받으면 아래 규칙을 적용하여 바로 수행한다.

복잡한 에이전트 모듈 프롬프트는 `docs/agent-guides/prompt-rules.md` 를 추가로 참고한다.

# 사용법

```
/prompt-engineer                                                                                   # 프로젝트 전체의 문서 정비
/prompt-engineer resources/prompts/reason/                                                         # 디렉토리 전체 점검·정비
/prompt-engineer resources/prompts/reason/context_interpreter_system.txt                           # 특정 파일 점검·정비
/prompt-engineer resources/prompts/reason/ resources/prompts/reason/context_interpreter_system.txt # 디렉토리 하위 전체와 특정 파일 점검·정비
/prompt-engineer --check-only                                                                      # 정비 없이 부족한 곳만 리스트업
/prompt-engineer --this                                                                            # 현재 작업 중인 파일에 대해서만 점검·정비
```

## 1. 프롬프트 유형 분류

생성 전 유형을 먼저 식별한다. 유형에 따라 적용 규칙이 달라진다.

- 단순형: 단일 지시, 단순 출력 (챗봇, 요약, 분류 등)
- 에이전트 계획 수립형: 도구 실행 계획 수립, 다음 행동 결정 → `docs/agent-guides/prompt-rules.md` 참고
- 에이전트 분석 판정형: 도구 결과 해석, 지식 갱신, 판정 → `docs/agent-guides/prompt-rules.md` 참고

유형이 불명확하면 사용자에게 확인한다.

## 2. 구조 표기 규칙

### 지시/제어 영역 — [TAG] 형식

```
[ROLE]
[CONTEXT]
[RULES]
[TOOLS]
[EXAMPLES]
[OUTPUT_CONTRACT]
[TASK]       ← 반드시 마지막
```

- 태그는 영어 대문자로만 쓴다
- 모든 태그가 필수는 아니다. 유형에 따라 필요한 태그만 사용한다
- 블록이 필요한 경우: `[TAG]...[/TAG]`
- 지시 태그와 식별자 태그를 혼용하지 않는다

### 문서/지식 영역 — ## 형식

- 대주제: `##`, 소주제: `###`
- 계층은 최대 3단계(`##`, `###`, `####`)까지만 허용한다
- 3단계 초과 시 새로운 `##` 섹션으로 분리한다

### 항목 나열 — `-` 하이픈

- 순서가 중요한 절차에만 숫자를 쓴다
- 항목에 설명이 한 줄이면 콜론으로 이어쓴다
- 항목 설명이 두 줄 이상이면 `###` 로 승격한다
- 중첩은 1단계까지만 허용한다 (초과 시 새 `##` 섹션으로 분리)

### 부연설명 — 인라인 괄호

- 짧은 부연: 항목 뒤에 `(부연 내용)` 형식으로 작성
- 긴 부연: 별도 항목으로 분리하거나 평문으로 작성
- `[NOTE]` 태그는 지시 태그와 형태가 동일하므로 사용하지 않는다

### 조건-결과 매핑 — `→` 형식

```
- 테이블 메타에서 컬럼 존재 확인 → CANDIDATE (confidence 0.3~0.5)
- 샘플 데이터에서 실제 값 확인 → CONFIRMED (confidence 0.8~0.95)
```

산문으로 섞어 쓰지 않는다. 모델이 조건과 결과를 직접 파싱한다.

### 판단 기준 이중 구조

하나의 판단이 "해야 할 때"와 "하지 않아도 될 때"를 모두 포함할 때는 명시적으로 분리한다.

```
fail로 판단하는 경우:
- 조건값이 코드 매핑에 없음
- 필요한 컬럼이 테이블에 없음

success를 유지하는 경우 (결과 정확성에 영향 없는 불확실성):
- 날짜 범위 해석, 정렬 방향, 행 제한 수
```

## 3. 식별자 표기 규칙

지식 항목, 스텝, 가설 등 식별자가 필요한 경우 아래 형식을 따른다.

```
# 지식 항목 식별자 — 소문자 괄호
(k1) measure: 평균 여신 잔액
 - 상태: PROBABLE
 - 값: AVG(LN_BAL_AMT)
 - 확인근거: TB_ADW_LNB301M에서 잔액 집계 패턴 확인
             (도구: search_use_cases("고객 마스터 정보", page=1))

# 스텝 식별자 — ### [Step N]
### [Step 1] tool_name(input)

# 가설 식별자 — H_숫자
H_R1, H_R2
```

- 지시 태그 `[TAG]`와 혼동을 피하기 위해 식별자에 대괄호를 쓰지 않는다
- `##`, `###` 계층과 혼동을 피하기 위해 `#` prefix를 쓰지 않는다

## 4. 설명 본문 규칙

- 한 문단 3줄 이내
- 들여쓰기로 설명을 구분하지 않는다

## 5. 주입 데이터 형식 규칙

플레이스홀더 자리에 주입되는 데이터의 형식 기준이다.

| 데이터 성격 | 권장 형식 |
|---|---|
| 단일 스칼라 값 | 인라인 자연어 |
| 상태+근거가 있는 항목 | `(kN)` 레이블 형식 |
| 실패/오류 기록 | `- [TYPE] 설명 \n  교훈: ...` |
| 복수 반복 블록 | `### [Step N]` + `---` 구분자 |

JSON을 입력으로 주입하지 않는다. JSON은 출력 형식에만 사용한다.

### 플레이스홀더 의미 명시 원칙

플레이스홀더의 형식은 코드에서 치환되어 주입되므로 프롬프트에서 형식을 재정의할 필요는 없다.
대신 해당 데이터가 **무엇이고, 어떻게 활용해야 하는지** 의미를 명시한다.

```
## 도구 실행 결과

{tool_results}

위는 지금까지의 모든 도구 실행 결과입니다.
- 이미 실행한 검색을 반복하지 마세요.
- 결과가 부족했다면 page=N으로 다음 페이지를 조회하세요.
```

의미가 자명한 단순 스칼라({query}, {today} 등)에는 별도 설명이 불필요하다.

## 6. 모듈 간 데이터 전달 규칙

에이전트 루프에서 한 모듈의 출력이 다음 모듈의 입력으로 전달된다.

이 모듈의 `[OUTPUT_CONTRACT]`에 명시된 형식이
다음 모듈이 플레이스홀더로 받는 형식과 동일해야 한다.

```
이 모듈 [OUTPUT_CONTRACT]:
  "dead_ends": [{"type": "TERM_UNRESOLVABLE", "lesson": "..."}]

다음 모듈 플레이스홀더 형식 명시:
  {dead_ends_summary} 는 아래 형식으로 제공된다:
  - [TYPE] 설명
    교훈: ...
```

형식이 불일치하면 다음 모듈이 데이터를 잘못 파싱한다.

## 7. [OUTPUT_CONTRACT] 작성 규칙

`[OUTPUT]` 대신 `[OUTPUT_CONTRACT]` 를 쓴다.
CONTRACT는 형식을 반드시 지켜야 한다는 의미를 강화한다.

### 스키마 기술 방식

필드명, 타입, 허용값, 조건을 명시한다.

```
"action": "replan" | "give_up"
"confidence": number (0.0~1.0)
"status": "CANDIDATE" | "PROBABLE" | "CONFIRMED" | "CONFLICTED"
```

### 조건부 필드 기술 방식

상황에 따라 포함/생략/빈값이 달라지는 필드는 선언 바로 아래에 조건을 명시한다.

```
"execution_plan": array
- action이 give_up이면 빈 배열([])로 출력
- action이 replan이면 1~4개 스텝 포함

"new_hypothesis": object | null
- 이전 가설과 다른 접근일 때만 포함
- 없으면 null로 출력 (필드 생략 금지)
```

### 출력 품질 기준 — 좋은 예/나쁜 예

출력 필드의 품질 기준이 주관적일 때 좋은 예/나쁜 예를 함께 기술한다.

```
failure_reasons 작성 기준:
- 나쁜 예: "코드값 부족"
- 좋은 예: "LN_STCD 코드값 매핑 없음 — WHERE 조건에 대출상태 필터 필요"
```

### 출력 형식 위반 방지

- JSON 앞뒤에 마크다운 코드블록(` ``` `), 설명 텍스트 금지
- 모든 string 필드는 비워두지 않는다
- 필드 생략과 null은 다르다. null로 정의된 필드는 null로 출력한다

## 8. 사고 과정 강제 패턴

모델이 특정 순서로 판단해야 하는 경우 STEP 번호로 강제한다.

```
## 사고 과정

STEP 1: 사용자가 원하는 데이터가 무엇인지 파악
STEP 2: 확인된 지식 항목에서 테이블/컬럼을 찾음
STEP 3: 참고 SQL이 있으면 조인 구조·집계 방식을 참고
STEP 4: 충분성 판단 — STEP 2~3에서 모두 확인되었는가?
        하나라도 빠지면 즉시 fail을 출력한다
```

STEP 중간에 분기 조건(충분성 판단, 즉시 종료 등)을 명시한다.
이 패턴은 다단계 판단이 필요하고 순서 오류가 결과에 직접 영향을 줄 때 사용한다.

## 9. 환각 방지 규칙 기술 패턴

모델이 존재하지 않는 값을 생성하는 것을 방지할 때 사용한다.

```
## 환각 방지 규칙

1. {section}에 나열되지 않은 테이블명을 사용하지 않는다
2. 컬럼 목록에 없는 컬럼명을 사용하지 않는다
3. 코드값 매핑에 없는 코드값을 사용하지 않는다

위반 예시:
- confirmed_terms에 TB_A만 있는데 TB_B를 사용 → 금지
- 컬럼 목록에 LN_NO만 있는데 OVERDUE_RATE를 사용 → 금지
```

위반 예시를 함께 기술한다. 추상적 금지보다 구체적 예시가 훨씬 효과적이다.

## 10. 조건 분기 섹션 기술 패턴

런타임 변수 값에 따라 적용 규칙이 달라질 때 사용한다.

```
## dialect별 규칙

### Sybase IQ (dialect = tsql)
- 행 제한: SELECT TOP N
- 문자열 결합: col1 + col2

### PostgreSQL (dialect = postgresql)
- 행 제한: LIMIT N
- 문자열 결합: col1 || col2
```

각 분기를 독립적인 `###` 섹션으로 분리한다.
섹션 제목에 분기 조건(`dialect = tsql`)을 명시한다.

## 11. 테이블 형식 조건-결과 매핑

케이스가 많고 구조가 일정할 때 `→` 나열 대신 테이블을 쓴다.

```
| 단위 | 승수       | 예시  | 변환        |
|------|------------|-------|-------------|
| 천   | ×1,000     | 5천   | 5,000       |
| 만   | ×10,000    | 15만  | 150,000     |
| 억   | ×100,000,000 | 1억 | 100,000,000 |
```

3개 이하 케이스는 `→` 형식, 4개 이상은 테이블 형식이 가독성이 높다.

## 12. [SELF_CHECK] 출력 규칙

생성 후 반드시 아래 항목을 검증하고 결과를 출력한다.

```
[SELF_CHECK]
- 플레이스홀더명이 치환 코드(.replace())의 키와 일치하는가: (일치/불일치 — 불일치 시 항목 나열)
- [OUTPUT_CONTRACT]가 다음 모듈의 플레이스홀더 의미와 정합하는가: (정합/불일치 — 해당 없으면 N/A)
- 같은 계층 기존 프롬프트와 형식이 일관되는가: (일관/차이 — 차이 시 사유)
- 금지 패턴 없음: (완료/미완료)
```

## 13. 금지 패턴

- 구분선 (`────`)
- 이모지
- 4단계 이상 들여쓰기
- 볼드 남용
- API 파라미터 기재 (`enable_thinking`, `temperature` 등)
- `[TASK]`를 중간에 배치
- 도구 명세에 번호 목록 사용 (우선순위 오해 유발)
- 조건-결과 매핑을 산문으로 기술
- 식별자에 대괄호 사용 (`[K1]` → `(k1)`)
- 입력 데이터에 JSON 사용

## 14. 언어 정책

- 태그: 영어 대문자
- 필드명: 영어 소문자 스네이크케이스
- 본문 설명: 사용자 입력 언어를 따른다
- 예시 JSON의 string 값: 한국어 허용
