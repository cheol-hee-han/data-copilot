# Qwen3.5-397B-A17B 프롬프트 엔지니어링 스킬

이 스킬은 Qwen3.5-397B-A17B(MoE, 512 experts / 10+1 active) 모델 전용 프롬프트를
생성하거나 수정하는 규칙을 정의한다. 사용자의 지시를 받으면 아래 규칙을 적용하여 바로 수행한다.

- 에이전트 모듈 전용 추가 규칙: `docs/agent-guides/prompt-rules.md`
- 본 지침의 근거·기각된 대안·레퍼런스: `docs/todo/qwen35-prompting-skill-strategy.md`

## 사용법

```
/prompt-engineer                                                          # 프로젝트 전체 점검·정비
/prompt-engineer resources/prompts/reason/                                # 디렉토리 전체 점검·정비
/prompt-engineer resources/prompts/reason/context_interpreter_system.txt  # 특정 파일 점검·정비
/prompt-engineer --check-only                                             # 정비 없이 부족한 곳만 리스트업
/prompt-engineer --this                                                   # 현재 열려 있는 파일에 대해서만 점검·정비
```

## 0. 최우선 원칙 — 모델 응답 성능이 규칙보다 우선한다

본 스킬의 모든 규칙은 Qwen3.5 계열의 일반적 실패 모드를 막기 위한 **경험칙**이다.
규칙은 수단이며, **노드의 실제 응답 성능이 본질적 목표**다. §0.1 이하의 모든 규칙은
"반박 가능한 경험칙"으로 읽는다.

규칙을 기계 적용할 때 두 가지 실패가 발생한다. 이 두 함정을 경계하는 것이 본 원칙의
핵심이다.

1. **방어 과잉**: 특정 실패 모드를 막기 위한 규칙이, 그 실패 모드가 없는 노드에도 적용되어
   모델의 창발적 능력을 억누른다. (예: "예시 3개 상한"은 평이한 예시 남발을 막기 위한 것이지
   풍부한 예시 자체를 막는 것이 아니다)
2. **구조적 해결책 차단**: 진짜 성능 개선은 출력 스키마·블록 구조 변경에서 오는데, 규칙이
   기존 구조를 고정하면 그 경로 자체가 탐색되지 않는다

### 규칙을 벗어날 때 조건

- **근거 있는 가설**: 벗어나려는 규칙이 해당 노드 성능을 실제 저해한다는 메커니즘을 설명
- **성능 지향 대안**: 벗어난 설계가 성능을 올리는 구체 경로를 제시
- **위반 범위 최소화**: 필요한 최소 범위에만 한정, 관련 없는 규칙까지 느슨해져선 안 됨
- **명시와 보고**: 벗어난 §N과 이유를 파일·설계 문서에 기록하고 사용자에게 보고
- **일반화 판단**: 노드 한정 예외인지 스킬 전체 갱신 대상인지 판단, 후자면 본 문서 업데이트

본 원칙은 "규칙을 편하게 어긴다"가 아니다. **"규칙을 지킬 때도 어길 때도 판단 기준은
노드의 응답 성능"** 이라는 뜻이다.

## 0.1 대원칙 — 3계층 분리

프롬프트를 쓰기 전에 어느 계층의 문제인지 먼저 판정한다.

1. **인프라 계층**: thinking 모드, temperature, top_p, top_k, presence_penalty, guided_json — **`src/utils/llm/client.py` 또는 노드 호출 코드에서 설정. 프롬프트 본문에 절대 기재하지 않는다.**
2. **프롬프트 계층**: ROLE, RULES, CONTEXT, TOOLS, EXAMPLES, OUTPUT_CONTRACT, HALLUCINATION_GUARD, TASK — 본 스킬이 담당.
3. **코드 계층**: JSON fence/trailing 제거 재시도, `reasoning_summary` 교차 검증, fail 시 recovery 라우팅 — 노드 코드에서 처리.

각 계층이 서로의 책임을 침범하면 방어 구조가 무너진다.

## 1. 노드별 thinking 정책 (프롬프트 계층의 전제)

프롬프트 자체가 아니라 **어떤 mode로 호출될지**를 먼저 알아야 글을 쓸 수 있다. 아래 표를
먼저 확인하고, 노드 코드가 `_resolve_thinking_params(model, mode=...)`에 올바른 mode를
넘기는지 점검한다.

| 노드 | thinking | 비고 |
|---|---|---|
| `context_interpreter` | **ON** | 다단계 교차 참조 추론 / 스텝별 `insight`+`evidence`로 근거 분산 (§5.2 예외, `reasoning_summary` 면제) |
| `recovery_agent` | **ON** | 실패 진단 + 재계획 / `reasoning_summary` 필수 |
| `sql_generator` | **ON** | 복잡 SQL 생성 / `reasoning_summary` 필수 |
| `analyzer` | **ON** | 인사이트 도출 다단계 추론 / `reasoning_summary` 필수 |
| `intent_classifier` | OFF | 결정성 우선 |
| `query_normalizer phase1` | OFF | JSON 안정성 우선 |
| `query_normalizer phase2` | OFF | 교차검증 체크리스트 |
| `sql_validator` | OFF | 교차 검증자 역할 — 결정성 절대 우선 |
| `analyzer_viz_judgment` | OFF | 이산 선택 |
| `analyzer_viz_svg` | OFF | 구조화 출력 |

thinking ON 4개 노드는 반드시 `[HALLUCINATION_GUARD]` + `reasoning_summary` 필드(§5.2 예외 제외) +
`[TASK]` 말미 재강조를 동반한다(§5, §6, §9).

프롬프트 본문에는 `enable_thinking`, `/no_think`, `<think>`, temperature 같은 어떤 인프라
파라미터도 기재하지 않는다. 본 스킬의 가장 강한 금지 규칙이다.

## 2. 프롬프트 유형 분류

생성·수정 전 유형을 먼저 식별한다. 유형에 따라 블록 집합과 배치 순서가 달라진다.

- **단순형**: 단일 지시, 단순 출력. 예: `intent_classifier`, `analyzer_viz_judgment`, `analyzer_viz_svg`
- **에이전트 계획 수립형**: 도구 실행 계획, 다음 행동 결정. 예: `recovery_agent`, `sql_generator`
- **에이전트 분석 판정형**: 도구 결과 해석, 지식 갱신, 판정. 예: `context_interpreter`, `query_normalizer phase1/phase2`, `sql_validator`, `analyzer`

유형이 불명확하면 사용자에게 확인한다. 에이전트 유형은 `prompt-rules.md`를 반드시 함께 참고한다.

## 3. 구조 표기 규칙

### 3.1 지시/제어 영역 — `[TAG]` 형식

```
[ROLE]
[MISSION]              ← 계획 수립형 선택
[CONTEXT]
[HARD_CONSTRAINTS]     ← 위반 시 즉시 fail
[RULES]
[TOOLS]                ← 계획 수립형 전용
[EXAMPLES]
[OUTPUT_CONTRACT]
[HALLUCINATION_GUARD]
[TASK]                 ← 반드시 마지막
```

- 태그는 영어 대문자 스네이크
- 모든 태그가 필수는 아님. 유형에 따라 필요한 태그만 사용
- 블록이 필요한 경우: `[TAG]...[/TAG]`
- 지시 태그 `[TAG]`와 식별자 `(k1)`, 스텝 `[Step N]`을 혼용하지 않는다

### 3.2 문서/지식 영역 — `##` 형식

- 대주제 `##`, 소주제 `###`, 최대 `####`까지
- 초과 시 새 `##` 섹션으로 분리

### 3.3 규칙 리스트 분량 상한 (MoE 라우팅 대응)

**왜**: Qwen3.5 MoE는 한 카테고리에 규칙이 6개 이상 나열되면 라우팅 분기 과정에서 중간 규칙이 무시되는 경향이 있다.

**어떻게**:

- **카테고리당 최대 5 규칙**, 초과 시 카테고리 분리
- **한 `[RULES]` 블록 내 총 20 규칙 이내**
- 초과 시 `[HARD_CONSTRAINTS]`, `[HALLUCINATION_GUARD]` 등 별도 섹션으로 분할

"5개를 6개로 늘리는" 절충은 허용하지 않는다. 규칙이 늘면 반드시 쪼갠다.

### 3.4 항목 나열 — `-` 하이픈

- 순서가 중요한 절차에만 숫자
- 항목 설명 한 줄이면 콜론으로 이어쓰기
- 두 줄 이상이면 `###` 승격
- 중첩은 1단계까지만 허용

### 3.5 조건-결과 매핑 — `→` 형식

```
- 테이블 메타에서 컬럼 존재 확인 → CANDIDATE (confidence 0.3~0.5)
- 샘플 데이터에서 실제 값 확인 → CONFIRMED (confidence 0.8~0.95)
```

산문으로 섞어 쓰지 않는다. 케이스가 4개 이상이면 테이블(§14) 사용.

### 3.6 판단 이중 구조

한 판단이 "해야 할 때"와 "하지 않아도 될 때"를 동시에 가질 때는 명시적으로 분리한다.

```
fail로 판단하는 경우:
- 조건값이 코드 매핑에 없음
- 필요한 컬럼이 테이블에 없음

success를 유지하는 경우 (결과 정확성에 영향 없는 불확실성):
- 날짜 범위 해석, 정렬 방향, 행 제한 수
```

### 3.7 Positive Form 우선 원칙 (필수)

**무엇**: 제약은 기본적으로 "허용되는 것"을 적는 positive form으로 쓴다. "금지되는 것"은 예외적으로만.

**왜**: negative 문장("X 하지 마라")은 금지 대상 토큰을 먼저 생성해 오히려 해당 패턴을 priming한다. instruction-tuned LLM은 positive form 준수율이 유의하게 높다.

**어떻게**:

- "INSERT/UPDATE/DELETE를 사용하지 말 것" → "생성하는 SQL은 SELECT 구문으로만 구성한다"
- "스키마에 없는 컬럼을 쓰지 말 것" → "[INPUT_CONTEXT]의 컬럼 목록에 있는 컬럼만 사용한다"
- "설명을 붙이지 말 것" → "JSON 객체 하나만 출력한다"

**예외 1 — HALLUCINATION_GUARD 위반 예시**: `[HALLUCINATION_GUARD]`의 "위반 예시"는
구체 예시 제시 목적이므로 negative 형태로 두되, 반드시 "올바른 대응"과 쌍으로 제시한다(§6).

**예외 2 — 분류 서술(classification statement)**: "X는 Y 집합에 속하지 않는다" 형태의
타입·소속 기술은 허용한다. 이는 **행동 금지**("X를 쓰지 마라")가 아니라 **슬롯의 타입
경계 정의**이므로 priming 부작용이 작다. 행동 금지는 동사(쓰다/사용하다)를 부정해
대상 토큰을 컨텍스트 상위로 올리지만, 분류 서술은 "X의 소속 집합이 Y가 아니다"라는
관계 기술이라 대상 토큰이 후보 분포에 올라오는 효과가 약하다.

- 허용: "agg_function을 고를 때 modifiers[].type 아래의 PERCENTAGE·DELTA_RATE는 후보가 아니다"
- 허용: "EXIST_CHECK와 DEDUP은 primary 후보가 아니다"
- 금지: "PERCENTAGE를 agg_function에 쓰지 마라"
- 금지: "EXIST_CHECK를 primary로 선택하지 마라"

예외 2를 적용할 때도 가능하면 positive form 병기를 권장한다. 예: 분류 서술 바로 옆에
"agg_function은 SUM/AVG/COUNT/… 중에서 고른다" 같은 허용 목록 언급을 추가하면 방어가
이중화된다.

### 3.8 식별자 표기

```
(k1) measure: 평균 여신 잔액         # 지식 항목 — 소문자 괄호
### [Step 1] tool_name(input)         # 스텝 — ### [Step N]
H_R1, H_R2                            # 가설 — H_숫자
```

식별자에 대괄호(`[K1]`)를 쓰지 않는다. 지시 태그 `[TAG]`와 혼동 방지.

### 3.9 부연설명

- 짧은 부연: 항목 뒤 `(부연 내용)`
- 긴 부연: 별도 항목 또는 평문
- `[NOTE]` 같은 지시 태그 형태 부연 금지

### 3.10 이해가능성 우선 원칙 (간결성과의 균형)

**본 원칙은 §3의 다른 모든 상한·축약 규칙(§3.3 카테고리 5개 상한, §3.4 콜론 이어쓰기,
§3.6 판단 이중 구조, §9 2줄 상한 등)보다 우선한다.**

**무엇**: 내용이 본질적으로 복잡할 때는 간결성 규칙을 완화하고, **LLM이 그 줄만 읽고도
올바르게 해석할 수 있도록** 충분히 풀어 쓴다. 간결성은 수단이지 목적이 아니다.

**왜**: 본 스킬의 대다수 규칙은 MoE 라우팅 드롭·토큰 예산·lost-in-the-middle 같은
"과잉 서술의 부작용"을 막기 위한 상한이다. 그러나 복잡한 판단 로직을 무리하게 줄이면
정반대의 실패, 즉 **축약된 추상 라벨만 남아 디코더 LLM이 해석 불가능한 상태**가 된다.
읽는 주체가 인간이면 줄 사이 행간을 채워 넣지만, LLM은 그러지 못한다. 간결성 규칙을
기계적으로 적용해 내용을 이해할 수 없게 되는 순간, 그 축약은 자기 목적을 배반한다.

**어떻게 — 풀어 쓰기를 적용할 조건**:

다음 중 하나라도 해당하면 상한을 완화하고 중첩/분리/예시를 추가한다.

- **복수 조건의 AND/OR 관계**: "a, b, c를 모두 만족해야 한다" 같은 문장을 한 줄로
  합치지 않고, 각 조건을 독립 하위 항목으로 펼친다. §3.4 "한 줄이면 콜론 이어쓰기"는
  본 조건에서 무력화된다. 하위 중첩 1단계(§3.4)도 필요 시 초과 허용한다.
- **추상 라벨 + 경계 판단**: `CANDIDATE`·`PROBABLE`·`CONFIRMED` 같은 라벨만 나열하면
  경계 케이스에서 어디에 속하는지 판단 불가능. 각 라벨 아래에 1~2줄의 구체 판별 기준
  또는 한 줄 예시를 반드시 덧붙인다.
- **일반 규칙과 엣지 케이스의 공존**: 일반 규칙과 엣지 케이스를 한 문장으로 합치지
  않는다("보통은 X, 단 Y일 때는 Z" 금지). 일반 규칙 항목 아래 엣지 케이스를 별도
  하위 항목으로 분리한다.
- **판단 이중 구조(§3.6)의 근거가 비대칭일 때**: fail 조건과 success 유지 조건이 서로
  다른 이유로 그렇게 판정되는 경우, 각 조건 옆에 그 이유를 짧게 덧붙인다. 이유 없는
  라벨 나열은 모델이 경계에서 잘못된 쪽으로 기운다.
- **규칙 적용의 전제(context)가 필요할 때**: "이 규칙은 X일 때만 적용된다"는 전제를
  규칙 본문 안에 녹이지 않고, 규칙 앞 또는 옆에 명시한다.

**판단 기준 — 축약이 성공인가 실패인가**:

축약 후 "이 한 항목만 읽고 경계 케이스에서 올바른 판단이 가능한가?"를 자문한다.
답이 "아니오"면 그 축약은 실패다. 다음 체크를 통과해야 한다.

- 추상 라벨에 최소 1개의 구체 판별 기준이 붙어 있는가
- AND 관계의 조건이 시각적으로 분리되어 있는가
- 엣지 케이스와 일반 규칙이 같은 줄에 눌려 있지 않은가
- 판단의 이유가 결론 옆에 함께 있는가

**적용 범위**: 프롬프트 파일뿐 아니라 **본 스킬 문서 자체에도 적용된다**. 스킬의 규칙
설명이 과하게 축약되면 에이전트(=LLM)가 그 규칙을 잘못 적용하게 되어 스킬 전체가
의도대로 작동하지 않는다. 스킬을 수정할 때도 이 원칙으로 자기검증한다.

**§3.3·§3.4·§9와의 우선순위 재확인**:

- §3.3의 "카테고리당 5개 상한"은 **단순 나열 규칙**에만 해당한다. 각 규칙이 복수 조건
  또는 경계 판별 기준을 요구하면 5개를 넘더라도 본 원칙이 우선한다.
- §3.4의 "한 줄이면 콜론 이어쓰기"는 **단일 조건 규칙**에만 해당한다. 복수 조건이나
  엣지 케이스가 엮이면 본 원칙이 우선해 펼쳐 쓴다.
- §9의 "TASK 2줄 상한"은 **출력 형식 재강조**에만 해당한다. 판단 로직 자체를 TASK에
  재강조해야 하면 본 원칙이 우선하되, 그래도 4줄 상한은 유지한다.

### 3.11 자기 설명적 용어 원칙 (신조어·메타포 금지)

**본 원칙은 §3.10과 쌍을 이룬다. §3.10이 "복잡한 내용을 충분히 풀어 쓰라"는 원칙이라면,
본 원칙은 "용어 자체가 해석 비용을 만들지 말라"는 원칙이다.**

**무엇**: 프롬프트에 새 용어를 도입할 때는 그 용어 자체가 무엇을 지시하는지 자명해야
한다. 메타포·축약 라벨·프로젝트 내부 은유를 새로 만들어 쓰지 않는다.

**왜**: 디코더 LLM은 "축", "관점", "차원", "프레임", "벡터" 같은 추상 메타포를 처리할
때 "이 용어가 이 문맥에서 무엇을 가리키는가"를 매번 해석해야 한다. 인간 개발자는
수학·분석 분야에서 이런 메타포에 익숙하지만, 모델에게는 추가 해석 비용이다. 특히
MoE 모델은 메타포 해석이 라우팅 분기를 흔들어 판단을 불안정하게 만든다. 같은 내용을
동사형 명사("검색어 변경", "페이지 증가")로 쓰면 라벨 자체가 "무엇을 해야 하는지"를
직접 지시하므로 해석 비용이 0이 된다. 과거 프로젝트에서 "변형 축", "관점 변경" 같은
내부 메타포를 도입한 결과 동일 개념을 블록마다 다르게 부르는 파편화와 예시-규칙 간
용어 불일치가 발생한 적이 있다.

**어떻게 — 금지 패턴**:

- "~축", "~관점", "~차원", "~프레임", "~벡터", "~공간" 같은 수학·분석 메타포를 프로젝트
  내부 개념에 붙이지 않는다
  - "변형 축" (X) → "변경 방법" (O)
  - "관점 변경" (X) → "도구 변경" 또는 "검색어 변경" (O)
  - "탐색 차원" (X) → "탐색 방법" 또는 "탐색 대상" (O)

**어떻게 — 선호 패턴**:

- **동사형 명사**(동사 어근 + 명사)를 우선 사용한다. "~변경", "~증가", "~확장", "~선택",
  "~분류", "~재구성". 이런 형태는 라벨 자체가 행동을 지시한다
- **일반 한국어 어휘**로 구성한다. 한 단어만 읽고 의미를 알 수 없는 조합은 쓰지 않는다

**어떻게 — 새 용어 도입 시 의무 사항**:

- 만약 기존 어휘로 표현이 안 되는 새 개념이 정말 필요하다면, 그 용어를 도입한 첫 자리에
  반드시 1줄 정의 + 1개 구체 예시를 붙인다
- 한 프롬프트 안에서 같은 개념을 다른 이름으로 부르지 않는다. 용어는 한 번 정하면 모든
  블록에서 동일하게 쓴다(일관성 의무). 예: "변경 방법"과 "접근 방법"을 혼용 금지
- 기존 프롬프트를 수정할 때는 해당 용어의 모든 등장 위치(다른 블록·예시·TASK)를 grep으로
  찾아 함께 갱신한다. 파편화된 동의어가 남지 않도록 한다

**자기 검증 체크 — 새 용어를 쓰기 전 자문**:

- 이 용어는 일반 한국어 단어로 구성되어 있는가? (X: "변형 축", O: "변경 방법")
- 이 용어만 읽고 무엇을 지시하는지 바로 알 수 있는가?
- 같은 개념을 다른 이름으로 이미 부른 적 있는가?
- 이 용어가 동사형 명사인가, 아니면 추상 메타포인가?

답이 "아니오" 또는 "메타포"이면 해당 용어는 쓰지 않는다. 기존 일반 어휘로 풀어 쓴다.

**§3.10과의 관계**:

- §3.10 "추상 라벨 + 경계 판단" 항목은 **기존 상태 라벨**(CANDIDATE/PROBABLE/CONFIRMED
  같이 이미 확립된 도메인 라벨)에 구체 판별 기준을 붙이라는 원칙이다
- §3.11은 **새 용어를 만들 때** 메타포를 피하라는 원칙이다
- 두 원칙은 상호 보완: 불가피한 추상 라벨에는 §3.10(판별 기준 첨부), 새 용어에는 §3.11
  (메타포 금지·동사형 명사 우선)이 적용된다

**적용 범위**: 프롬프트 파일과 본 스킬 문서 모두에 적용된다. 스킬 자체에서 메타포를
쓰면 에이전트가 해당 용어를 프롬프트에 전파할 위험이 있다.

### 3.12 `[HARD_CONSTRAINTS]`와 `[RULES]`의 책임 분리

**무엇**: 두 블록은 "강도"의 차이가 아니라 **성격의 차이**다. `[HARD_CONSTRAINTS]`는
"위반 시 즉시 실패하는 형식 규약"만 담고, `[RULES]`는 "의미 판단 기준"만 담는다.
한 규칙이 양쪽에 중복되면 `[HARD_CONSTRAINTS]`의 "즉시 실패" 체감 강도가 희석된다.

**왜**: LLM 입장에서 두 블록이 같은 내용을 서로 다른 표현으로 반복하면, "어느 쪽이 더
강한 제약인가"를 해석하느라 판단 분기가 흔들린다. 특히 `[HARD_CONSTRAINTS]`에 의미
판단 규칙이 섞이면 "즉시 실패" 신호가 의미 규칙에도 전파되어, 모델이 보수적으로
판단을 유보(fail)하거나 반대로 의미 규칙을 형식 규약처럼 기계적으로 적용해
맥락에 맞지 않는 출력을 낸다.

**어떻게 — 판단 기준**:

이 규칙 위반을 **코드 레이어에서 정적으로 탐지 가능한가?**

- YES — 형식 규약이므로 `[HARD_CONSTRAINTS]`
  - JSON 파서·SQL 파서·정규식·스키마 검증 등으로 탐지 가능한 것
  - 예: "JSON 객체 하나만 출력", "SELECT 구문만", "스키마.테이블 형식", "enum 허용값",
    "빈값은 []/null", "큰따옴표만", "세미콜론 연쇄 금지"
- NO — 판단 기준이므로 `[RULES]`
  - 의미 해석·추론·도메인 판단이 필요한 것
  - 예: "명시 > 추론 > inferred_value 우선순위", "확정 불가 정보는 ambiguities로",
    "GROUP이 있으면 집계 함수 적용", "결과 SQL이 달라질 수준의 모호성만 기록"

**재사용 가능 여부**: 같은 규칙을 양쪽에 반복하지 않는다. 한 규칙은 한 블록에만
존재한다. 중복이 발견되면 기준에 따라 한쪽으로 이동시킨다.

**단순형 프롬프트**: `[HARD_CONSTRAINTS]`나 `[RULES]` 중 하나만 있는 프롬프트는 본 원칙
"해당 없음". 원칙은 두 블록이 공존할 때만 트리거된다.

## 4. 블록 배치 순서 원칙 (필수)

**왜 순서가 중요한가**: 디코더 LLM은 attention이 "맨 앞"과 "맨 뒤"에 쏠린다
(lost-in-the-middle + recency bias). 동일한 블록 집합이라도 순서를 바꾸면 모델이 무엇을
더 강하게 참고할지가 달라진다. 특히 가변 `[CONTEXT]`(플레이스홀더 치환)를 중간에 두면
매 호출마다 위치가 흔들려 규칙과의 상대 거리가 달라지는 숨은 품질 편차 원인이 된다.

### 4.1 순서 설계 4원칙

1. **불변 → 가변**: 매 호출 동일한 블록(`[ROLE]`·`[RULES]`·`[TOOLS]`·`[EXAMPLES]`·`[OUTPUT_CONTRACT]`)을 먼저, 런타임 치환 블록(`[CONTEXT]`)을 뒤에 배치. 캐시 친화적이고 규칙 해석 안정.
2. **lost-in-the-middle 방어**: 핵심 규칙은 **최상단** `[RULES]`·`[HARD_CONSTRAINTS]` 와 **최하단** `[TASK]` 재강조 양쪽에 배치.
3. **Recency bias 활용**: 가장 중요한 "출력 제약 + 현재 과제"는 **반드시 마지막** → `[TASK]`는 항상 최종 블록. Few-shot 마지막 예시는 "가장 대표적인 케이스".
4. **Few-shot ↔ OUTPUT_CONTRACT 상대 위치**: `[EXAMPLES]`는 `[OUTPUT_CONTRACT]` **앞**에 둔다. 예시 먼저 보고 contract를 해석해야 스키마가 구체화된다.

### 4.2 가변 CONTEXT 배치의 결정적 규칙

가변 `[CONTEXT]`(플레이스홀더 포함)는 **`[TASK]` 바로 직전**에 배치한다. 중간이 아니다.
recency bias가 "가장 최신 컨텍스트 → 즉시 과제 수행"으로 이어져야 한다.
`context_interpreter`의 긴 `{tool_results}` 내부 배치는 별도 규칙(§7.3) 참고.

### 4.3 유형별 권장 블록 순서

| 유형 | 권장 순서 |
|---|---|
| 단순형 | `[ROLE]` → `[RULES]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]` → `[TASK]` |
| 분석 판정형 (thinking OFF) | `[ROLE]` → `[RULES]` → `[HALLUCINATION_GUARD]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]` → `[TASK]` |
| 분석 판정형 (thinking ON, long context) | `[ROLE]` → `[RULES]` → `[HALLUCINATION_GUARD]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]`(§7.3) → `[TASK]`(핵심 규칙 재강조) |
| 분석 판정형 (thinking ON, 생성) | `[ROLE]` → `[RULES]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]` → `[TASK]`(reasoning_summary 재명시) |
| 계획 수립형 (도구 사용) | `[ROLE]` → `[RULES]` → `[TOOLS]` → `[HALLUCINATION_GUARD]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]` → `[TASK]`(reasoning_summary 재명시) |
| 계획 수립형 (복잡 생성) | `[ROLE]` → `[MISSION]` → `[HARD_CONSTRAINTS]` → `[HALLUCINATION_GUARD]` → `[RULES]` → `[EXAMPLES]` → `[OUTPUT_CONTRACT]` → `[CONTEXT]` → `[TASK]`(reasoning_summary + fail 우선 재명시) |

### 4.4 공통 규칙

- `[TASK]`는 언제나 맨 마지막. 예외 없음.
- 가변 `[CONTEXT]`는 언제나 `[TASK]` 바로 앞. 중간 금지.
- `[HALLUCINATION_GUARD]`는 `[RULES]`/`[HARD_CONSTRAINTS]` 직후. 뒤쪽(`[TASK]` 근처)에 두면 "하지 말 것" 토큰이 recency로 역priming.
- 여러 `[RULES]` 섹션이 있으면 가장 중요한 제약을 첫 번째 섹션에.

## 5. `[OUTPUT_CONTRACT]` 규칙과 JSON 3중 방어

### 5.1 작성 원칙

**무엇**: `[OUTPUT]` 대신 `[OUTPUT_CONTRACT]`. 태그 이름 자체가 "형식 위반 불허" 신호로 작동한다.

**왜**: 필드명 옆에 `description` 문자열을 같은 줄에 두면 Qwen3가 description을 필드 **값**으로 오인하여 스키마를 깨뜨리는 버그(vLLM #23404)가 있다.

**어떻게**: 필드 선언과 설명을 물리적으로 분리한다. `description=` 인라인 표기 금지.

**필드 선언 방식**:

```
"action": "replan" | "give_up"
"confidence": number (0.0~1.0)
"status": "CANDIDATE" | "PROBABLE" | "CONFIRMED" | "CONFLICTED"
```

**조건부 필드**: 선언 아래에 조건 명시.

```
"execution_plan": array
- action이 give_up이면 빈 배열([])로 출력
- action이 replan이면 1~4개 스텝 포함

"new_hypothesis": object | null
- 이전 가설과 다른 접근일 때만 포함
- 없으면 null로 출력 (필드 생략 금지)
```

**필드 설명 위치**: 필드명 옆 `description=` 인라인 표기 금지. 설명은 별도 `### 필드 설명` 섹션으로 분리.

### 5.1.3 비확정 표식(unresolved marker) 명시 원칙

**무엇**: 스키마에 "확정 불가 플레이스홀더"(`UNKNOWN`, `null`, `[]`, `"N/A"` 등)가 존재한다면,
해당 값이 **확정값이 아닌 비확정 표식**임을 프롬프트에 명시적으로 선언한다.

**왜**: 비확정 표식을 도입하지 않고 "확정 불가 정보는 슬롯에 넣지 말 것"만 규정하면, LLM이
두 가지 실패 패턴 중 하나에 빠진다.

- 보수적 실패: 해당 슬롯을 아예 누락해 스키마가 깨진다
- 반대 방향 실패: 플레이스홀더가 허용값이라는 것만 알고 반복적으로 UNKNOWN을 남발한다

또한 HARD_CONSTRAINTS에 "허용값만 사용"을 둔 경우, 슬롯 규칙의 "확정 불가면 비워라"와
표면적으로 충돌하는 것처럼 보여 LLM이 한쪽을 위반 회피용으로 기계 적용할 수 있다.

**어떻게**: HARD_CONSTRAINTS 또는 RULES 중 관련 규칙 근처에 한 줄을 추가한다.

```
- UNKNOWN, null, 빈 배열은 "비확정 표식"이므로 슬롯 본체에 사용 가능하다
  (HARD_CONSTRAINTS 위반이 아니다)
- 비확정 표식은 "확정할 수 없음"을 표현하는 수단이지, 판단을 미루는 도피처가 아니다
```

**적용 조건** — 다음을 **모두** 만족할 때만 필요하다.

- 출력 스키마에 비확정 플레이스홀더(`UNKNOWN`, `null`, `[]` 등)가 실제로 정의되어 있다
- 동일 스키마에 "허용값 목록"을 강제하는 HARD_CONSTRAINTS가 존재한다
- 슬롯 본체에 비확정 표식이 들어갈 수 있는 설계다(ambiguities 같은 메타 필드 한정이 아니다)

세 조건 중 하나라도 빠지면 본 원칙은 **해당 없음**. 불필요하게 추가하지 않는다.

### 5.2 `reasoning_summary` 필드 (thinking ON 노드 — 단일 출력 노드 한정)

**무엇**: thinking ON 노드 중 **단일 최종 산출물을 생성하는 3개 노드**(`recovery_agent`,
`sql_generator`, `analyzer`)의 `[OUTPUT_CONTRACT]`에 `reasoning_summary: string` 필드 추가.

**예외 — `context_interpreter`는 면제**:

- `context_interpreter`의 출력은 단일 산출물이 아니라 **스텝별 해석 `interpretations` 배열**이다.
- 각 interpretation이 이미 `insight`와 `knowledge_updates[].evidence` 필드에 판단 근거를
  **스텝 단위로 분산 기록**하고 있어, 별도의 `reasoning_summary`를 두면 의미 중복 + 토큰 낭비 +
  think-answer 교차 검증 지점이 오히려 모호해진다.
- 코드 레이어 교차 검증은 각 interpretation의 `evidence`가 해당 스텝의 도구 결과에 실제로
  등장하는지 확인하는 방식으로 수행한다(단일 최상위 요약 필드가 아니라 스텝별 evidence 배열 대상).
- 따라서 본 노드는 §7.2 방어 4중 구조에서 "1번(reasoning_summary)"을 **"각 interpretation의
  insight + evidence 필드"**로 대체한다. 나머지 2·3·4번 방어는 그대로 유지.

**왜**: thinking ON 모델은 `<think>` 블록 결론과 최종 answer가 어긋나는 think-answer mismatch(arXiv:2505.23646)에 노출된다. think 내부는 코드로 직접 검증하기 어렵다. 모델이 "어떤 근거로 이 답을 냈는지"를 JSON 내부 필드로 요약하게 해서 코드 레이어 교차 검증을 가능하게 한다. 사용자용 `explanation`과 목적이 다른 검증용 메타데이터.

**스키마**:

```
"reasoning_summary": string
- 최종 출력(sql/judgment/plan/insight)을 도출한 핵심 근거를 1~3줄 요약
- "어떤 테이블/컬럼/도구 결과를 사용했는가" + "어떤 판단을 내렸는가"
- explanation(사용자용 자연어)과 목적이 다름: 시스템 검증용
```

**sql_generator 적용 예시**:

```json
{
  "status": "success",
  "sql": "SELECT ... FROM ADWOWN.TB_ADW_LNB301M WHERE LN_DT >= ...",
  "reasoning_summary": "여신기본마스터(TB_ADW_LNB301M)의 LN_DT 기준 당월 필터, COUNT/SUM 집계. 참고 SQL EX_042의 DATE_TRUNC 패턴 차용.",
  "failure_reasons": [],
  "assumptions": ["'이번 달 신규'의 해석 → 대출실행일자(LN_DT) 기준 당월"],
  "explanation": "이번 달 여신기본마스터에서 신규 실행 건수와 금액 합계를 집계"
}
```

**코드 레이어 검증 로직** (노드 코드에서 구현):

1. `reasoning_summary`에 언급된 테이블/컬럼이 `sql`에 실제 등장하는지 확인
2. 불일치 시 mismatch 로그 + recovery_agent 라우팅
3. `reasoning_summary`가 비었으면 정합성 검증 불가 → fail

### 5.3 JSON 안정성 3중 방어

**무엇**: Qwen3 계열이 JSON 출력에서 자주 실패하는 3대 패턴(```json 펜스, trailing 설명, description 오인)을 차단.

**왜 3중인가**: 각 계층마다 커버하는 실패 모드가 다르고, 어느 한 계층만으로는 빠져나가는 케이스가 존재한다. 하나가 뚫려도 다음 계층에서 잡는 구조.

**어떻게**: 계층 1은 프롬프트에 필수 반영, 계층 2는 `client.py`에서 설정(프롬프트에 쓰지 않음), 계층 3은 노드 응답 처리 코드에 구현. 세 계층 책임을 섞지 않는다.

**계층 1 — 프롬프트 레이어** (모든 JSON 출력 노드 필수)

`[OUTPUT_CONTRACT]` 말미 또는 별도 `[FORMAT_LOCK]` 블록에 정확히 포함:

```
출력은 JSON 객체 하나로만 구성한다.
- 출력의 첫 문자는 반드시 { 이어야 한다.
- 마크다운 코드 펜스(```json, ```) 를 포함하지 않는다.
- JSON 이전이나 이후에 어떤 설명 텍스트도 쓰지 않는다.
- 모든 문자열은 큰따옴표만 사용한다.
```

thinking ON 노드에서는 `<think>` 블록 **바깥** 첫 지시로 "최종 출력은 raw JSON만"을
`[TASK]`에 재명시한다.

**계층 2 — 샘플링 레이어** (인프라 설정, 프롬프트 기재 금지)

- no_think: `temperature=0.7`, `presence_penalty=1.5`
- vLLM ≥ 0.9.1: `guided_json` 권장
- vLLM < 0.9.1: `guided_json` 사용 금지(#18819), 프롬프트 + 코드 레이어로만 방어

**계층 3 — 코드 레이어** (`src/utils/llm/` 또는 노드 응답 처리)

```python
import re, json

def extract_json(raw: str) -> dict:
    cleaned = re.sub(r'```json?\s*|\s*```', '', raw).strip()
    start = cleaned.find('{')
    if start > 0:
        cleaned = cleaned[start:]
    end = cleaned.rfind('}')
    if end != -1:
        cleaned = cleaned[:end + 1]
    return json.loads(cleaned)
```

재시도 최대 2회, 3회 실패 시 `recovery_agent` 라우팅.

### 5.4 출력 스키마를 통한 사고 scaffolding (§0 성능 우선 원칙 적용 사례)

**무엇**: thinking ON 노드 중 "표면 관찰 → 재해석" 또는 "증상 → 원인" 같은 **사고 단계
분리가 출력 품질의 핵심**인 노드의 경우, OUTPUT_CONTRACT에 두 단계를 **분리된 필드**로
두어 모델에게 구조적으로 사고 순서를 강제한다.

**§5.2와의 차이**: §5.2의 `reasoning_summary`는 "사후 검증용 메타데이터"다. 모델이 출력을
만든 **후**에 근거를 요약하는 용도. 본 §5.4의 scaffolding은 출력을 만드는 **과정 자체**를
스키마로 분리하는 것으로, 목적과 작동 위치가 다르다. 두 패턴은 병존 가능하며, 깊이 문제가
있는 노드는 양쪽 다 적용한다.

**왜 RULES 지시보다 강력한가**: "깊이 있게 분석하라" 같은 텍스트 지시는 모델이 무시할 수
있다. 그러나 출력 스키마가 `initial_reading`과 `insights` 두 필드로 나뉘어 있고 **"insights는
initial_reading과 달라야 한다"**가 규칙이면, 모델은 구조적으로 두 단계를 분리해야 한다.
텍스트 지시(RULES)보다 스키마 제약(OUTPUT_CONTRACT)이 훨씬 강한 규제력을 가진다.

### 적용 조건

다음을 모두 충족할 때 본 패턴을 적용한다.

- **thinking ON 노드**이다 (thinking OFF에서는 사고 scaffolding 자체가 의미 없음)
- 노드의 주된 실패 유형이 **"깊이 부족"**이다. 즉 표면 관찰 수준에서 출력이 멈추거나,
  증상을 원인으로 오인하거나, 첫 해석에서 더 나아가지 못하는 패턴
- 기존 `reasoning_summary`(§5.2)만으로는 이 실패를 잡을 수 없다. reasoning_summary는
  사후 요약이지 사고 순서 강제가 아니므로, 모델이 얕은 사고를 "요약만 그럴싸하게" 포장하는
  것을 막지 못한다
- 해당 노드의 입력이 **scatter 구조가 아니다**. step별 tool 결과가 있는 노드는 step 단위
  scatter가 이미 scaffolding 역할을 하므로 (예: `context_interpreter`의 step별
  `insight`+`evidence`), 별도 전체 단위 분리는 중복

### 적용 예

- **`analyzer`**: `initial_reading` (표면 수치 관찰) / `insights` (재해석) 분리.
  "insights의 각 항목은 initial_reading에 이미 적힌 관찰과 같은 내용이면 안 된다"가 하드 제약.
- **`recovery_agent`**: `surface_symptom` (마지막 시도의 표면 실패 이유) /
  `root_cause_diagnosis` (근본 원인 진단) 분리. "next_action은 surface_symptom만으로
  결정할 수 없고 root_cause_diagnosis에서 도출되어야 한다"가 하드 제약.

### 적용하지 않는 경우

- `context_interpreter`: 이미 interpretations 배열의 각 원소가 `insight`(재해석) +
  `knowledge_updates[].evidence`(표면 인용)로 **step 단위 scatter 분리**를 갖고 있음.
  전체 단위 scaffolding 추가는 중복
- `sql_generator`: SQL 생성은 structural/symbolic 태스크로 "표면 vs 심층" gap 자체가
  작음. 기존 `assumptions`·`explanation` 필드가 부분적으로 같은 역할을 수행하므로 새
  필드 추가는 중복 위험

### 보완 규칙 (필수)

본 패턴을 적용할 때 아래 3가지 규칙을 함께 박지 않으면 효과가 반감된다.

- **비동일성 제약**: "후속 필드는 선행 필드의 내용을 반복하면 안 된다"를 RULES 또는
  HARD_CONSTRAINTS에 positive form으로 명시. 예: "insights의 각 항목은 initial_reading에
  없는 재해석만 담는다"
- **빈 값 허용 명시**: "선행 필드만 채우고 후속 필드를 빈 배열/빈 문자열로 두는 것은
  허용한다 (억지 해석 금지)". 이 명시가 없으면 모델이 가짜 심층 해석을 만들어내는 환각이
  증가
- **예시에서 변환 노출**: few-shot 예시의 reasoning_summary에 "선행 필드의 표면 관찰에서
  후속 필드의 재해석으로 어떻게 넘어갔는가"를 1~2줄 기록. 모델이 "사고의 이동" 패턴을
  학습하도록 함

### 안티 패턴 블록(선택)

깊이 부족이 만성적인 노드는 `[ANTI_PATTERN]` 블록을 추가하여 **"얕은 출력의 구체 예시와
왜 얕은지"**를 명시할 수 있다. 구조는 §6.2의 HALLUCINATION_GUARD 포맷을 따르되, "환각
방지"가 아닌 "얕음 방지"를 목적으로 함을 제목에 명시. 안티 패턴은 few-shot positive 예시
3개보다 "얕음 회피"에 대한 신호가 더 강할 때가 많다.

## 6. `[HALLUCINATION_GUARD]` 블록

### 6.1 목적

모델이 존재하지 않는 테이블/컬럼/코드값을 생성하는 것을 방지. 위반 예시와 "올바른 대응"을
쌍으로 제시하여 negative 예시의 priming 부작용을 억제한다.

### 6.2 블록 구조

각 위반은 **입력 상황 / 잘못된 출력 / 올바른 출력** 3줄을 한 단위로 묶어 제시한다.
"위반 예시 전체"와 "올바른 대응 전체"를 두 개의 병렬 그룹으로 분리하지 않는다 —
독자가 위-아래로 매칭하며 점프해 읽는 구조가 되어 가독성이 크게 떨어진다.

```
[HALLUCINATION_GUARD]

원칙:
- [INPUT_CONTEXT]에 명시된 테이블·컬럼·코드값만 사용한다
- 샘플 데이터 목록이 제공되면 그 값만 WHERE 조건에 사용한다
- 불확실하면 fail로 출력한다

위반 예시 (이 형태로 출력하지 않는다):

### 위반 1 — 없는 테이블 사용
- 입력 상황: confirmed_terms에 ADWOWN.TB_ADW_LNB301M만 존재
- 잘못된 출력: FROM TB_ADW_LNB302M 사용
- 올바른 출력: fail, failure_reasons "재검색 필요: 해당 테이블 미확인"

### 위반 2 — 없는 컬럼 사용
- 입력 상황: 컬럼 목록에 LN_NO, EDPS_CSN, LN_BAL_AMT만 존재
- 잘못된 출력: SELECT OVERDUE_RATE ...
- 올바른 출력: fail, failure_reasons "컬럼 미확인 — {컬럼의 비즈니스 의미}"

### 위반 3 — 존재하지 않는 코드값 사용
- 입력 상황: 코드값 "01=정상, 02=연체"만 확인됨
- 잘못된 출력: WHERE LN_STCD='ACTIVE'
- 올바른 출력: fail, failure_reasons "코드값 매핑 미확인"

### 위반 4 — 스키마 누락
- 입력 상황: 스키마가 ADWOWN로 확인됨
- 잘못된 출력: FROM TB_ADW_DEP201P
- 올바른 출력: FROM ADWOWN.TB_ADW_DEP201P
```

### 6.3 작성 원칙

- **위반 예시는 카테고리당 최대 5개**. 초과 시 카테고리 분리.
- **위반과 대응은 같은 단위로 묶는다**: 각 위반의 `입력 상황 / 잘못된 출력 / 올바른 출력`을 하나의 `### 위반 N` 블록 안에 나란히 둔다. "위반 전체"와 "대응 전체"를 분리된 두 섹션으로 나열하지 않는다.
- **위반 제목에 라벨**: `### 위반 N — 짧은 유형 라벨` 형태로 본질을 한 구절로 요약(예: "없는 테이블 사용", "코드값 변조", "스키마 누락"). 독자가 목차만 봐도 위반 유형을 파악할 수 있어야 한다.
- **도메인 특화**: 실제 스키마명(`ADWOWN.TB_ADW_LNB301M` 등) 사용. 일반 "Table A" 금지.
- **배치**: `[HARD_CONSTRAINTS]` 직후 또는 `[RULES]` 직후. 뒤쪽(`[TASK]` 근처) 배치 금지.

### 6.4 가드레일 적용 범위 (IN / OUT)

**왜 범위를 제한하는가**: 도메인 지식 자체를 프롬프트에 박아넣으면 토큰 폭발 + MoE 라우팅 드롭 + 지식 업데이트 시 프롬프트 전면 개편이라는 3중 비용이 발생한다. 이런 지식은 이미 RAG(Qdrant 업무매뉴얼·상품설명서) 또는 메타 조회(MongoDB 코드/테이블 메타)라는 **단일 진실원**을 갖고 있다. 가드레일의 본분은 "모델이 도메인 지식을 외우게 만드는 것"이 아니라 "조회 결과를 정확히 해석하고 환각을 억제하는 것".

**IN — 포함할 항목**:

- 유사 테이블/컬럼 혼동 방지 (LNB301M vs LNB302M)
- 금융 용어 오역 방지 (여신 ≠ 대출 ≠ 여신금)
- 코드값 함정 (메타 조회 결과 값만 사용, 영문 상수 금지)
- 불완전 메타 대응 (컬럼 미확인 시 fail 선언)
- 스키마 누락 방지 (`ADWOWN.` prefix)

**OUT — 넣지 않을 항목** (→ 단일 진실원에서 런타임 주입):

- 금융 계수산출식(연체율·BIS·LCR 등) → RAG 업무매뉴얼
- 전체 테이블 카탈로그 → `context_retriever`
- 업무 프로세스 설명 → RAG 업무매뉴얼
- 상품 설명 일반 지식 → RAG 상품설명서
- 모든 코드값 매핑 나열 → `lookup_code_meta` 도구 결과

**예시 커버리지 판단 기준**: "도메인 지식 나열 수"가 아니라 **"실패 유형 축에서 각각 1개 이상 커버했는가"**. 같은 실패 유형의 예시를 여러 개 나열하는 것은 확장이 아니라 중복.

## 7. thinking ON 노드를 위한 추가 방어

### 7.1 think-answer mismatch 배경

thinking ON 모델은 `<think>` 블록의 결론과 최종 answer가 다를 수 있다. NL-to-SQL에서는
"think에서 올바른 SQL을 도출했으나 answer에 이전 버전 출력"의 형태로 나타나 검출이 어렵다.

### 7.2 방어 장치 4중 구조

**무엇**: thinking ON 노드 4개에 대해 프롬프트 레이어 2중 + 코드 레이어 2중 방어를 동시에 건다.

**왜 4중인가**: think-answer mismatch는 확률적 현상이라 단일 방어로는 누락된다. "생성 시점(프롬프트)"과 "검증 시점(코드)"을 각각 이중화하여 어느 한 쪽이 뚫려도 다른 쪽에서 잡도록 설계.

**어떻게**: 프롬프트 작성 시 1·2를 빠짐없이 반영하고, 노드 코드에 3·4의 검증 로직을 구현한다. 하나라도 빠지면 방어 구조가 무너진다.

1. **`reasoning_summary` 필드 의무화** (§5.2) — think 결론 요약을 JSON 내부에 가둠
2. **`<think>` 바깥 첫 지시로 출력 형식 재명시** — `[TASK]`에 "최종 출력은 reasoning_summary 포함 JSON 객체 하나"
3. **코드 레이어 교차 검증** — `reasoning_summary` 언급 테이블/컬럼/지표가 실제 출력에 등장하는지 검사
4. **하방 검증자 노드 강화** — `sql_validator`(OFF)는 `sql_generator` 출력 재검증. `analyzer`는 코드에서 `reasoning_summary` vs `insight` 텍스트 매칭.

### 7.3 context_interpreter long context 배치

가장 긴 컨텍스트를 받는 노드. lost-in-the-middle 원칙에 따라 내부를 다음과 같이 배치한다.

```
[ROLE]
[RULES]         ← 최상단, 핵심 판단 기준

[CONTEXT]
## 원 질의        ← 가장 짧고 중요
## 미해결 항목     ← 짧고 판단 분기의 기준
## 도구 실행 결과  ← 가장 길고 중간 위치 불가피, 관련도 상위 N개 트리밍
## 이전 지식 상태  ← 갱신 대상

[EXAMPLES]
[OUTPUT_CONTRACT]
[TASK]          ← 말미, 핵심 규칙 1~2줄 재강조
```

- 가장 중요한 규칙은 `[RULES]` 최상단 + `[TASK]` 말미 양쪽에
- 중간 도구 결과는 `context_retriever`가 상위 N개로 트리밍한 뒤 전달

## 8. Few-shot 설계 규칙

### 8.1 노드별 개수 정책

| 노드 | 권장 | 상한 | 근거 |
|---|---|---|---|
| `intent_classifier` | 11 | 12 | 분류 태스크, 경계 학습이 주 목적, template trap 거의 없음 |
| `sql_generator` | 6 | 6 | 각 예시가 서로 다른 구조적 패턴 커버 |
| `query_normalizer phase1` | 5 | 5 | 슬롯 채움 edge case |
| `recovery_agent` | 5 | 5 | 실패 유형별 재계획 |
| `query_normalizer phase2` | 3 | 4 | R1~R12 중 빈발 위반만 |
| `sql_validator` | 3 | 4 | 체크리스트 경계 |
| `context_interpreter` | 3 | 4 | 예시가 길어 template trap ↑ |
| `analyzer` | 3 | 3 | 인사이트 도출은 예시 의존도 낮음 |
| `analyzer_viz_judgment` | 2~3 | 3 | 조건 매칭 |
| `analyzer_viz_svg` | 2 | 3 | 과다 시 구조 고착화 |

**원칙**:

- 분류 태스크는 7+ 허용. 독립 클래스 레이블을 학습한다.
- 생성 태스크는 5~6 상한. 각 예시가 서로 다른 구조적 패턴을 커버해야 함.
- 기타 태스크는 3 기본, 5 초과 금지.
- 7+는 **intent_classifier 단 하나만 허용**.

### 8.2 Few-shot 커버리지 매트릭스 (예시 선택 방법론)

**무엇**: 빠듯한 예시 예산 안에서 무엇을 넣을지 결정하기 위해 **2차원 매트릭스**를
먼저 그리고, 각 칸을 덮는 최소 집합을 고른다.

**왜**: "가장 흔한 케이스 + 가장 헷갈리는 케이스" 같은 직관적 선택은 커버리지 구멍이
생긴다. 매트릭스를 그리면 중복이 가시화되고, 골든셋 회귀 시 "어느 칸이 비었으니 교체"
의사결정이 가능해진다.

**어떻게**:

1. **축 선정**: 한 축은 "케이스 유형(성공/fail/edge)", 다른 축은 "구조적 패턴(집계/조인/분기)". 노드별 실패 유형 기준.
2. **각 칸에 케이스 배치**: 노드 단위 회귀 테스트 결과 기반으로 빈도 높은 칸 우선.
3. **최소 커버 집합**: 3~6개로 가장 많은 칸을 덮도록 선택. 한 예시가 2칸을 동시 커버하면 효율적.
4. **중복 제거**: 같은 칸에 속하는 예시는 절대 둘 이상 넣지 않는다. 새 예시 추가 시 "어느 칸이 비어 있는가"부터 확인.
5. **갱신**: 골든셋에서 회귀 실패 패턴이 반복되면 빠진 칸을 식별하고, 기존 예시 중 중복도가 가장 높은 하나를 교체.

**sql_generator 매트릭스 (v3의 6개 예시 매핑)**:

| 구조 ↓ / 결과 → | 성공 (SQL 생성) | 성공적 fail (fail 선언) |
|---|---|---|
| 단순 집계 + 용어 해석 | EX1 | - |
| 복수 해석 + JOIN | EX2 | - |
| 다중 JOIN + 코드값 명칭 | EX6 | - |
| 산출식 불명 | - | EX3 |
| 코드값·텍스트값 부족 | - | EX4 |
| 실제 값 목록 잘림 | - | EX5 |

**노드별 필수 커버리지 축**:

| 노드 | 축 1 | 축 2 |
|---|---|---|
| `intent_classifier` | 의도 레이블 전수 | 경계(애매한 의도) |
| `sql_generator` | 성공 vs 성공적 fail | 환각 트리거(코드값·산출식·테이블·컬럼) |
| `query_normalizer_phase1` | 슬롯 유형 | 암묵 vs 명시 표현 |
| `query_normalizer_phase2` | 교차검증 규칙 | 위반 유형 |
| `recovery_agent` | 실패 유형 | 재계획 전략 |
| `sql_validator` | 검증 규칙 카테고리 | pass vs fail 경계 |
| `context_interpreter` | 도구 유형 | 지식 갱신 결과 |
| `analyzer` | 인사이트 유형 | 데이터 충분성 |
| `analyzer_viz_judgment` | 시각화 적합성 | 데이터 유형 |
| `analyzer_viz_svg` | 차트 유형 | 데이터 스케일 |

**새 예시 추가/교체 전 반드시 이 매트릭스를 먼저 그려야 한다.** 매트릭스 없이 "좋아
보이는 예시"를 추가하면 거의 항상 중복이 발생한다.

### 8.3 예시 내부 구조

```
### 예시 N: 상황 제목 (케이스 유형)
상황: 한 줄 요약
- 핵심 상태 정보만 나열

{JSON 출력 예시}
```

### 8.4 배치 순서 — Recency Bias 활용

**왜**: 디코더 LLM은 recency bias 때문에 동일한 예시 세트라도 배치 순서만 바꾸면 출력 분포가 달라진다. 특히 Few-shot 블록의 마지막 예시가 바로 뒤따라오는 [TASK]에 가장 강한 템플릿 영향을 준다. 이를 "활용할 도구"로 취급.

**어떻게**:

- **가장 유사/대표적 예시를 마지막에 배치**
- 정적 프롬프트: "가장 복잡하고 실전적인 패턴"을 마지막에
- 동적 retrieval: retrieve된 케이스를 맨 마지막 슬롯 고정
- 테스트 시 순서만 바꿔 품질 차이 확인을 루틴 절차로

### 8.5 예시 JSON 품질 기준

**계획 수립형**:

- `analysis`: 실패 원인을 구체적으로. "코드값 부족" → "LN_STCD 매핑 없음 — WHERE 조건에 대출상태 필터 필요"
- `lessons_learned`: 이 케이스에서만 배울 수 있는 교훈. 일반론 금지
- `execution_plan`: 실제 실행 가능한 도구 조합만
- `depends_on`: 선행 필요 시 스텝 번호, 독립이면 null

**분석 판정형**:

- `insight`: 관찰 내용을 한 문장, 판단 포함
- `knowledge_updates`: key는 `unresolved_items`의 key 그대로
- `confidence`: 조건-결과 매핑 기준에 맞는 값
- `reason`: 판정 사유 구체적으로 (SELECTED/REJECTED 근거)
- 관찰 도구 스텝 예시에는 `explored_*` 배열 포함하지 않음

### 8.6 Negative Example 처리

**원칙**: Few-shot 내부에는 **성공 예시만** 포함. 실패/위반 예시는 `[HALLUCINATION_GUARD]`로 분리.

**왜**: Few-shot은 인간에게는 "good vs bad 대조 학습"이 효과적이지만 디코더 LLM에게는 그렇지 않다. 모델은 few-shot 영역의 토큰 패턴을 "따라 쓸 템플릿"으로 해석하기 때문에, "이렇게 틀리면 안 된다"라고 써둔 예시조차 그 토큰 분포를 모방할 확률이 높아진다.

**어떻게**:

- "성공한 출력" 또는 "성공적으로 fail을 선언한 출력"만 few-shot에 둔다.
- 후자는 sql_generator의 `status: "fail"` 출력처럼 "실패 상황에서 올바르게 fail을 선언한 예시"로, **success 카테고리의 일종**(v2의 EX_4, EX_5, EX_6 참고).
- "SQL에 존재하지 않는 컬럼을 쓴 잘못된 예시" 같은 것은 Few-shot에 절대 넣지 않고 `[HALLUCINATION_GUARD]`로 옮긴다.
- 예시 검토 시 "이 예시의 토큰 패턴을 모델이 그대로 따라 써도 괜찮은가?"를 자문하여 필터링.

## 9. User 말미 재강조 패턴

### 9.1 원칙

**무엇**: system 블록 상단에서 선언한 핵심 제약 1~2개를 user 메시지 말미 또는 `[TASK]` 블록에 한 번 더 짧게 반복.

**왜**: 긴 프롬프트에서는 앞쪽 제약이 lost-in-the-middle로 attention이 약해진다. 말미 재강조는 "가장 마지막에 본 지시를 따른다"는 recency bias를 활용해 보상한다.

**어떻게**: 재강조는 **정말 중요한 1~2개 제약에만** 한정. 모든 규칙을 재반복하면 토큰 낭비 + "앞의 지시와 뒤의 지시가 서로 다르지 않나?" 혼동 유발.

### 9.2 기본값

```
[TASK]
- 위의 입력을 근거로 {목표 작업}을 수행하라.
- 출력은 [OUTPUT_CONTRACT]의 JSON 객체 하나만. 마크다운 코드 펜스·설명 텍스트 금지.
```

**2줄 상한**. 이 이상은 토큰 낭비 + 과잉 반복 역효과.

### 9.3 고위험 노드 추가 재강조

`sql_generator`, `context_interpreter`, `analyzer`, `recovery_agent` 는 1~2줄 추가 허용
(총 3~4줄 상한):

```
[TASK]
- [INPUT_CONTEXT]의 확인된 테이블·컬럼·코드값만 사용하여 {작업} 수행.
- 정확성을 보장할 수 없으면 추측하지 말고 fail로 출력.
- 출력은 [OUTPUT_CONTRACT]의 JSON 객체 하나만. reasoning_summary 필드 필수.
```

### 9.4 재강조 금지 내용

다음은 user 말미에 반복하지 않는다:

- 금지 패턴 리스트 (이미 [RULES]에 있음)
- 전체 규칙 나열
- few-shot 패턴 설명
- 도메인 용어 설명

user 말미는 **출력 형식 + 최상위 제약 1~2개만**. system의 "판단 기준"을 user 말미에 또
쓰면 모델이 두 버전을 대조하며 혼동한다.

## 10. `[CONTEXT]` 변수 주입 규칙

### 10.1 플레이스홀더 의미 명시

형식은 코드 치환이므로 재정의 불필요. 대신 **무엇이고 어떻게 활용할지** 의미를 명시.

```
## 도구 실행 결과

{tool_results}

위는 지금까지의 모든 도구 실행 결과입니다.
- 이미 실행한 검색을 반복하지 마세요.
- 결과가 부족했다면 page=N으로 다음 페이지를 조회하세요.
```

단순 스칼라(`{query}`, `{today}`)는 별도 설명 불필요.

### 10.2 JSON을 입력으로 주입하지 않는다

JSON은 출력 전용. 입력은 `(kN)` 레이블 또는 `### [Step N]` 블록.

| 데이터 성격 | 권장 형식 |
|---|---|
| 단일 스칼라 값 | 인라인 자연어 |
| 상태+근거가 있는 항목 | `(kN)` 레이블 형식 |
| 실패/오류 기록 | `- [TYPE] 설명 \n  교훈: ...` |
| 복수 반복 블록 | `### [Step N]` + `---` 구분자 |

### 10.3 플레이스홀더 순서 원칙

```
원 질의 → 확인된 것 → 미확인된 것 → 도구 결과 → 이력 → 요약
```

### 10.4 선택지 설명 분리

변수가 여러 경우의 수일 때, 선택지 설명을 플레이스홀더와 같은 블록에 두지 않는다.
`[RULES]`에 별도 기술.

잘못된 방식:

```
[CONTEXT]
진입 경로: {entry_source}
  - readiness_gate: 초기 탐색 불충분
  - sql_validator: SQL 검증 실패
```

올바른 방식:

```
[CONTEXT]
진입 경로: {entry_source}

[RULES]
## 진입 경로 해석
### readiness_gate
초기 탐색이 불충분하여 추가 탐색이 필요하다.
### sql_validator
SQL 검증이 실패하여 원인 분석과 재생성이 필요하다.
```

에이전트 모듈 전용 추가 규칙(`[ROLE]` 3요소, 교차 참조, 도구 타입별 분기, 엔티티별 판정,
`[TOOLS]` 명세)은 `docs/agent-guides/prompt-rules.md` 참고.

## 11. 모듈 간 데이터 전달 규칙

에이전트 루프에서 한 모듈의 출력이 다음 모듈의 입력이 된다. 이 모듈의
`[OUTPUT_CONTRACT]` 형식과 다음 모듈 플레이스홀더 형식이 **정확히 동일**해야 한다.

```
이 모듈 [OUTPUT_CONTRACT]:
  "dead_ends": [{"type": "TERM_UNRESOLVABLE", "lesson": "..."}]

다음 모듈 플레이스홀더 형식 명시:
  {dead_ends_summary} 는 아래 형식으로 제공된다:
  - [TYPE] 설명
    교훈: ...
```

형식 불일치 시 다음 모듈이 잘못 파싱한다. 프롬프트 수정 시 업스트림/다운스트림 양쪽을
동시에 점검한다.

## 12. 사고 과정 강제 패턴 (thinking OFF 전용)

모델이 특정 순서로 판단해야 하는 경우 STEP 번호로 강제한다.

```
## 사고 과정

STEP 1: 사용자가 원하는 데이터가 무엇인지 파악
STEP 2: 확인된 지식 항목에서 테이블/컬럼을 찾음
STEP 3: 참고 SQL이 있으면 조인 구조·집계 방식을 참고
STEP 4: 충분성 판단 — STEP 2~3에서 모두 확인되었는가?
        하나라도 빠지면 즉시 fail을 출력한다
```

**주의**: thinking ON 노드에서는 STEP 강제가 `<think>` 자유 추론과 충돌한다.
thinking ON 노드는 `[RULES]`에 판단 기준만 기술하고 순서는 모델 자율.
**STEP 강제는 thinking OFF 노드에서만 사용.**

### 12.1 판별 트리의 공통 예외 배치

**무엇**: STEP 내부에서 Q1, Q2, Q3... 같은 순차 판별 질문을 나열하고, 그 질문 전체에
동일하게 적용되는 "공통 예외"가 있다면, 예외 블록은 **반드시 Q1보다 앞**에 놓는다.

**왜**: 디코더 LLM은 프롬프트를 선형으로 읽는다. Q1~QN을 먼저 통과한 뒤 마지막에
"공통 예외: 앞의 Q들을 평가할 때 이 경우는 NO로 간주한다"라고 적으면, 모델은 이미
Q1~QN을 평가해 primary를 확정한 상태에서 예외를 만난다. 이 시점에는 이전 판정을
역행해 재평가하지 않고, 다음 입력에서도 예외가 제때 적용되지 않는다. 공통 예외는
각 Q를 평가하는 시점에 활성화되어야 하므로, 평가 흐름의 **상류**에 있어야 한다.

**어떻게**:

```
STEP 1: 후보 감지 및 primary 결정

  공통 예외 (각 Q 평가 시 항상 적용):
    시그널 키워드가 존재하더라도, 질의에서 그 단어가 "행위/목적"이 아니라
    "데이터 항목명", "수식어", "엔티티명"으로 쓰인 경우 해당 Q는 NO로 판정한다.
    예: "변화량 TOP 3" → "변화"는 데이터 항목명 → Q2=NO, Q3=YES (RANK)

  Q1. ...
  Q2. ...
  ...
```

**적용 조건** — 다음을 모두 만족할 때만 필요하다.

- STEP 내부에 Q1~QN 같은 순차 판별 질문이 나열된다
- 그 중 일부 또는 전체에 동일하게 적용되는 예외가 존재한다
- 예외가 "판별 결과 이후의 후처리"가 아니라 "각 Q 평가 조건 자체"에 해당한다

단일 Q만 있거나, 예외가 특정 Q 하나에만 해당한다면 본 원칙은 해당 없음.
예외는 해당 Q의 설명에 직접 붙인다.

## 13. 조건 분기 섹션

런타임 변수 값에 따라 적용 규칙이 달라질 때 사용.

```
## dialect별 규칙

### Sybase IQ (dialect = tsql)
- 행 제한: SELECT TOP N
- 문자열 결합: col1 + col2

### PostgreSQL (dialect = postgresql)
- 행 제한: LIMIT N
- 문자열 결합: col1 || col2
```

각 분기를 독립 `###` 섹션으로, 섹션 제목에 분기 조건 명시.

## 15. 금지 패턴

**왜**: 각 항목은 과거 실패 사례 또는 Qwen3 계열의 알려진 불안정성에서 도출된 실증 규칙이다.
"이번엔 괜찮을 것 같다"는 예외 허용이 품질 회귀의 주 원인. `[SELF_CHECK]`에서 반드시 체크.

- 구분선 (`────`, `===`) — markdown 비호환, 토큰 낭비
- 이모지 — Qwen3 출력 불안정
- 4단계 이상 들여쓰기 — 파싱 혼란
- 볼드 남용 — 본문 강조는 헤더로
- API 파라미터 기재 (`enable_thinking`, `temperature`, `top_p` 등) — 인프라 계층 (§0)
- `[TASK]`를 중간에 배치 — recency bias 활용 불가
- 도구 명세에 번호 목록 — 우선순위 오해, 카테고리 헤더 + 하이픈 사용
- 조건-결과 매핑을 산문으로 기술 — `→` 형식 사용
- 식별자에 대괄호 (`[K1]` → `(k1)`)
- 입력 데이터에 JSON 사용 — JSON은 출력 전용
- Few-shot에 negative 예시 포함 — `[HALLUCINATION_GUARD]`로 분리
- thinking 모드 관련 지시를 프롬프트 본문에 기재 — 인프라 계층 책임
- 필드 옆 인라인 description — vLLM #23404 Qwen3 description 값 오인 버그 트리거
