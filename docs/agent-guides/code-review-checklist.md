# 코드 리뷰 체크리스트

## 일반 검토 항목

1. 의미가 유사한 기능이 여기저기 중복구현 되어있는지 확인
2. 실제 런타임에 분기되지 않고 호출되지 않는 죽은 코드인지 확인
3. 구현된 모듈과 성격이 맞지 않은데 모듈내에 구현되어있는지 확인
4. 비즈니스 역할과 책임이 과하게 섞여 있는 코드
5. 함수명, 클래스명, 파일명 등 이름이 역할을 제대로 설명하지 못하는 코드
6. 인터페이스는 비슷한데 동작 규약이 제각각인 코드
7. 변경 전파 범위가 지나치게 큰 코드
8. 하나의 비즈니스 함수안에 "문자열 처리" 같은 저수준 구현이 너무 많이 같이 있어서 가독성이 떨어지는 경우
9. 공통화가 오히려 과한 코드
10. 업무요건상 예외처리가 미흡하거나 부적절한 코드
11. 전역변수, 멤버변수 등이 관련도가 낮거나 과도하게 많이 선언된 경우

## NL-to-SQL 특화 검토 항목

### 보안 (security-guard와 협업)
- [ ] SQL은 반드시 파라미터 바인딩 사용 (f-string, format() 금지)
- [ ] SQLValidator를 거치지 않는 DB 실행 경로 없음
- [ ] API 키, DB 패스워드 등 비밀정보 하드코딩 없음
- [ ] 사용자 입력의 로깅 시 PII 마스킹
- [ ] LLM 출력(SQL)을 그대로 실행하지 않고 반드시 후처리/검증 수행

### 에러 처리
- [ ] 모든 LLM API 호출에 타임아웃 설정
- [ ] 모든 DB 쿼리에 타임아웃 설정
- [ ] 사용자에게 노출되는 에러 메시지에 내부 정보 없음
- [ ] 재시도 로직에 지수 백오프(exponential backoff) 적용
- [ ] LLM 응답 실패 시 fallback 전략 존재 (재시도 / 대체 모델 / rule-based)
- [ ] timeout 발생 시 graceful degradation 처리
- [ ] DB 오류와 LLM 오류를 구분하여 처리
- [ ] 사용자 입력 기반 에러 메시지에 입력 내용 그대로 노출 금지
- [ ] 에러코드와 에러메세지는 한 곳에 통합하여 관리하고 호출 계층간 일관성 있는 try/catch 구조 구현

### 코드 품질
- [ ] 모든 함수에 타입 힌트
- [ ] 모든 함수의 입력변수에 대해서는 간략한 인라인 주석
- [ ] Docstring 작성 (특히 public API)
- [ ] 복잡도 높은 로직에 중간마다 흐름을 알 수 있도록 주석
- [ ] 더 이상 활용되지 않거나(호출/참조 없음), 이전 버전에서 생성된 불필요 로직의 경우 삭제 검토
- [ ] 단위 테스트 커버리지 80% 이상
- [ ] 분기 3개 이상 또는 중첩 2단계 이상 로직에는 의도 설명 주석 존재

### 명명 규칙 품질
- [ ] 디렉토리명, 프로그램명, 클래스명, 함수명, 변수명 명명 시 의미 및 패턴에 일관성 준수
- [ ] 동일 역할에는 동일 suffix 사용 (예: *service, *repository, *client, *connector)
- [ ] 약어 사용 시 프로젝트 전반에서 일관성 유지 (ex: cfg 사용 시 config 금지)
- [ ] boolean 변수는 is/has/can prefix 사용

### 에이전트 구조
- [ ] 노드는 얇게, 서비스에 위임한다. 노드 함수는 "`state` 에서 꺼내고 → `service` 를 호출하고 → `state` 에 넣는" 3줄 구조를 유지한다. (비즈니스 로직은 전부 서비스에 있어야 노드 없이도 테스트가 가능)
- [ ] 프롬프트는 로직과 분리한다. (프롬프트 텍스트가 노드나 서비스 안에 하드코딩되면, 프롬프트 튜닝할 때마다 로직 파일을 건드리게 됨)
- [ ] 의존성은 항상 아래로만 흐른다. `graph` → `nodes` → `services` → `connectors` 순서이고, 역방향 참조는 절대 없다.
- [ ] `prompt` 는 항상 `node` 로 주입되고 필요한 경우 `state` 와 함께 조립된다. 만약, `service` 에서 LLM 호출이 필요한 경우 `prompt` 를 인자로 전달한다.


### 디렉토리 구조 리뷰 체크리스트
- [ ] 이 디렉토리의 파일들은 하나의 주요 책임을 공유하는가
- [ ] 디렉토리 이름만 보고 역할을 추론할 수 있는가
- [ ] 서로 다른 계층(도메인, 인프라, 프레젠테이션)이 혼합되어 있지 않은가
- [ ] common, utils, misc처럼 의미가 약한 이름을 남용하지 않았는가
- [ ] 함께 변경되지 않는 파일들이 한 디렉토리에 섞여 있지 않은가
- [ ] 외부 시스템별 책임이 적절히 분리되어 있는가
- [ ] 순환 의존 또는 역방향 의존을 유도하는 구조가 아닌가
- [ ] 동일 디렉토리 내 프로그램들이 실행 맥락이 같은가

### 성능
- [ ] N+1 쿼리 패턴 없음
- [ ] 반복 호출되는 스키마/도메인 정보 캐싱 적용
- [ ] 비동기 처리 가능한 부분 async 적용
- [ ] 동일 요청 내 중복 LLM 호출 없음 (전략 수정 후 retry 하는 경우 예외)
- [ ] 동일 쿼리 반복 실행 방지 (캐시 또는 dedup)
- [ ] 병렬 처리 시 불필요한 순차 await 없음
- [ ] 외부 API 호출은 batch 또는 병렬 처리 고려

### NL-to-SQL 특화
- [ ] 생성된 SQL의 실행 전 반드시 validation 통과
- [ ] 신뢰도 점수 임계값 체크 로직 존재
- [ ] 도메인별 비즈니스 규칙 적용 여부 검증
- [ ] 생성된 SQL에 반드시 정해진 LIMIT 또는 row 제한 존재
- [ ] 생성된 SQL에 JOIN 조건 누락 여부 검증 (Cartesian product 방지)
- [ ] 생성된 SQL에 GROUP BY / aggregation 시 컬럼 정합성 검증
- [ ] SQL이 생성되었어도 신뢰도 낮을 경우 실행하지 않고 fallback (원인분석 명시)
- [ ] 동일 질문에 대해 결과 일관성 검증 로직 존재 (optional)
  
### 금지 규칙
- [ ] utils, common 디렉토리는 5개 이상의 서로 다른 책임이 섞이면 분리 필요
- [ ] 하나의 디렉토리가 10개 이상의 파일을 가지면 하위 디렉토리 책임 분리 검토

## 자동 정적 분석

```bash
# 타입 검사
mypy src/ --strict

# 코딩 컨벤션
ruff check src/

# 보안 취약점 스캔
bandit -r src/ -ll

# 테스트 커버리지
pytest tests/ --cov=src --cov-report=term-missing --cov-fail-under=80
```

## 리뷰 결과 형식

각 항목은 아래 정보를 반드시 포함한다.

- 심각도: Critical / Warning / Info
- 위치: 파일 + 라인
- 위반 규칙: 체크리스트 항목
- 문제 설명: 왜 문제인지
- 개선 방법: 구체적인 수정 방법

```markdown
### 🔴 Critical (반드시 수정)
1. Line 45: f-string으로 SQL 조립 → 파라미터 바인딩으로 변경

### 🟡 Warning (권장 수정)
2. Line 78: API 타임아웃 미설정 → timeout=10 추가

### 🟢 Info (참고)
3. Line 92: 캐싱 적용 시 성능 20% 향상 예상
```

## 리뷰 결과 판정 기준

- 하나의 항목이라도 명백히 위반하면 Warning 이상으로 분류한다.
- 보안 관련 항목 위반은 모두 Critical로 분류한다.
- 동일 유형의 문제가 2개 이상 발견되면 심각도를 한 단계 상향한다.
- “애매한 경우”는 Warning으로 분류하고 근거를 반드시 명시한다.

## 리뷰 작성 규칙

- 단순 나열이 아니라 “문제 → 이유 → 해결 방법” 순으로 작성한다.
- 추측이 아닌 코드 근거 기반으로 판단한다.
- 애매한 경우 근거와 함께 Warning으로 분류한다.
- 동일 유형 문제는 묶어서 설명한다.


## 기타 참고 개발 지침

1. 설계 원칙
- 코드는 우선 단순하고 명확하게 작성한다.
- 디자인 패턴은 실제로 변경 가능성, 확장 필요성, 책임 분리가 필요한 경우에만 적용한다.
- 패턴 적용 자체를 목표로 하지 않는다.
- 과도한 추상화, 불필요한 계층 분리, 과한 인터페이스 도입은 피한다.
- 현재 요구사항을 충족하면서도, 향후 변경에 무리가 없도록 균형 있게 설계한다.
2. 책임 분리
- 각 클래스, 함수, 모듈은 하나의 명확한 책임만 가지도록 작성한다.
- 서로 다른 책임이 한 곳에 섞이지 않도록 분리한다.
- 비즈니스 로직, 데이터 접근, 입출력 처리, 상태 관리는 역할에 맞는 계층에 배치한다.
- 공통 로직은 중복 구현하지 말고 재사용 가능한 단위로 분리한다.
3. 의존성 관리
- 구현체보다 추상화된 인터페이스나 명확한 계약에 의존하도록 설계한다.
- 모듈 간 결합도를 낮추고, 내부 응집도는 높게 유지한다.
- 하위 계층의 세부 구현이 상위 계층 전체에 영향을 주지 않도록 한다.
- 의존성 방향이 뒤섞이지 않도록 계층 구조를 일관되게 유지한다.
4. 재사용성과 모듈화
- 동일하거나 유사한 기능은 공통 모듈로 추출해 재사용 가능하게 구현한다.
- 다만, 재사용 이점이 불분명하면 무리하게 공통화하지 않는다.
- 공통화로 인해 코드 흐름이 더 복잡해지면 분리를 재검토한다.
- 모듈은 독립적으로 이해 가능하고 테스트 가능해야 한다.
5. 가독성
- 코드만 읽어도 의도가 이해되도록 작성한다.
- 변수명, 함수명, 클래스명은 역할과 목적이 드러나게 작성한다.
- 한 함수는 한 가지 작업만 수행하도록 유지한다.
- 조건문과 중첩은 가능한 단순하게 유지한다.
- 불필요한 축약, 숨겨진 동작, 과도한 트릭성 구현은 피한다.
6. 유지보수성
- 변경이 자주 일어날 가능성이 있는 부분은 분리하고, 고정된 부분과 섞지 않는다.
- 수정 시 영향 범위가 최소화되도록 설계한다.
- 예외 처리, 경계 조건, 실패 케이스를 명확히 다룬다.
- 테스트하기 쉬운 구조로 작성한다.
- 기존 구조와 스타일을 존중하며 일관성을 유지한다.
7. 계층과 라이프사이클
- 컴포넌트는 실행 위치와 생명주기에 맞는 계층에 배치한다.
- 상태가 필요한 객체와 Stateless 객체를 구분하여 설계한다.
- 초기화, 생성, 해제 시점이 중요한 자원은 라이프사이클을 고려해 안전하게 관리한다.
- UI, 애플리케이션 서비스, 도메인 로직, 인프라 로직이 섞이지 않도록 한다.
8. 구현 판단 기준 : 구현 중에는 항상 아래를 점검한다.
- 이 구조가 지금보다 더 단순해질 수 있는가
- 이 책임이 다른 계층이나 다른 객체에 있어야 하는가
- 중복되는 로직이 있는가
- 변경 시 영향 범위가 넓어지지 않는가
- 팀원이 처음 봐도 이해 가능한가
- 테스트하기 어려운 구조가 아닌가
- 패턴 적용이 실제 이점을 주는가
- 변경에 따라 죽은 코드는 없는가
- 중복 구현되는 모듈, 클래스, 함수, 변수, 객체는 없는가
9. 금지 사항
- 패턴을 보여주기 위해 불필요하게 복잡한 구조를 만들지 않는다.
- 작은 문제를 해결하기 위해 지나치게 많은 클래스와 인터페이스를 만들지 않는다.
- 서로 다른 책임을 하나의 클래스나 함수에 몰아넣지 않는다.
- 중복을 방치하지 않는다.
- 기존 프로젝트의 구조와 어울리지 않는 방식으로 혼자만의 스타일을 강하게 밀어 넣지 않는다.
10. 최종 목표
- 읽기 쉬운 코드
- 수정하기 쉬운 코드
- 테스트하기 쉬운 코드
- 중복이 적고 책임이 명확한 코드
- 요구사항 변경에 유연하게 대응 가능한 코드
