# 설계 비판적 검토 프레임워크

## 비판 원칙

### 원칙 1: 근거 없는 비판 금지
모든 지적에 실패 사례, 수치 근거, 논문/문서 출처, 또는 논리적 추론 동반 필수.

### 원칙 2: 비판 = 비판 + 대안
```
[금지] "이 방식은 느릴 수 있습니다."
[올바름] "이 방식은 응답 지연 문제 가능. 근거: MAC-SQL에서 +3.2초. 대안: early-exit 조건 추가."
```

### 원칙 3: 심각도 등급
- [P0] 치명적: 서비스 불가, 보안 취약, 데이터 유실
- [P1] 중대한: 목표 정확도/성능 달성 불가
- [P2] 개선 필요: 비효율, 기술 부채
- [P3] 제안: 더 나은 방향이 있으나 현재도 허용 가능

## 검토 프레임워크

### 프레임 1: 가정 검증 (Assumption Audit)
설계에 내포된 전제를 명시적으로 드러내고 타당성 검토.

### 프레임 2: 실패 시나리오 시뮬레이션
설계가 무너질 구체적 시나리오 열거.

### 프레임 3: 대안 아키텍처 비교
제안된 설계와 다른 접근법의 트레이드오프 병렬 비교.

### 프레임 4: 확장성 및 운영 리스크
단기(0~3개월), 중기(3~9개월), 장기(9개월+) 시간축 리스크 분석.

## 검토 보고서 템플릿

```markdown
# 설계 검토 보고서: <제목>
- 검토일 / 검토자 / 검토 대상

## 총평
## 가정 검증 결과
## 주요 비판 사항 ([P0] ~ [P3])
## 실패 시나리오
## 아키텍처 대안 비교
## 재조사 요청 사항
## 수용 불가 항목 (재설계 권고)
## 수용 가능 항목 (개선 권고)
## 합의 추천 설계 방향
```
