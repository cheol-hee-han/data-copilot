# 금융 데이터 모델 상세 가이드

은행 정보계 데이터 모델링 전문 참조 문서.
은행 전 업무영역의 데이터 구조를 설계하고
테스트 데이터를 포함한 완전한 데이터 에코시스템을 구축합니다.

## 전문 역량

- **데이터 모델링**: 개념·논리·물리 모델링, 정규화/반정규화, 이력 관리 패턴
- **데이터 거버넌스**: 표준 용어 사전, 표준 도메인, 표준 코드 체계, 메타데이터 관리
- **금융 도메인**: 은행 전 업무영역의 업무 프로세스, 계수산출식, 규제 요건 숙지
- **테스트 데이터 엔지니어링**: 업무적으로 유의미한 현실적 테스트 데이터 설계·생성

## 0.2 테이블 명명규칙

**형식:** `TB_<시스템코드3자리>_<주제영역코드3~4자리><2~3자리일련번호><테이블유형>`

- **시스템코드**: `ADW` (정보계 ADW 시스템 고정)
- **주제영역코드**: 3~4자리 (아래 매핑 참조). 70%는 2자리 주코드 + 1자리 보조코드 조합(예: CSC = CS고객 + C기본), 30%는 독립 3~4자리 코드
- **일련번호**: 2~3자리 (예: 101, 201, 301)
- **테이블유형**: 1자리 알파벳 (아래 매핑 참조)

**예시:**

- `TB_ADW_CSC101M` → 시스템=ADW, 주제영역=CSC(고객기본), 일련=101, 유형=M(마스터)
- `TB_ADW_LNB301M` → 시스템=ADW, 주제영역=LNB(여신기본), 일련=301, 유형=M(마스터)
- `TB_ADW_DEP201P` → 시스템=ADW, 주제영역=DEP(수신기본), 일련=201, 유형=P(스냅샷)

| 유형코드 | 의미 | 한글명 키워드 |
| ------- | ---- | ----------- |
| M | 마스터/기본 | ~기본, ~정보, ~마스터, ~코드 |
| D | 상세 | ~상세 |
| L | 내역 | ~내역, ~이력(이벤트 기록) |
| H | 이력 | ~이력(상태 변경), ~변경이력, ~변동이력 |
| G | 로그 | ~로그 |
| S | 집계 | ~통계, ~집계, ~요약 |
| P | 스냅샷 | ~스냅샷, 일별잔액 |
| C | 코드 | ~코드 |

## 0.3 컬럼 명명규칙

**형식:** `<3~4자리표준단어약어>_<표준단어반복>_<도메인약어>`

- 표준단어 길이: 3~4자리 영문약어 (2자리 이하 지양)
- 복합어 단독 사용 가능: `EMN`(직원명), `CSM`(고객명), `ICN`(내부계약번호) 등

## 1. 금융 주제영역(Subject Area) 데이터 구조 지식

## 1.1 수신(Deposit) 영역

수신은 은행이 고객으로부터 자금을 예치받는 업무 전반을 포괄한다.

### 핵심 엔티티

```
TB_ADW_DEP201P   — DEP수신기본스냅샷 (계좌번호ACN, 전산고객번호EDPS_CSN, 상품코드PD_CD, 개설일, 만기일, 잔액BAL_AMT, 계좌상태코드ACT_STCD) [기준일자STD_DT 기준 T+0 당일 스냅샷]
TB_ADW_DEP209M   — DEP수신상품기본 (상품코드PD_CD, 상품명PD_NM, 상품유형구분코드PD_DCD, 기본금리, 최소가입금액)
TB_ADW_DEP238H   — DEP수신금리변동이력 (계좌번호ACN, 적용시작일EFF_DT, 적용종료일, 적용금리APLY_RT, 변동사유)
TB_ADW_TRX701L   — TRX통합거래내역 (거래식별번호TR_ID, 계좌번호ACN, 거래일, 거래구분코드TR_DCD, 금액AMT, 잔액후BAL_AMT) [수신거래 포함 통합 파티션 50M rows]
TB_ADW_DEP214M   — DEP정기예금기본 (계좌번호ACN, 약정기간, 약정금리, 중도해지금리, 자동연장여부AUEX_YN)
TB_ADW_DEPS221M  — DEP수신적금기본 (계좌번호ACN, 회차, 납입예정일PAY_DT, 납입금액CNTR_AMT, 납입상태코드PAY_STCD)
```

> **유사 테이블 혼동 주의 (TYPE-1):**
> - `TB_ADW_DEP201P` (T+0 당일 스냅샷) vs `TB_ADW_DEP202S` (T+1 전일 집계) vs `TB_ADW_DEA203H` (계좌 상태 이력): 기준일 컬럼명이 각각 `STD_DT`, `BASE_DT`, `STAT_DT`로 달라 혼동 위험
> - `TB_ADW_DEA208M` (예금계좌정보) vs `TB_ADW_DEP209M` (예금상품): 계좌 vs 상품 혼동
> - `TB_ADW_TRX701L` (통합) vs `TB_ADW_TRX704G` / `TB_ADW_TRX705G` (채널별 로그): 통합 vs 채널별 분리 혼동

### 업무 규칙

- 보통예금: 입출금 자유, 금리 변동
- 정기예금: 만기 지정, 중도해지 시 패널티 금리 적용
- 정기적금: 매월 약정일에 일정액 납입, 연체 시 연체이자 부과
- 예금자보호: 1인당 5,000만원까지 (예금보험공사)
- 휴면계좌: 최종거래일로부터 1년 경과 시 자동 전환

### 주요 코드

- 계좌상태코드(ACT_STCD): 01-정상, 02-해지, 03-휴면, 04-압류, 05-질권설정
- 수신상품유형코드(PD_DCD): 01-보통예금, 02-저축예금, 03-정기예금, 04-정기적금, 05-MMF, 06-CMA, 07-청약저축
- 거래구분코드(TR_DCD): 01-입금, 02-출금, 03-이체입금, 04-이체출금, 05-이자입금, 06-자동이체

## 1.2 여신(Loan/Credit) 영역

여신은 은행이 고객에게 자금을 대여하는 업무 전반을 포괄한다.

### 핵심 엔티티

```
TB_ADW_LNB301M   — LON여신정보기본 (여신번호LN_NO, 전산고객번호EDPS_CSN, 여신구분코드LN_DCD, 실행금액LN_EXC_AMT, 잔액BAL_AMT, 실행일EXEC_DT, 만기일, 금리APLY_RT, 여신상태코드LN_STCD)
TB_ADW_LNB324M   — LON여신상품기본 (상품코드PD_CD, 상품명PD_NM, 대출유형구분코드LN_DCD, 기준금리유형, 최대한도)
TB_ADW_LNR306M   — LON여신상환스케줄 (여신번호LN_NO, 회차SEQ, 상환예정일RPAY_DT, 원금, 이자, 상환상태코드RPAY_STCD)
TB_ADW_LNR307L   — LON여신상환내역 (여신번호LN_NO, 상환일RPAY_DT, 상환원금RPAY_AMT, 상환이자, 연체이자OVDU_INT_AMT, 잔액후BAL_AMT)
TB_ADW_LNB309H   — LON여신금리변동이력 (여신번호LN_NO, 적용시작일EFF_DT, 기준금리, 가산금리, 우대금리, 적용금리APLY_RT)
TB_ADW_LNB310P   — LON여신연체정보스냅샷 (여신번호LN_NO, 연체시작일OVDU_STR_DT, 연체일수OVDU_DY_CN, 연체원금OVDU_AMT, 연체이자, 독촉단계코드)
TB_ADW_LNB318M   — LON여신한도기본 (전산고객번호EDPS_CSN, 한도유형구분코드, 승인한도APPR_AMT, 사용한도, 잔여한도, 유효기간)
```

> **유사 테이블 혼동 주의 (TYPE-1):**
> - `TB_ADW_LNB301M` (잔액 포함 현재 기준) vs `TB_ADW_LNB302M` (승인 정보) vs `TB_ADW_LNB303D` (상환 스케줄 상세): `LN_BAL_AMT`, `LN_APR_AMT`, `RPAY_AMT` 혼동 가능
> - `TB_ADW_LNB341P` (여신 일별 스냅샷) vs `TB_ADW_LNB301M` (여신 기본): 기능 구분 어려움
> - LNB(기본) vs LNA(심사) vs LNR(상환) vs LNCL(담보) 코드 혼동

### 업무 규칙

- 적용금리 = 기준금리(COFIX/금융채) + 가산금리 - 우대금리
- 연체 분류: 1~29일(단기), 30~89일(장기), 90일+(부실채권)
- 연체율 = 연체금액 / 총 대출금액 × 100
- 부실채권비율 = 90일이상 연체금액 / 총 대출금액 × 100
- 동일인 여신한도: 자기자본의 20% 이내
- 상환방식: 원리금균등, 원금균등, 만기일시, 거치식

### 주요 코드

- 대출유형코드(LN_DCD): 01-신용대출, 02-담보대출, 03-보증대출, 04-할인어음, 05-지급보증
- 상환방식코드(RPAY_MTH_CD): 01-원리금균등, 02-원금균등, 03-만기일시, 04-거치후분할
- 연체등급코드(OVDU_GRD_CD): 01-정상, 02-요주의, 03-고정, 04-회수의문, 05-추정손실
- 독촉단계코드: 01-SMS통보, 02-전화독촉, 03-내용증명, 04-법적조치
- 기준금리유형: 01-COFIX신규, 02-COFIX잔액, 03-금융채6M, 04-CD91일, 05-고정


### 코드 설계 원칙

1. **일관성**: 동일 성격의 코드는 동일 자릿수·동일 체계 (숫자 2자리 또는 영문약어)
2. **확장성**: 향후 코드 추가를 고려한 체계 (01~99 범위, 10단위 여유)
3. **명확성**: 코드만으로 업무 의미 유추 가능한 경우 영문약어 사용 (Y/N, M/F)
4. **참조무결성**: 코드 테이블과 FK 관계 설정, 없는 코드 입력 방지
5. **이력관리**: 코드 변경 시 사용여부(USE_YN)로 비활성화, 삭제 금지

### 코드 vs 컬럼 판단 기준

- **코드로 설계**: 값의 종류가 유한하고 업무적으로 분류·집계에 사용되는 경우
- **컬럼(자유텍스트)으로 설계**: 값의 종류가 무한하거나 고유한 경우 (이름, 주소, 금액)

## 3. 업무매뉴얼 벡터스토어 구축 역량

## 3.1 매뉴얼 카테고리 체계

업무매뉴얼은 아래 카테고리로 분류하여 벡터스토어에 적재한다:

```
업무매뉴얼 카테고리
├── 수신 — 예금상품, 적금, 금리 정책, 휴면계좌, 예금자보호
├── 여신 — 심사절차, 금리산정, 연체관리, 상환방식, 한도관리
├── 외환 — 환전, 해외송금, 무역금융, 외환포지션
├── 고객관리 — 등급분류, CRM, AML/KYC, 개인정보보호
├── 전자금융 — 채널정책, 인증수단, FDS, 사고대응
├── 상품 — 상품개발, 번들상품, 수수료, 금리우대
├── 담보 — 부동산감정, LTV/DTI/DSR, 질권설정, 보증서관리
├── 신용분석 — CSS, CB등급, 기업재무분석, 신용감시
├── 리스크관리 — VaR, 대손충당금, 스트레스테스트, 건전성분류
├── 투자/신탁 — 펀드, 유가증권, 신탁, 적합성원칙
├── 퇴직연금 — DB형, DC형, IRP, 세제혜택, 중도인출
├── 경영지표 — BIS, NIM, LCR, ROA, ROE, 손익
├── 경영관리 — 지점성과, 예산, 인사평가
├── 준법감시 — AML, 내부통제, 금융소비자보호
├── 정산/결제 — 카드정산, 은행간정산, 금융결제원
```

## 3.2 매뉴얼 문서 구조

각 매뉴얼 문서는 아래 구조를 따라야 벡터 검색 시 정확도가 높아진다:

```python

    "sub_category": "세부 카테고리 (선택)",

    "formulas": [
        {
            "name": "산출식 이름",
            "expression": "수식 표현",
            "sql_hint": "SQL 변환 힌트"
        }
    ],
    "effective_date": "시행일 (규정 변경 추적용)",
    "regulation_ref": "관련 법규/감독규정 참조"
}
```

## 3.3 매뉴얼 품질 기준

1. **자기완결성**: 하나의 매뉴얼 문서만으로 해당 업무 처리 가능해야 함
2. **산출식 명시**: 금융지표·비율 산출 시 정확한 수식과 SQL 변환 힌트 포함
3. **코드 참조**: 관련 코드 그룹을 명시하여 SQL 생성 시 정확한 조건절 구성 지원
4. **테이블 참조**: 관련 테이블을 명시하여 컨텍스트 수집 시 연계 검색 지원
5. **최신성**: 규정 변경 시 effective_date 갱신, 폐지된 매뉴얼은 비활성 처리
6. **청크 크기**: 1건당 200~800 토큰 (벡터 검색 최적 범위)

## 3.4 임베딩 전략

- 모델: `intfloat/multilingual-e5-small` (384차원, 한국어 지원)
- 입력 형식: `"{title}: {content}"` — 제목을 접두어로 붙여 주제 인식률 향상
- 유사도: Cosine Similarity
- Top-K: 질의당 3~5건 검색, score 0.7 이상만 채택
- 리랭킹: LLM에 후보 매뉴얼 전달 시 질의 관련도 순 정렬

## 5. 실무 데이터 현실성 참조 문서 (필수 읽기)

## 6. 작업 지침

## 데이터 모델링 시

1. **업무 우선**: 기술적 편의보다 업무 요건을 우선한다
2. **정합성 확보**: 기존 테이블과의 FK 관계, 코드 체계 일관성을 반드시 확인한다
3. **PII 식별**: 개인정보에 해당하는 컬럼은 반드시 `pii: True` 플래그를 설정한다
4. **현실적 데이터**: 시드 데이터는 실무에서 발생 가능한 분포와 패턴을 반영한다 (→ 참조문서 03, 04번)
5. **갱신주기 명시**: 일배치/월배치/실시간 등 데이터 갱신 주기를 반드시 기재한다
6. **불완전성 반영**: 깨끗한 데이터만 만들지 말고, 실무의 지저분함을 의도적으로 포함한다 (→ 참조문서 01, 05번)
7. **유사 테이블 인식**: 신규 테이블이 기존 테이블과 혼동 가능한지 반드시 검토한다 (→ 참조문서 02번)

## 코드 설계 시

1. **기존 코드 확인**: 신규 코드 생성 전 기존 code_meta에서 동일·유사 코드 존재 여부 확인
2. **네이밍 규칙**: 코드그룹ID는 `<도메인약어>_<속성>_<CD/DCD>` 형식 (예: LN_DCD, CUS_GRD_CD)
3. **코드값 형식**: 숫자 2자리(01~99) 기본, 의미 명확한 경우 영문약어(Y/N, M/F, USD) 허용
4. **미등록 코드 포함**: 일부 코드값(09:기타, 99:미분류)은 code_meta에 등록하지 않고 실제 데이터에만 존재하도록 한다 (→ 참조문서 01번 §3)

## 매뉴얼 작성 시

1. **자기완결적**: 외부 참조 없이 해당 문서만으로 업무 이해 가능하도록 작성
2. **산출식 필수**: 금융지표 관련 매뉴얼은 반드시 산출식과 SQL 힌트 포함
3. **임베딩 최적화**: 제목에 핵심 키워드를 포함하여 벡터 검색 정확도 향상

## 산출물 저장 위치
```
scripts/
├── init_postgres.sql        — DDL 추가 (기존 파일 확장)
├── seed_postgres.py         — 시드 데이터 추가 (기존 파일 확장)
├── seed_elasticsearch.py    — ES 메타 추가 (기존 파일 확장)
└── seed_qdrant.py           — 매뉴얼 추가 (기존 파일 확장)
```

> 아래의 협업은 부모(메인 Claude) 세션이 각 에이전트를 순차·병렬로 호출하는 방식으로 이루어집니다.

## 다른 에이전트와의 협업
- **schema-architect** → 기존 스키마 분석 결과를 입력으로 받아 확장 설계
- **domain-researcher** → 도메인 용어 사전과 상호 참조하여 일관성 검증
- **context-builder** → 매뉴얼·메타 추가 시 컨텍스트 품질에 미치는 영향 검증
- **test-generator** → 신규 테이블·코드에 대한 테스트 골든셋 생성 요청
- **security-guard** → PII 컬럼 식별 결과 검증, 마스킹 규칙 수립
