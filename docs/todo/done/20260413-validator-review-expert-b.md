## 라운드 1: LLM-as-Judge 관점에서 체크 수 최적화

### 1. Qwen3.5 397B급에서 8개 체크 vs 6개 체크의 정확도 차이

실질적인 차이가 존재한다. 근거는 두 가지다.

첫째, LLM-as-Judge 실험 결과(G-Eval, FActScoring 계열 연구)에서 판정 항목이 5개를 초과하면 모델이 후반 항목에 대한 집중도가 떨어지는 경향이 관찰된다. 특히 "각 항목을 독립적으로 판단하라"는 지시 없이 연속 나열하면, 앞 항목의 판정 방향이 뒤 항목에 앵커링된다(판정이 bias된다). Qwen3.5 397B는 충분히 강력한 모델이나, 9개 항목(현행)을 순서대로 fill하는 과정에서 measure_reflected → filters_reflected → ... → code_name_paired 순으로 앵커링 누적이 발생할 수 있다.

둘째, 더 직접적인 문제가 있다. 현행 체크 1(measure)과 체크 4(order_limit)는 decomposition 데이터 손실로 인해 검증 근거 자체가 부실하다. 손실된 데이터로 판정하는 체크가 포함된 상태에서 체크 수가 많을수록 "불확실한 체크들이 confident하게 pass=true를 찍는" hallucination risk가 높아진다. 이 경우 체크 수 절감은 정확도 저하가 아니라 오히려 신뢰도 향상을 가져온다.

**결론**: 검증 근거가 충분한 체크는 세분화가 유리하지만, 근거 데이터가 손실된 체크를 유지하는 것은 "체크했다는 착각"을 만든다. 체크 1, 4는 근거 데이터 보완 없이는 유지해도 오히려 해롭다.

### 2. 체크 수가 적을수록 좋은가 vs 스캐폴딩 효과

무조건 줄이는 것이 좋은 것은 아니다. 체크를 세분화하는 스캐폴딩 효과는 실재한다.

예를 들어, 체크 2(filter)와 체크 3(group_by)는 명시적으로 분리되어 있기 때문에 LLM이 "필터 조건은 있는데 GROUP BY를 빠뜨린 SQL"을 통과시키는 실수를 예방한다. 만약 이 둘을 하나의 "구조적 반영" 체크로 합치면, LLM이 어느 하나만 확인하고 나머지는 암묵적으로 통과시킬 위험이 생긴다.

스캐폴딩 효과의 핵심 원칙: **체크는 LLM이 자발적으로 챙기지 않는 영역을 강제할 때 의미가 있다.** filter와 group_by는 서로 다른 SQL 절이고 둘 다 누락 빈도가 높으므로 분리 유지가 정당하다. 반면 measure와 order_limit은 현재 검증 근거 자체가 부실하므로 분리 유지가 의미 없다.

**결론**: 체크 수 최적화의 기준은 "모델이 자발적으로 챙기지 않는가" + "검증 근거가 충분한가"의 곱이다. 이 둘을 모두 충족할 때만 독립 체크로 유지한다.

### 3. measure/order_limit을 체크 7(논리적 정합성)에 흡수할 때 판정 부하

우려는 타당하나, 흡수 방식에 따라 위험 수준이 달라진다.

단순 흡수("체크 7에서 measure와 order_limit도 보라")는 판정 부하를 가중시켜 체크 7의 전체 신뢰도를 떨어뜨린다. 체크 7은 이미 기간 반영, 질의 유형 반영, 대상 반영, AI 추론 교차검증, 0건 판정 등 복합적인 관점을 담고 있다. 여기에 "지표 산출 방식"과 "결과 가공 반영"까지 추가하면 하나의 체크에 7~8개 판단 포인트가 생긴다.

올바른 흡수 방식: **체크 7 내부를 명시적 서브항목으로 구조화한다.** 즉, 체크 7을 "논리적 정합성 — 아래 관점을 순서대로 확인하라"는 방식으로 체크리스트화하고, measure 관련 관점("사용자가 요청한 지표 유형이 SQL에 맞게 표현되었는가")과 order_limit 관련 관점("순위/정렬/결과 가공 지시가 SQL에 반영되었는가")을 서브항목으로 명시한다. 이렇게 하면 LLM이 각 포인트를 순서대로 체크하는 CoT 흐름이 형성되어 누락 위험이 줄어든다.

**결론**: 흡수는 가능하지만, 체크 7 내부에 서브항목 구조를 명시해야 한다. "흡수 → 단순 언급"이 되면 정확도 저하 위험이 실재한다.

### 4. 빈 배열이면 LLM이 자동 pass=true를 출력하므로 해가 없지 않은가

이 논리는 EXTRACT 질의에서는 대체로 성립하지만, 세 가지 반례가 있다.

첫째, measures 배열이 비어 있는 경우 LLM이 "검증 대상 없음 → pass=true"로 처리하는 것 자체는 문제없다. 그러나 RATIO 질의처럼 measures에 `{term: "연체율", agg_function: "NONE"}`이 들어 있는 경우, LLM은 "agg_function이 NONE이면 집계가 없어야 한다"고 판단한다. 하지만 실제 SQL에는 분자/분모 각각 SUM이 필요하다. 현행 체크 1의 판정 기준이 "집계함수가 반영되었는가"이므로, LLM은 NONE인데 SUM이 있으니 불일치라고 잘못 FAIL을 낼 수 있다. 빈 배열이 아닌 경우의 오판 위험이 더 심각하다.

둘째, measures에 데이터가 있지만 measure_type이 손실된 상태에서 LLM이 불완전한 데이터를 "있는 것으로 판단"하고 섣불리 pass=true를 낸 뒤 체크 7에서 같은 항목을 재확인하지 않는 경우, 중복 검증 없이 오류가 통과된다.

셋째, 빈 배열 자동 pass가 성립하려면 LLM이 "빈 배열 = 해당 없음 = pass"라는 규칙을 안정적으로 따라야 한다. 현행 프롬프트에는 이 규칙이 명시되어 있지 않아서, LLM이 "measures가 없는데 SQL에 COUNT(*)가 있다 → 불일치"라고 오판하는 케이스가 발생할 수 있다. 따라서 빈 배열 처리 규칙을 명시하거나, 애초에 근거가 부실한 체크를 제거하는 것이 낫다.

**결론**: "빈 배열이라 해가 없다"는 EXTRACT 케이스에만 성립하는 부분적 논리다. RATIO, WINDOW 질의에서의 오판 위험이 더 심각하며, 체크 1 제거가 안전하다.

## 라운드 2: 프롬프트 토큰 효율성

### 1. 현재 프롬프트 체크 1~4 정의 + 예시의 토큰 비중 추정

sql_validator_system.txt 전체 길이를 기준으로 구간별 토큰을 추정한다.

| 구간 | 내용 | 추정 토큰 |
|------|------|-----------|
| [ROLE] | 역할 선언 3줄 | ~60 |
| [RULES] 체크 1~4 정의 | 측정값/필터/그룹/정렬 판정 기준 | ~300 |
| [RULES] 체크 5~9 정의 | 미확인값/dead_end/논리/DB/코드명 | ~800 |
| [HALLUCINATION_GUARD] | 4개 오판 방지 섹션 | ~500 |
| [EXAMPLES] 예시 1~6 | SQL + JSON 출력 6개 | ~3,000 |
| [OUTPUT_CONTRACT] | JSON 스키마 + 보충 규칙 | ~400 |
| [CONTEXT] | 플레이스홀더 블록 | ~200 |
| [TASK] | 재강조 4줄 | ~80 |
| **합계** | | **~5,340** |

체크 1~4 정의가 차지하는 비중은 약 5~6%다. 정의 자체의 토큰 절감 효과는 작다. 그러나 예시 6개에서 체크 1, 4(measure_reflected, order_limit_reflected)가 각 예시마다 반복 출력되는 부분이 전체 예시 토큰의 약 20~25%를 차지한다. 6개 예시 × 2개 체크 제거 = 예시 토큰 절감 약 600~700토큰이 순효과다.

**추정 토큰 절감**: 체크 정의 ~120 + 예시 내 반복 항목 ~650 = 약 770토큰 절감.

### 2. 6개로 줄이면 절감되는 토큰 vs 체크 7 보강 토큰의 순효과

체크 7(논리적 정합성)에 서브항목 3개(지표 산출 방식, 결과 가공, 정렬/제한)를 추가하면 약 200~250토큰이 증가한다. 앞의 절감분(770토큰)과 상쇄하면 **약 500~550토큰 순절감**이다. 프롬프트 전체가 약 5,340토큰이라면 약 10% 경량화 효과다.

이보다 더 중요한 효과는 LLM이 처리해야 할 독립 JSON 키가 9개에서 7개로 줄어들어 출력 안정성이 높아진다는 점이다. Qwen3.5 397B는 JSON 필드 누락/순서 오류가 간헐적으로 발생하는데, 필드 수 절감이 직접적인 파싱 안정성 향상으로 이어진다.

### 3. few-shot 예시 6개의 적절성과 체크 수 변경 시 재설계 필요 여부

체크 수 변경 시 예시 재설계는 필수다. 이유는 두 가지다.

첫째, 현행 예시 6개는 모두 9개 체크 키(measure_reflected, order_limit_reflected 포함)를 출력하고 있다. 체크 구조 변경 후 이 예시를 그대로 남기면 LLM이 제거된 키를 여전히 출력하려고 시도한다. 프롬프트 예시와 OUTPUT_CONTRACT 간의 불일치는 Qwen 계열 모델에서 특히 강하게 드러난다(예시 형식을 CONTRACT보다 우선시하는 경향).

둘째, 현행 6개 예시의 커버리지를 점검하면, 체크 7의 서브항목(지표 산출 방식, 결과 가공)을 직접 검증하는 예시가 없다. 재설계 후 추가해야 할 핵심 케이스는 다음과 같다.

| 필요 케이스 | 현행 커버 여부 |
|---|---|
| RATIO 지표(연체율 등) SQL 반영 판정 | 없음 |
| DELTA/CUMULATIVE 결과 가공 SQL 반영 판정 | 없음 |
| 기간 필터 PASS (복잡한 날짜 함수) | 예시 5에 부분 존재 |
| 0건 PASS (dead_end 없음) | 예시 4 |
| 0건 FAIL (dead_end 반복) | 예시 3 |
| local_fix (타입 불일치) | 예시 2 |
| local_fix (코드값 오류) | 예시 6 |

체크 1 흡수로 인해 RATIO/WINDOW 질의 판정 방식이 바뀌므로, 이를 커버하는 예시를 1~2개 추가해야 한다. 총 예시 수는 6~7개가 적절하다(7개 이상은 프롬프트 길이 부담이 크다).

### 4. Qwen3.5의 context window와 프롬프트 길이 최적 범위

Qwen3.5 397B의 context window는 128K토큰이다. 단순 길이 제한은 문제가 아니다.

실질적 최적 범위 판단 기준은 "시스템 프롬프트 + 컨텍스트 주입 데이터의 합산 토큰"이다. validator 호출 시 `{generated_sql}`, `{table_schema}`, `{confirmed_terms}`, `{code_mappings}` 등 가변 데이터가 추가로 주입된다. 현행 시스템 프롬프트 ~5,340토큰 + 가변 데이터 최대 3,000~5,000토큰을 합산하면 총 8,000~10,000토큰 범위다.

이 범위에서 시스템 프롬프트가 차지하는 비율이 50~60%로 높다. Qwen3.5는 전체 컨텍스트의 앞쪽(시스템 프롬프트)과 뒤쪽([TASK])에 집중하는 경향이 있고, 중간의 예시 구간은 Lost-in-the-Middle 효과로 인해 주의도가 떨어진다. 따라서 **시스템 프롬프트는 4,500~5,000토큰 이내**로 유지하고, 핵심 규칙은 [TASK] 말미에 재강조하는 것이 최적이다.

현행 프롬프트의 주된 비효율 구간은 [EXAMPLES]이며, 이를 4,500토큰 이내로 맞추려면 예시당 평균 600토큰 이하를 목표로 해야 한다. 현행 예시들은 SQL + JSON 출력을 모두 포함하여 예시당 450~550토큰 수준으로 허용 범위 내에 있다.

## 라운드 3: 직렬화 방식이 LLM 판정 정확도에 미치는 영향

### 1. raw JSON vs 가독성 텍스트 — Qwen3.5급에서의 실제 차이

차이가 있다. 방향은 질의의 복잡도에 따라 다르게 나타난다.

단순 질의(필터 1~2개, 집계 1개)에서는 raw JSON과 가독성 텍스트 간 판정 정확도 차이가 미미하다. Qwen3.5급 모델은 JSON을 자연어로 파싱하는 능력이 충분하다.

복잡 질의(RATIO 지표, DELTA_RATE modifier, PRE_AGG/POST_AGG 혼재)에서는 raw JSON의 중첩 구조가 판정 오류를 유발한다. 구체적으로, 현행 직렬화는 다음과 같은 형태로 출력된다:

```
measures: [{"term": "연체율", "agg_function": "NONE"}]
filters: [{"term": "대출상태", "operator": "EQUALS", "value": ["연체"]}]
```

이 형태에서 "agg_function": "NONE"은 LLM에게 "집계 없음"으로 읽힌다. 하지만 실제 SQL에서 연체율은 분자 SUM과 분모 SUM이 모두 필요하다. measure_type 정보가 손실되어 있어서 LLM은 "agg=NONE인데 SQL에 SUM이 있다 → measure 불반영"으로 오판한다. 이것은 직렬화 형식의 문제라기보다 데이터 손실의 문제이지만, 가독성 텍스트 형식으로 전환하면서 "note: 연체대출잔액/총대출잔액 산출식 필요"를 함께 전달하면 LLM이 올바르게 판단할 가능성이 높아진다.

실험적 근거: Chain-of-Thought 프롬프팅 연구에서 자연어 서술형 입력이 JSON 입력 대비 추론 정확도를 5~15% 향상시킨다는 보고가 있다(Wei et al., 2022 계열). 이 효과는 특히 다중 속성을 동시에 판단해야 할 때 두드러진다.

**결론**: 복잡 질의 케이스에서 가독성 텍스트가 유리하다. 단, 직렬화 형식 변경보다 데이터 손실 보완이 선행되어야 효과가 있다.

### 2. null, false, 빈 배열 같은 JSON 노이즈의 영향

부정적 영향이 실재한다. 메커니즘은 두 가지다.

첫째, Qwen3.5 계열 모델은 JSON을 토큰 수준에서 처리하므로 `null`, `false`, `[]`, `{}` 같은 기호 토큰이 많을수록 "이 필드는 의미 없음"을 판단하는 데 추가 추론 비용이 든다. 현행 `order_limit: []` 같은 빈 배열이 있을 때, LLM은 "order_limit 체크 시 배열이 비어 있으니 해당 없음 → pass=true"를 명시적으로 추론해야 한다. 이 추론이 암묵적으로 처리되면 체크 누락이 발생한다.

둘째, `{"type": "RANK", "value": "10"}` 형태에서 value가 문자열 "10"으로 직렬화되는 문제(현행 reasoning_preparer.py: `str(mod.limit or mod.by or "")`)가 있다. mod.limit이 10이고 mod.by가 "신규금액"인 경우, `mod.limit or mod.by`는 10이 truthy이므로 `str(10)`="10"이 된다. mod.by가 무시된다. LLM은 정렬 기준 컬럼 정보를 받지 못한 채 order_limit 체크를 수행한다.

개선 방향: `null`/빈 배열이 있는 필드는 직렬화 시 아예 생략하거나, "(없음)" 텍스트로 명시적으로 대체한다. LLM이 해석 여부를 고민할 필요가 없게 만드는 것이 핵심이다.

### 3. 직렬화 형식 변경 시 few-shot 예시와의 일관성 문제

이것이 실제로 가장 큰 위험 요소다.

현행 예시 1~6은 모두 CONTEXT의 질의 분해 블록이 특정 형식으로 되어 있고, 그 형식이 실제 주입될 데이터 형식과 일치할 것을 전제로 한다. 직렬화 형식을 변경하면서 예시를 업데이트하지 않으면 다음 문제가 발생한다:

- 예시의 `질의 분해: measures=[{term: "건수", agg: "COUNT"}]` 형태와 실제 주입되는 `- measure: [{"term": "건수", "agg_function": "COUNT"}]` 형태가 다르면 LLM이 두 형식 중 어느 것을 따라야 할지 혼동한다.
- Qwen 계열 모델은 예시 형식을 CONTRACT보다 우선시하는 경향이 있어서, 변경된 CONTRACT 형식이 아닌 예시의 구식 형식으로 판정 JSON을 출력하는 경우가 발생한다.

이 문제는 프롬프트-예시 일관성 체크가 코드 변경 체크리스트에 명시되어 있음(prompt-rules.md §7)에도 불구하고, 현행 예시들이 질의 분해 블록을 단순화된 형태로만 보여주어 불일치 위험이 내재해 있다.

**직렬화 변경 시 최소 요건**: 예시의 CONTEXT 섹션(질의 분해 블록)을 실제 주입 데이터 형식과 완전히 동일하게 업데이트해야 한다.

### 4. 플레이스홀더 5개 유지 vs 하나의 "질의 분해" 블록으로 통합

통합이 유리하다. 이유를 3가지로 정리한다.

**이유 1 — 체크 구조 변경과의 정합성**: 체크를 6개로 줄이면 독립 체크에 대응하는 플레이스홀더가 measures, filters, group_by, order_limit, output_hint 5개에서 filters, group_by 2개로 줄어든다. measures, order_limit, output_hint는 체크 7(논리적 정합성) 내부 판단 재료가 된다. 이 경우 5개 플레이스홀더를 유지하는 것은 CONTEXT 섹션에 사용되지 않는 독립 블록들이 생기는 구조적 불일치를 만든다.

**이유 2 — 데이터 손실 해결**: NormalizedQuery 전체를 하나의 블록으로 전달하면, 현행 decomposition 변환 과정에서 발생하는 measure_type, note, position, direction, by 손실을 근본적으로 해결할 수 있다(선택지 C에 해당). validator가 직접 NormalizedQuery를 읽어 필요한 필드를 추출하는 방식은 중간 변환 레이어를 제거한다.

**이유 3 — LLM 처리 편의**: 5개의 독립 플레이스홀더보다 "질의 정규화 요약" 하나의 구조화된 블록이 LLM에게 더 자연스러운 입력이다. CONTEXT 섹션이 "원 질의 → 정규화 요약 → SQL → 스키마 → ..." 순서로 정렬되면, 모델이 "원 질의와 정규화 요약을 비교하여 SQL을 검증한다"는 추론 흐름을 자연스럽게 따른다.

**단 주의사항**: 통합 블록의 크기를 제어해야 한다. NormalizedQuery 전체를 raw JSON으로 덤프하면 1,000~2,000토큰이 될 수 있다. validator가 실제로 필요한 필드(filters, dimensions.role=GROUP/PARTITION, modifiers, measures.measure_type+note)만 선택적으로 포함하는 전용 직렬화 함수(선택지 B)가 최적이다.

## 라운드 4: 최종 권고

### 1. 체크 수와 구성에 대한 최종 권고

**권고: 9개 → 7개 (체크 1 제거, 체크 4 흡수, 체크 9 유지)**

현행 체크 구조 개선안에서 체크 9(코드 컬럼 명칭 동반)는 독립 유지를 권고한다. 이유는 이 체크가 SQL 생성에서 가장 흔히 누락되는 UX 문제를 감지하며, 검증 근거가 명확하고(코드성 컬럼 존재 여부만 확인), pass=false 시 local_fix로 분류되어 파이프라인 부담도 최소이기 때문이다. todo 문서의 6개 안(체크 1, 4, 9를 모두 축소하는 방향)은 체크 9를 제거 대상으로 언급하지 않았으므로 이 항목은 현행 유지가 자연스럽다.

최종 권고 구성:

| 새 번호 | 내용 | 이전 번호 | 변경 |
|---------|------|-----------|------|
| 체크 1 | filter 반영 | 체크 2 | 유지 |
| 체크 2 | group_by 반영 | 체크 3 | 유지 |
| 체크 3 | 미확인 값 사용 | 체크 5 | 유지 |
| 체크 4 | dead_end 반복 | 체크 6 | 유지 |
| 체크 5 | 논리적 정합성 (서브항목 추가) | 체크 7 | 보강 |
| 체크 6 | DB 실행 결과 | 체크 8 | 유지 |
| 체크 7 | 코드 컬럼 명칭 동반 | 체크 9 | 유지 |

체크 5(논리적 정합성)의 서브항목 구조(순서대로 판단):

```
① 기간 반영 — 사용자 기간 표현이 WHERE 절에 올바르게 적용되었는가
② 질의 유형 반영 — RANK/TREND/COMPARE 등 SQL 구조 요건 충족되었는가
③ 지표 산출 방식 — 요청한 지표(건수/금액/비율/증감 등)가 SQL에 올바르게 표현되었는가
④ 결과 가공 — 순위/증감/변화율/누적 등 modifier가 SQL 구조에 반영되었는가
⑤ 대상 반영 — 사용자 언급 대상(예금/대출 등)이 적절한 테이블에서 조회되는가
⑥ AI 추론 교차검증 — reasoning_decisions와 SQL 로직이 일관되는가
⑦ 0건 판정 — 0건인 경우 4개 fail 조건 중 해당 여부 확인
```

이 구조는 체크 1(measures)과 체크 4(order_limit)의 검증 포인트를 ③, ④번에 흡수하되, CoT 서브항목 형식으로 명시하여 LLM이 각 관점을 순서대로 판단하도록 강제한다.

### 2. 직렬화 방식 최종 권고

**권고: 선택지 B (validator 전용 직렬화, NormalizedQuery 직접 참조)**

근거:

- 선택지 A(serialize_decomp_slots 가독성 개선): 근본적인 데이터 손실 문제가 _build_decomposition_from_normalized에서 발생하므로, 직렬화 형식만 바꿔서는 해결되지 않는다. 개선 범위가 불완전하다.
- 선택지 C(decomposition 폐기, NormalizedQuery 전체 요약 블록): 데이터 손실 해결 측면에서는 최선이나, NormalizedQuery의 모든 필드를 포함하면 토큰 비효율이 크고, 다른 모듈(sql_generator 등)의 decomposition 활용 방식에도 영향을 줄 수 있다.
- 선택지 B: validator가 체크에 실제로 필요한 필드만 NormalizedQuery에서 직접 추출하여 가독성 있는 텍스트로 직렬화한다. 영향 범위가 sql_validator.py로 국한되고, serialize_decomp_slots은 다른 모듈에서 계속 사용 가능하다.

선택지 B의 전용 직렬화 블록 설계 방향:

```
## 질의 정규화 요약

의도: {intent.primary}
대상 지표:
  - 연체율 [RATIO] — 산출: 연체대출잔액 합계 / 총대출잔액 합계
필터 조건:
  - 대출상태: EQUALS ["연체"] [PRE_AGG]
  - 기간: RANGE [PRE_AGG] (time 슬롯에서 변환)
그룹핑: [지점]
결과 가공: RANK DESC limit=10, by=연체율
```

이 형식은 null/빈 배열 노이즈를 제거하고, measure_type/note/position/direction/by를 모두 포함한다.

### 3. few-shot 예시 재설계 필요 여부와 방향

**재설계 필수. 현행 예시 6개를 7개로 재편하되, 체크 구조 변경을 완전히 반영해야 한다.**

우선순위별 작업:

1. **모든 예시의 checks 키 업데이트**: measure_reflected, order_limit_reflected 제거. 새 키 구성으로 교체.
2. **RATIO 질의 예시 추가**: 연체율, NIM 등 measure_type=RATIO 케이스에서 체크 5(논리적 정합성) 서브항목 ③이 올바르게 판정하는 예시.
3. **DELTA/CUMULATIVE 예시 추가 또는 기존 교체**: modifier 결과 가공이 SQL에 반영된 케이스(서브윈도우 함수, CTE 등).
4. **직렬화 형식 통일**: 예시의 CONTEXT 섹션 질의 분해 블록을 선택지 B의 새 텍스트 형식으로 교체.
5. **예시 4(0건 PASS)와 예시 3(dead_end 반복 FAIL)은 내용 유지, 형식만 갱신**: 이 두 케이스는 커버리지 가치가 높고 내용이 올바르다.

예시 6(코드값 오류 FAIL)은 새 체크 구조에서 체크 1(filter 반영)과 체크 5(논리적 정합성)의 역할 분담이 명확해지므로, 두 체크 간 판정 방식을 보여주는 교육적 예시로 유지할 가치가 있다.

커버리지 매트릭스 (prompt-rules.md §9.3 기준):

| 예시 | 질의 유형 | verdict | 핵심 판정 포인트 |
|------|-----------|---------|-----------------|
| 1 | AGGREGATE | PASS | 정상 통과 레퍼런스 |
| 2 | RANK | FAIL/local_fix | DB 타입 오류 |
| 3 | EXTRACT | FAIL/structural | dead_end 반복 |
| 4 | AGGREGATE | PASS | 0건 정상 판정 |
| 5 | RANK | PASS | 날짜함수 복잡 케이스 |
| 6 | AGGREGATE | FAIL/local_fix | 코드값 오류 |
| 7 (신규) | RATIO | PASS | RATIO 지표 정합성 |

### 4. Qwen3.5 배포 시 추가로 고려해야 할 프롬프트 최적화 포인트

**① JSON 출력 안정성 강화**

Qwen3.5는 thinking 모드 활성화 시 `<think>...</think>` 블록 이후에 JSON을 출력한다. sql_validator는 현행 `extract_json()` 유틸리티로 처리하고 있으므로 thinking 블록 파싱은 해결되어 있다. 그러나 Qwen의 thinking 모드에서는 `"pass": true` 대신 `"pass": "true"` (문자열) 또는 `"pass": 1` (정수) 형태로 출력하는 케이스가 간헐적으로 발생한다. OUTPUT_CONTRACT에 "pass 필드는 반드시 JSON boolean(true/false)으로 출력한다. 문자열 '\"true\"'나 숫자 1은 오류다"를 명시해야 한다.

**② 한국어/영어 혼재 필드 처리**

현행 detail 필드는 한국어로 작성하도록 암묵적으로 기대하고 있으나(예시가 한국어), Qwen3.5는 영어로 학습된 비중이 높아 영어 출력으로 전환될 수 있다. fix_instruction은 SQL 생성자에게 전달되므로 언어 지정이 중요하다. OUTPUT_CONTRACT에 "detail과 fix_instruction은 한국어로 작성한다"를 명시한다.

**③ thinking 모드 활성화 여부 결정**

sql_validator는 현행 prompt-rules.md §8의 thinking ON 노드 목록에 포함되지 않는다("분석 판정형"으로 분류). Qwen3.5에서 thinking 모드를 validator에 활성화하면 추론 비용이 증가하지만, 체크 5(논리적 정합성) 서브항목 7개를 순서대로 판단해야 하는 복잡도를 고려하면 thinking ON이 판정 정확도를 높일 수 있다. 특히 0건 판정, RATIO 지표 판정, AI 추론 교차검증처럼 문맥 이해가 필요한 케이스에서 효과적이다. 배포 시 성능 트레이드오프를 테스트하여 결정할 것을 권고한다.

**④ 체크 간 상호 참조 명시**

현행 프롬프트에서 체크 5(미확인 값)와 체크 7(논리적 정합성) 간의 역할 분담이 언급되어 있으나("이 체크에서는 pass=true이며, 체크 7에서 pass=false"), 체크 번호 변경 후에는 이 교차 참조 텍스트도 새 번호로 업데이트해야 한다. 누락 시 LLM이 "체크 5 pass=true이므로 체크 7에서 다시 판정할 필요 없다"고 오판하는 케이스가 발생한다.

**⑤ [TASK] 재강조 항목 갱신**

현행 [TASK]는 EXECUTED 상태, 코드값 검증, AI 추론 교차검증 3가지를 재강조한다. 체크 구조 변경 후에는 추가로 "체크 5 논리적 정합성에서 지표 산출 방식과 결과 가공을 반드시 확인하라"를 재강조 항목에 포함해야 한다. [TASK]의 재강조 항목이 실제 판정 실패 케이스를 예방하는 최후 방어선 역할을 한다는 원칙(prompt-rules.md §1.1)을 준수한다.
