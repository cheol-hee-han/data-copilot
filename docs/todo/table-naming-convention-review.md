## 배경

정보계 DB의 테이블명에는 은행 내부 명명규칙이 존재한다.
현재 LLM이 이 규칙을 이해하지 못한 채로 테이블을 탐색/선택하고 있다.
Planner 또는 Explorer 프롬프트에 규칙을 알려주면 정확도가 올라갈지 검토.

## 관찰된 명명 패턴

trace_session-1774565791726 기준:

```
TB_ADW_DEP201P  → DEP수신계좌잔액(T+0)
TB_ADW_COM001M  → COM부점정보기본
TB_ADW_DEP219M  → DEP휴면예금
TB_ADW_DEP212L  → DEP예금세금정보
TB_ADW_DEP213L  → DEP예금이자지급내역
TB_ADW_DEA208M  → (예금계좌정보)
```

추론된 규칙:

| 위치 | 의미 | 예시 |
|---|---|---|
| `TB_` | 테이블 접두사 | 고정 |
| `ADW_` | 정보계(DW) | 고정 |
| `DEP`/`COM`/`DEA` | 도메인 코드 | DEP=예금, COM=공통 |
| `201`/`219` | 일련번호 | 도메인 내 고유 |
| `P`/`M`/`L` | 유형 접미사 | P=원장, M=마스터, L=이력 |

## 검토 결과: 현재 불필요

### 1. alt_name이 이미 동일한 정보를 제공

ES 메타 검색 결과에 `alt_name`이 포함되어 있고, LLM은 이를 통해 테이블 용도를 판단한다.

- "DEP휴면예금" → "예금신규"와 무관함을 바로 판단
- "DEP예금이자지급내역" → 이자 관련이라 제외

접미사 `M`/`L`을 알려주는 것보다 한국어 설명이 훨씬 직접적이다.

### 2. 배치 해석으로 교차 참조가 가능해짐

context_explorer의 배치 해석 구조(v3.0)에서는 모든 테이블의 메타 + alt_name + 날짜 분포 + 샘플 데이터를 한 번에 보고 selected/rejected를 판정한다.
명명규칙 없이도 교차 참조로 충분히 걸러진다.

### 3. 은행마다 명명규칙이 다르다

이 규칙은 현재 은행의 것이며, 폐쇄망 배포 시 다른 은행은 다른 규칙을 사용할 수 있다.
프롬프트에 하드코딩하면 범용성이 떨어진다.

### 4. 규칙이 불완전할 수 있다

`TB_ADW_DEA208M`은 DEP가 아니라 DEA 도메인코드를 사용한다.
이런 예외가 있으면 LLM이 규칙을 과신하여 오히려 적합한 테이블을 제외할 위험이 있다.
alt_name 기반 판단이 더 안전하다.

### 5. 소형 모델에서 규칙 과부하 위험

폐쇄망 소형 모델(7B~70B)은 프롬프트에 규칙이 많을수록 무시하거나 잘못 적용할 확률이 높아진다.
핵심 판단 기준(메타 설명, 컬럼 구조, 날짜 분포)에 집중하는 것이 낫다.

## 재검토 조건

다음 상황이 발생하면 명명규칙 추가를 재검토한다:

- alt_name이 비어있거나 부실한 테이블이 전체의 30% 이상인 경우
- 배치 해석에서 명명규칙을 알았으면 피할 수 있었던 오판이 반복되는 경우
- 특정 은행에 맞춤 배포 시 도메인 사전에 명명규칙을 포함하는 것이 합리적인 경우
