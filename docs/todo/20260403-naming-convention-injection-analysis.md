# 테이블/컬럼 명명규칙 프롬프트 주입 방안 — 비판적 설계 분석

> **Version 1.0** (2026-04-03)
> 이 문서는 설계 분석 전용이며, 구현 코드를 포함하지 않는다.

---

## 0. 분석 대상

**제안된 방안**: 4개 LLM 노드(knowledge_interpreter, sql_generator, sql_validator, recovery_agent)의 시스템 프롬프트에 테이블/컬럼 명명규칙 참조표를 주입하여, LLM이 테이블 유형코드(M/S/P/L/H/G)와 컬럼 도메인 접미사(_AMT, _RT, _DT 등)를 인지하고 활용하게 한다.

**명명규칙 요약**:
- 테이블: `TB_ADW_<주제영역3~4자리><일련번호2~3자리><유형1자리>`
- 유형코드: M(마스터), S(집계), P(스냅샷), L(내역), H(이력), G(로그)
- 컬럼 접미사: _AMT(금액), _RT(율), _DT(일자), _YM(년월), _CD(코드), _NM(명칭), _YN(여부), _CN(건수) 등

---

## 1. 어떤 노드에 넣어야 효과적인가?

### 결론: 4개 모두에 넣는 것은 비효율적이다

| 노드 | 명명규칙 필요성 | 이유 |
|------|:---:|------|
| knowledge_interpreter | **높음** | 후보 테이블 적합성 판정 시 유형코드(S vs L)가 핵심 판단 근거 |
| sql_generator | **중간** | 이미 SELECTED 테이블만 받으므로 유형 선택은 끝났지만, S 테이블에 이중 집계 방지 등 SQL 작성 시 참고 필요 |
| sql_validator | **낮음** | 검증 대상 SQL이 이미 생성된 상태. 유형 기반 경고는 rule-based로 처리 가능 |
| recovery_agent | **낮음** | 재계획 시 도구 실행 계획을 수립할 뿐, 테이블 직접 판정은 하지 않음 |

**핵심 판단**: 명명규칙이 가장 큰 가치를 발휘하는 순간은 **테이블 선택**(knowledge_interpreter)과 **SQL 작성**(sql_generator) 단계이다. sql_validator와 recovery_agent에는 넣을 필요가 없으며, 넣더라도 이미 잘못 선택된 테이블을 이 단계에서 바로잡기는 구조적으로 어렵다.

## 2. 토큰 효율성 문제

### 현재 프롬프트 크기 (추정)

| 프롬프트 | 정적 템플릿 | 동적 변수 주입 | 합산 추정 |
|----------|:-----------:|:-----------:|:---------:|
| knowledge_interpreter_system.txt | ~350줄 | tool_results, table_observations | 3,000~6,000 토큰 |
| sql_generator_system.txt | ~185줄 | tables, confirmed_terms, reference_sqls | 2,500~5,000 토큰 |

명명규칙 참조표(6가지 유형 설명 + 8가지 접미사 + 사용 지침)를 추가하면 **약 300~500 토큰** 증가한다.

### 리스크 평가

- **Claude API**: 200k context window에서 300~500 토큰 추가는 무시할 수준. **문제 없음**.
- **Solar Pro 2 70B (폐쇄망)**: context window가 32k~64k 수준으로 추정되며, 동적 변수(후보 테이블 5개 이상 + 유사 SQL 3건 이상)가 주입되면 이미 빠듯할 수 있다. 300~500 토큰이 결정적이지는 않지만, **누적 효과를 경계**해야 한다.
- **진짜 문제는 토큰 수가 아니라 attention 희석**: 이미 긴 프롬프트에 참조 규칙을 추가하면, 모델이 실제로 해당 규칙을 주의 깊게 참조하는지 보장할 수 없다. 특히 70B 모델에서 이 현상이 두드러진다.

## 3. 정보 과부하 vs 정보 부재

### LLM이 명명규칙을 실제로 활용하는가?

**비관적 시나리오 (Solar Pro 2 70B)**:

1. **긴 프롬프트의 중간 정보 무시 현상** (lost-in-the-middle): 명명규칙이 프롬프트 중간에 위치하면 모델이 무시할 확률이 높다.
2. **규칙 적용의 복잡성**: "이 테이블은 마지막 글자가 S이므로 이미 집계된 데이터이다" 라는 2단계 추론(패턴 인식 + 의미 추론)을 70B 모델이 안정적으로 수행하기 어렵다.
3. **few-shot 부재**: 참조표만 주입하고 적용 예시가 없으면 모델이 규칙을 "이해"했다고 보기 어렵다.

**낙관적 시나리오 (Claude / Qwen3.5 397B)**:

1. 충분한 context window와 추론 능력으로 명명규칙을 참조할 수 있다.
2. 단, 참조표가 프롬프트 상단 또는 직전 컨텍스트에 위치해야 효과적이다.

**평가**: 모든 모델에서 "프롬프트에 넣었으니 당연히 쓸 것"이라는 가정은 위험하다. 특히 폐쇄망 70B 모델에서는 **프롬프트 주입만으로는 신뢰할 수 없다**.

## 4. 정적 vs 동적 주입

### 모든 질의에 항상 넣을 것인가?

**분석**: "이번 달 여신 실행 건수"처럼 후보 테이블이 1개뿐인 단순 질의에도 유형코드 참조표를 주입하는 것은 낭비이다.

**동적 주입이 효과적인 조건**:

1. **후보 테이블이 2개 이상**이고 동일 주제영역에서 유형만 다른 테이블이 존재할 때 (예: TB_ADW_LON01L vs TB_ADW_LON01S)
2. **집계 질의**에서 S/P 유형 테이블이 후보에 포함될 때 (이중 집계 위험)
3. **날짜 조건이 있는 질의**에서 P/G 유형 테이블이 후보에 포함될 때

**판단**: 후보 테이블의 유형코드를 rule-based로 파싱한 후, 위 조건에 해당할 때만 관련 주의사항을 프롬프트에 동적 삽입하는 것이 효율적이다.

## 5. 프롬프트 주입 vs Rule-based 전처리 — 핵심 논점

### 테이블 유형코드는 정규표현식으로 100% 파싱 가능하다

```
TB_ADW_<주제영역><일련번호><유형>
                              ^-- 마지막 1자리: M/S/P/L/H/G
```

`CandidateTable.table_name`이 이미 State에 존재하므로, Python 코드에서 `table_name[-1]`로 유형을 추출하고 의미를 부여할 수 있다.

### 비교 분석

| 관점 | 프롬프트 주입 | Rule-based 전처리 |
|------|------------|-----------------|
| **정확성** | LLM이 패턴을 잘못 해석할 수 있음 | 정규표현식 파싱은 100% 정확 |
| **일관성** | 모델/온도에 따라 결과 변동 | 결정론적, 항상 동일 결과 |
| **폐쇄망 호환** | 70B 모델 성능에 의존 | 모델 무관 |
| **유지보수** | 프롬프트 파일 수정 | Python 코드 수정 |
| **확장성** | 규칙 추가 시 토큰 증가 | 코드 추가만 |
| **디버깅** | LLM 내부 판단이라 추적 어려움 | 로그로 추적 가능 |

**판단**: 유형코드 파싱은 LLM에 위임할 이유가 없다. **Rule-based가 모든 면에서 우월**하다.

## 6. Granularity 문제의 본질 — "S 테이블 + AVG = silent failure"

### 사례 재현

질의: "지점별 평균 여신 잔액"
- TB_ADW_LON01**S** (월별 지점별 SUM 집계 테이블)
- TB_ADW_LON01**L** (건별 내역 테이블)

LLM이 S 테이블을 선택하고 `AVG(BAL_AMT)`를 적용하면:
- 이미 SUM된 값에 AVG를 적용하게 됨 → **숫자는 나오지만 의미가 틀림**
- DB 에러도 나지 않고, 행수도 정상 → **sql_validator가 PASS를 줌**
- 결과: **silent failure** (조용한 오류)

### 프롬프트 주입만으로 방어 가능한가?

**불가능하다.** 이유:

1. **방어 시점이 잘못됨**: S 테이블이 이미 SELECTED된 상태에서 sql_generator가 AVG를 쓰지 않도록 막아야 하는데, 이는 "S 테이블의 원래 집계 방식"을 알아야 가능하다. 명명규칙만으로는 "이 S 테이블이 SUM인지 COUNT인지"를 알 수 없다.

2. **sql_validator도 잡지 못함**: 의미 검증(L2b)은 "질의 의도 vs SQL 로직" 비교인데, S 테이블의 컬럼이 이미 집계된 값이라는 정보가 없으면 "AVG(BAL_AMT)"가 논리적으로 틀렸다고 판단할 수 없다.

3. **검증은 사후적이고, 방어는 사전적이어야 함**: 이 문제는 **테이블 선택 단계에서 유형 기반 경고를 rule-based로 주입**해야 방어 가능하다.

### 진짜 방어 메커니즘

```
IF 질의에 AVG/평균 포함 AND 후보에 S 테이블 존재:
  → CandidateTable에 warning 필드 추가:
    "이 테이블은 S(집계) 유형입니다. 이미 SUM/COUNT된 데이터이므로
     AVG 집계 시 이중 집계 위험이 있습니다. L(내역) 테이블을 우선 검토하세요."
  → knowledge_interpreter 프롬프트의 table_observations에 경고로 주입
```

이렇게 하면 경고가 **해당 테이블의 관찰 데이터 바로 옆에** 위치하므로, LLM이 lost-in-the-middle 문제 없이 참조할 수 있다.

## 7. 유지보수 — 단일 소스 원칙

### 문제

명명규칙을 4개 프롬프트에 복사하면:
- 유형 추가/변경 시 4곳 수정 필요
- 하나라도 누락하면 노드 간 판단 불일치 발생
- 프롬프트 파일은 `.txt`이므로 import/상수 공유 불가

### 해결 방향

프롬프트에 넣지 않고 **Python 코드에서 단일 정의**하면 문제 자체가 사라진다.

```python
# src/agents/constants/naming_rules.py (단일 소스)
TABLE_TYPE_MAP = {
    "M": {"label": "마스터", "hint": "현재 시점 기준정보"},
    "S": {"label": "집계", "hint": "기간 단위 SUM/AVG 완료 데이터, 이중 집계 주의"},
    "P": {"label": "스냅샷", "hint": "시점별 전체 상태 캡처, 날짜 필터 필수"},
    "L": {"label": "내역", "hint": "건별 이벤트 기록, COUNT/SUM 원천"},
    "H": {"label": "이력", "hint": "상태 변경 추적"},
    "G": {"label": "로그", "hint": "대용량, 날짜+LIMIT 필수"},
}
```

이 상수를 reasoning_preparer, knowledge_interpreter의 Python 코드에서 참조하여 State에 enrichment하는 방식.

## 8. 최적 설계안 — Hybrid (Rule-based 주도 + 조건부 프롬프트 보강)

### 설계 원칙

1. **파싱과 분류는 rule-based** (정규표현식, 결정론적)
2. **판단과 선택에 필요한 맥락은 프롬프트에 동적 주입** (LLM이 잘하는 영역)
3. **경고는 해당 테이블의 관찰 데이터 옆에 인라인 배치** (lost-in-the-middle 방지)

### 구현 위치별 역할

```
reasoning_preparer (rule-based)
├── CandidateTable에 table_type_code 필드 추가 (파싱)
├── table_type_label 필드 추가 ("S(집계)", "L(내역)" 등)
└── 질의 집계방식 vs 테이블 유형 충돌 시 warning 생성

knowledge_interpreter (프롬프트 동적 주입)
├── _build_table_block()에서 table_type_label 표시
│   예: "### TB_ADW_LON01S (여신잔액 월별집계) [유형: S(집계)]"
├── 유형 충돌 경고가 있으면 테이블 블록에 경고 삽입
│   예: "** 주의: 이 테이블은 집계 유형(S)입니다. 
│        질의의 AVG 집계와 충돌할 수 있습니다."
└── 유사 유형 테이블 비교 시 유형 차이를 명시적으로 제시

sql_generator (프롬프트 동적 주입, 조건부)
├── SELECTED 테이블이 S/P 유형일 때만 주의사항 1줄 삽입
│   예: "** 주의: TB_ADW_LON01S는 S(집계) 유형입니다.
│        이미 기간별 SUM된 데이터이므로 추가 SUM/AVG 시 의미를 확인하세요."
└── 컬럼 접미사 해설은 넣지 않음 (이미 alt_name으로 충분)

sql_validator (rule-based 체크 추가)
├── S 유형 테이블 + AVG/SUM 집계 조합 감지 → 경고 플래그
└── G 유형 테이블 + 날짜 조건 없음 감지 → 경고 플래그
```

### 구체적 State 변경

```python
class CandidateTable(BaseModel):
    # ... 기존 필드 ...
    
    # 신규: rule-based 파싱 결과
    table_type_code: str = ""       # "M", "S", "P", "L", "H", "G"
    table_type_label: str = ""      # "마스터", "집계", "스냅샷" 등
    table_type_warning: str = ""    # 질의 컨텍스트 기반 경고 (조건부)
```

### 파이프라인 흐름

```
[reasoning_preparer] ──rule-based──→ table_type_code/label/warning 파싱 및 설정
        │
        ▼
[knowledge_fetcher] ──도구 실행──→ 후보 테이블 수집 (기존과 동일)
        │
        ▼
[knowledge_interpreter] ──LLM──→ 테이블 블록에 유형 라벨+경고 포함
        │                         (프롬프트 동적 주입)
        │                         "S(집계) 유형" 정보가 판정 근거로 활용됨
        ▼
[sql_generator] ──LLM──→ SELECTED 테이블의 유형 경고 조건부 주입
        │
        ▼
[sql_validator] ──rule-based──→ 유형-집계 충돌 체크 (LLM 무관)
```

### 이 설계가 "S 테이블 + AVG" 문제를 어떻게 방어하는가

1. **reasoning_preparer**: TB_ADW_LON01S의 유형코드 `S`를 파싱, 질의에 "평균" 키워드가 있으므로 `table_type_warning = "S(집계) 유형: 이미 SUM된 데이터, AVG 시 이중 집계 위험"` 설정

2. **knowledge_interpreter**: 테이블 관찰 블록에 경고가 함께 표시됨 → LLM이 S 테이블 대신 L 테이블을 SELECTED할 확률 증가. 또는 S만 있어도 warning이 selection_reason에 기록됨

3. **sql_generator**: SELECTED된 테이블이 여전히 S 유형이면, "이미 집계된 데이터" 주의사항이 프롬프트에 삽입됨

4. **sql_validator**: rule-based 체크로 S 유형 + AVG 조합을 감지하여 `logical_consistency.pass = false` 판정. 이 단계는 LLM에 의존하지 않으므로 확실한 안전망

### 이 설계가 컬럼 접미사를 어떻게 처리하는가

컬럼 접미사(_AMT, _RT, _DT 등)는 **프롬프트에 주입하지 않는다**. 이유:

1. 이미 `ColumnInfo.alt_name`에 한글 설명이 있음 (예: "잔액금액")
2. ES 메타에서 `col_type`도 제공됨 (예: "DECIMAL", "DATE")
3. 접미사 규칙은 alt_name이 없는 경우의 **폴백 추론**에만 유용
4. 폴백이 필요한 경우에도 rule-based로 `_AMT → 금액 컬럼 추정` 태그를 CandidateTable.columns에 추가하는 것이 더 확실

## 9. 요약 판정표

| 검토 관점 | 프롬프트 전체 주입 | Hybrid (권장) |
|-----------|:--:|:--:|
| 유형코드 파싱 정확성 | LLM 의존 (불안정) | rule-based (100%) |
| 토큰 효율성 | 항상 주입 (낭비) | 조건부 주입 (효율) |
| 폐쇄망 70B 호환 | 추론 능력에 의존 | 핵심은 rule-based |
| silent failure 방어 | 불확실 | rule-based 안전망 |
| 유지보수 | 4곳 복사 (위험) | 단일 소스 (안전) |
| 디버깅 | LLM 블랙박스 | 로그 추적 가능 |
| 구현 복잡도 | 낮음 (프롬프트 수정) | 중간 (코드 + 프롬프트) |

## 10. 결론

**프롬프트에 명명규칙 참조표를 직접 넣는 방안은 채택하지 않는 것을 권고한다.**

핵심 이유:
1. 테이블 유형코드는 정규표현식으로 100% 파싱 가능한 구조화된 정보이다. LLM에 위임하면 불필요한 불확실성이 추가된다.
2. 가장 위험한 문제(S 테이블 이중 집계)는 프롬프트 주입만으로 방어할 수 없다. rule-based 안전망이 필수이다.
3. 폐쇄망 70B 모델에서 프롬프트에 추가된 규칙이 실제로 활용된다는 보장이 없다.

대신 **Hybrid 방식** (Section 8)을 권고한다:
- reasoning_preparer에서 rule-based로 유형코드를 파싱하고 경고를 생성
- knowledge_interpreter와 sql_generator 프롬프트에는 파싱된 결과를 **테이블별 인라인 주석**으로 동적 주입
- sql_validator에서 유형-집계 충돌을 rule-based로 검증

이 방식은 **결정론적 정확성 + LLM의 맥락 활용 능력**을 결합하며, 모델 성능에 관계없이 핵심 안전장치가 동작한다.
