# Validator 프롬프트 정제 — 과도한 상세화 제거

**작성일**: 2026-04-13
**대상 파일**: `resources/prompts/reason/sql_validator_system.txt`
**타겟 LLM**: Qwen3.5 397B (MoE, 활성 파라미터 ~17B)

## 배경

validator 프롬프트의 체크 규칙에서 SQL 구현 패턴을 괄호 안에 열거하는 구조가
false FAIL의 근본 원인으로 식별되었다.

**핵심 문제**: 패턴 목록은 완성이 불가능하고, 목록에 없는 정당한 SQL 구현이
FAIL 후보가 된다. 특히 폐쇄망 타겟(Sybase IQ, Impala)은 PostgreSQL과
문법이 달라 목록 누락 위험이 크다.

**해결 원칙**: 397B 모델의 의미 판단 능력을 신뢰하여, 패턴 열거를 원칙 서술로 교체한다.

## 적용해야 할 수정 (위험도 순)

### HIGH

#### 1. 체크 3 — RANK 패턴 열거 삭제

**현재:**
```
RANK: 상위/하위 N건 추출 구조가 존재하는가 (ORDER BY + LIMIT, 또는 RANK()/ROW_NUMBER() 윈도우 함수 + 필터 등). 방향과 건수가 올바른가
```

**수정:**
```
RANK: 상위/하위 N건을 추출할 수 있는 구조가 존재하는가? 방향과 건수가 올바른가?
```

**이유:** Sybase IQ의 `TOP N`, Impala의 `QUALIFY`, `DENSE_RANK()` 등이 목록에 없어
정당한 SQL이 FAIL 판정되는 가장 높은 위험. 원칙 한 문장이면 어떤 구현이든 판단 가능.

- [x] 적용 완료

---

#### 2. 체크 5 + 체크 6⑦ — dead_end 이중 판정 경계 명확화

**현재:** 동일한 dead_end 반복을 체크 5와 체크 6⑦에서 각각 pass=false 판정

**수정 (체크 6⑦ 0건 pass=false 조건):**
- dead_end 조건 제거, "체크 5에서 판정. 이 관점에서 중복 판정하지 않는다" 추가

**이유:** 이중 FAIL → Qwen이 체크 6 나머지 관점 ①~⑥을 건너뛰는 단락 처리 위험

- [x] 적용 완료

### MEDIUM

#### 3. 체크 1 — PRE_AGG/POST_AGG 괄호 열거 삭제

**현재:**
```
PRE_AGG 필터: 집계 전 단계에서 적용되어야 한다 (WHERE 절, 서브쿼리/CTE 내부 WHERE, JOIN ON 조건 등)
POST_AGG 필터: 집계 후 단계에서 적용되어야 한다 (HAVING 절, 또는 집계 서브쿼리 바깥의 WHERE 등)
```

**수정:**
```
PRE_AGG 필터: 집계 연산이 적용되기 전 행 필터링 단계에서 조건이 반영되어야 한다
POST_AGG 필터: 집계 결과를 필터링하는 단계에서 조건이 반영되어야 한다
```

**이유:** Sybase IQ/Impala의 `QUALIFY` 등이 POST_AGG 목록에 없음.
원칙문("핵심은 필터가 적절한 단계에서 적용되었는가")이 바로 아래에 있으면서
위에서 위치를 열거하는 모순 해소.

- [x] 적용 완료

---

#### 4. 체크 6① — 날짜 함수 해석 표 삭제

**현재:**
```
- "이번 달 1일" 이상 조건 → "이번 달" 필터
- "올해 1월 1일" 이상 조건 → "올해" 필터
- "작년 1월 1일" ~ "올해 1월 1일 미만" → "작년" 필터
- "올해 시작일 - 1일" → 작년 12월 31일
- "현재일 - N일" → 최근 N일 필터
```

**수정:** 표 전체 삭제, 다음 한 문장으로 대체:
```
날짜 함수 조합이 복잡해 보여도 실제 계산 결과의 의미를 먼저 구하고 사용자 기간 의도와 비교한다.
DB dialect에 따라 함수명/문법은 다를 수 있다.
```

**이유:**
- HALLUCINATION_GUARD의 날짜 오판 방지 항목과 역할 중복
- PostgreSQL 중심 표가 Sybase IQ/Impala에서 false FAIL 유발 가능
- 체크 6 총 길이 감소 → MoE 모델 attention 분산 완화

- [x] 적용 완료

---

#### 5. 체크 6② — 순위/추이/비교 패턴 열거 삭제

**현재:**
```
- 순위 질의(RANK): ... (ORDER BY + LIMIT, RANK()/ROW_NUMBER() 윈도우 함수, 서브쿼리 등)
- 추이 질의(TREND): ... (날짜 축 GROUP BY, 이미 기간별로 집계된 테이블의 직접 조회, LAG/LEAD, 기간별 서브쿼리 등)
- 비교 질의(COMPARE): ... (CASE WHEN, 셀프 조인, UNION, 서브쿼리 대조 등)
```

**수정:**
```
- 순위 질의(RANK): 상위/하위 N건을 추출할 수 있는 구조가 있는가?
- 추이 질의(TREND): 시간 흐름을 비교할 수 있는 구조가 있는가?
- 비교 질의(COMPARE): 두 집합을 비교할 수 있는 구조가 있는가?
```

**이유:** 체크 3과 패턴 목록 불일치(DENSE_RANK 등) 방지.
"주의: SQL 구현 방식은 다양하다..." 문단은 반드시 유지.

- [x] 적용 완료

```
정규화 요약(체크 1~3)은 정규화 결과의 일부이며 불완전할 수 있다.
```

```
체크 1~3은 정규화 요약 항목의 반영 여부만 확인한다.
이 체크 6은 원문 질의({original_query})를 직접 읽어 정규화가 놓쳤을 수 있는 의도까지 검증한다.
두 체크가 같은 항목을 다룰 수 있으나 관점이 다르므로 독립적으로 판정한다.
```

## 건드리지 말아야 할 목록

| 항목 | 이유 |
|------|------|
| 체크 2 GROUP 역할 열거 (DISTINCT, 이미 집계된 테이블) | 이 열거는 false FAIL을 **방지**하는 방향. GROUP BY 없는 정당한 구현을 보호함 |
| 체크 4 판정 분리 (존재 vs 의미) | 동일 이슈의 이중 FAIL 방지 핵심 규칙. 예시 6에서 시연됨 |
| 체크 7 세 분기 구조 (PASS/EXECUTED/ERROR) | EXECUTED=성공이 직관에 반하므로 상세 설명 필수 |
| 체크 8 코드성 컬럼 판단 기준 (_CD, _DCD 등) | 기준 없으면 모델이 코드성 컬럼 범위를 자의적 해석 |
| failure_classification 분기 전체 | 다운스트림 recovery_agent 복구 전략 선택 신호. 열거 필수 |
| HALLUCINATION_GUARD 4개 항목 전체 | 각각 방어하는 체크와 오판 유형이 달라 모두 필요 |

| 예시 6 (코드값 의미 불일치) | 체크 4와 체크 6 판정 분리의 시연 |

### Qwen3.5 MoE 특성

Qwen3.5 397B는 MoE 아키텍처로 활성 파라미터가 ~17B.
프롬프트 총 길이가 길수록 attention 분산으로 중간 영역 규칙 무시 위험(Lost-in-the-Middle).
체크 6이 가장 긴 섹션이므로 불필요한 상세 규칙 제거가 MoE 대응에도 유효.
