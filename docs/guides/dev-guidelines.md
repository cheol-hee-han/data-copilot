# 개발 지침 (상세)

> CLAUDE.md에는 핵심 3줄만 유지하고, 상세 원칙은 이 문서에 보관한다.
> 이 파일은 자동 로드되지 않으며, 필요 시 참조한다.

## 1. 설계 원칙
- 코드는 우선 단순하고 명확하게 작성한다.
- 디자인 패턴은 실제로 변경 가능성, 확장 필요성, 책임 분리가 필요한 경우에만 적용한다.
- 패턴 적용 자체를 목표로 하지 않는다.
- 과도한 추상화, 불필요한 계층 분리, 과한 인터페이스 도입은 피한다.
- 현재 요구사항을 충족하면서도, 향후 변경에 무리가 없도록 균형 있게 설계한다.

## 2. 책임 분리
- 각 클래스, 함수, 모듈은 하나의 명확한 책임만 가지도록 작성한다.
- 서로 다른 책임이 한 곳에 섞이지 않도록 분리한다.
- 비즈니스 로직, 데이터 접근, 입출력 처리, 상태 관리는 역할에 맞는 계층에 배치한다.
- 공통 로직은 중복 구현하지 말고 재사용 가능한 단위로 분리한다.

## 3. 의존성 관리
- 구현체보다 추상화된 인터페이스나 명확한 계약에 의존하도록 설계한다.
- 모듈 간 결합도를 낮추고, 내부 응집도는 높게 유지한다.
- 하위 계층의 세부 구현이 상위 계층 전체에 영향을 주지 않도록 한다.
- 의존성 방향이 뒤섞이지 않도록 계층 구조를 일관되게 유지한다.

## 4. 재사용성과 모듈화
- 동일하거나 유사한 기능은 공통 모듈로 추출해 재사용 가능하게 구현한다.
- 다만, 재사용 이점이 불분명하면 무리하게 공통화하지 않는다.
- 공통화로 인해 코드 흐름이 더 복잡해지면 분리를 재검토한다.
- 모듈은 독립적으로 이해 가능하고 테스트 가능해야 한다.

## 5. 가독성
- 코드만 읽어도 의도가 이해되도록 작성한다.
- 변수명, 함수명, 클래스명은 역할과 목적이 드러나게 작성한다.
- 한 함수는 한 가지 작업만 수행하도록 유지한다.
- 조건문과 중첩은 가능한 단순하게 유지한다.
- 불필요한 축약, 숨겨진 동작, 과도한 트릭성 구현은 피한다.

## 6. 유지보수성
- 변경이 자주 일어날 가능성이 있는 부분은 분리하고, 고정된 부분과 섞지 않는다.
- 수정 시 영향 범위가 최소화되도록 설계한다.
- 예외 처리, 경계 조건, 실패 케이스를 명확히 다룬다.
- 테스트하기 쉬운 구조로 작성한다.
- 기존 구조와 스타일을 존중하며 일관성을 유지한다.

## 7. 계층과 라이프사이클
- 컴포넌트는 실행 위치와 생명주기에 맞는 계층에 배치한다.
- 상태가 필요한 객체와 Stateless 객체를 구분하여 설계한다.
- 초기화, 생성, 해제 시점이 중요한 자원은 라이프사이클을 고려해 안전하게 관리한다.
- UI, 애플리케이션 서비스, 도메인 로직, 인프라 로직이 섞이지 않도록 한다.

## 8. 구현 판단 기준
구현 중에는 항상 아래를 점검한다:
- 이 구조가 지금보다 더 단순해질 수 있는가
- 이 책임이 다른 계층이나 다른 객체에 있어야 하는가
- 중복되는 로직이 있는가
- 변경 시 영향 범위가 넓어지지 않는가
- 팀원이 처음 봐도 이해 가능한가
- 테스트하기 어려운 구조가 아닌가
- 패턴 적용이 실제 이점을 주는가
- 변경에 따라 죽은 코드는 없는가
- 중복 구현되는 모듈, 클래스, 함수, 변수, 객체는 없는가

## 9. 금지 사항
- 패턴을 보여주기 위해 불필요하게 복잡한 구조를 만들지 않는다.
- 작은 문제를 해결하기 위해 지나치게 많은 클래스와 인터페이스를 만들지 않는다.
- 서로 다른 책임을 하나의 클래스나 함수에 몰아넣지 않는다.
- 중복을 방치하지 않는다.
- 기존 프로젝트의 구조와 어울리지 않는 방식으로 혼자만의 스타일을 강하게 밀어 넣지 않는다.

## 10. 최종 목표
- 읽기 쉬운 코드
- 수정하기 쉬운 코드
- 테스트하기 쉬운 코드
- 중복이 적고 책임이 명확한 코드
- 요구사항 변경에 유연하게 대응 가능한 코드
