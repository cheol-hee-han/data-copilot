## 1. 바이브코딩 개요

### 1.1 바이브코딩의 정의와 핵심 철학

바이브코딩(Vibe Coding)은 **자연어 의도(Vibe)를 AI에게 전달하여 코드를 생성하고,
개발자는 방향 설정·검증·의사결정에 집중하는 개발 방법론**이다.

핵심 철학:
- **의도 중심 개발**: "어떻게(How)" 대신 "무엇을(What)" 전달
- **인간은 설계자, AI는 실행자**: 아키텍처 결정은 인간, 구현은 AI
- **빠른 반복(Rapid Iteration)**: 동작하는 최소 구현 → 점진적 고도화
- **문서가 곧 코드의 씨앗**: 잘 쓴 문서가 잘 된 구현을 만든다
- **검증은 타협 불가**: AI 출력물은 반드시 검증한다

### 1.2 전통적 개발 방식과의 차이점

| 구분                 | 전통적 개발                        | 바이브코딩                           |
|--------------------|---------------------------------|-----------------------------------|
| 코드 작성 주체        | 개발자 직접 타이핑                   | AI 생성 + 개발자 검증                 |
| 설계 전달 방식        | UML, ERD 등 정형 다이어그램          | 자연어 + 구조화된 프롬프트              |
| 반복 주기            | 수일~수주                          | 수분~수시간                          |
| 병렬 작업            | 팀원 수에 비례                      | 서브에이전트로 1인도 병렬 처리 가능       |
| 문서화 시점           | 구현 완료 후(종종 생략)              | 구현과 동시에(AI가 작성)               |
| 디버깅 방식           | 로그 분석 + 수동 추적               | AI에게 에러 컨텍스트 전달 → 수정 제안     |
| 핵심 역량            | 코딩 실력                          | 프롬프트 설계 + 검증 + 아키텍처 판단     |

### 1.3 Claude Code + 서브에이전트 협업 구조의 강점

1. **컨텍스트 분리**: 서브에이전트별로 독립된 컨텍스트 → 토큰 낭비 없음
2. **전문화**: 각 에이전트에 역할별 시스템 프롬프트 부여 → 품질 향상
3. **병렬 실행**: 독립 태스크를 동시에 처리 → 시간 단축
4. **실패 격리**: 한 에이전트 실패가 전체에 전파되지 않음
5. **파일 기반 메모리**: CLAUDE.md와 메모리 시스템으로 세션 간 연속성 확보

## 2. 프롬프트 엔지니어링 핵심 원칙

> 이 섹션의 원칙은 이후 모든 템플릿과 프롬프트에 적용된다.

### 2.1 명확하고 구체적인 지시 작성법

**원칙**: AI는 추측하지 않아야 한다. 모호함을 제거하라.

```
❌ 나쁜 예시:
"사용자 인증 기능 만들어줘"

✅ 좋은 예시:
"FastAPI 기반 JWT 인증 모듈을 작성해줘.
- 엔드포인트: POST /auth/login, POST /auth/refresh
- JWT 토큰: access(15분), refresh(7일) 만료
- 비밀번호: bcrypt 해싱
- 의존성: python-jose, passlib[bcrypt]
- 반환 형식: {"access_token": "...", "token_type": "bearer"}
- 테스트 코드도 함께 작성"
```

### 2.2 역할 부여(Role Prompting) 활용법

역할을 부여하면 AI의 응답 품질이 해당 도메인에 특화된다.

```
❌ 나쁜 예시:
"이 코드 보안 문제 있는지 봐줘"

✅ 좋은 예시:
"당신은 OWASP Top 10에 정통한 시니어 보안 엔지니어입니다.
아래 FastAPI 엔드포인트 코드에서:
1. SQL 인젝션 가능성
2. 인증/인가 우회 가능성
3. 입력값 검증 누락
을 중심으로 보안 취약점을 분석하고,
각 취약점에 대해 수정된 코드를 제시해주세요."
```

### 2.3 긍정적/부정적 예시 동시 제공 (Few-shot)

```
❌ 나쁜 예시:
"커밋 메시지 잘 써줘"

✅ 좋은 예시:
"Conventional Commits 형식으로 커밋 메시지를 작성해줘.

좋은 예시:
  feat(auth): add JWT refresh token rotation
  fix(db): resolve connection pool exhaustion under high load

나쁜 예시:
  수정함
  update code
  fix bug

위 기준으로 현재 staged 변경사항에 맞는 메시지를 작성해줘."
```

### 2.4 Chain-of-Thought(CoT) 유도

복잡한 판단이 필요할 때 단계별 사고를 요청한다.

```
✅ 좋은 예시:
"이 쿼리의 성능 문제를 분석해줘. 다음 순서로 진행해:
1. 먼저 실행 계획(EXPLAIN)을 예측해봐
2. 어떤 인덱스가 활용되고 어떤 것이 누락인지 파악해
3. 병목 구간을 식별해
4. 개선안을 우선순위로 정렬해서 제시해"
```

**언제 CoT를 쓸지:**
- 다단계 추론이 필요한 아키텍처 의사결정
- 복잡한 버그의 근본 원인 분석
- 트레이드오프 비교가 필요한 설계 선택
- 성능 최적화 분석

### 2.5 XML 태그를 활용한 구조화된 요청

Claude는 XML 태그로 구조화된 입력을 잘 이해한다.

```
✅ 좋은 예시:
<task>사용자 등록 API 엔드포인트 구현</task>

<constraints>
- 프레임워크: FastAPI
- ORM: SQLAlchemy 2.0 async
- 비밀번호: bcrypt 해싱
- 이메일: 중복 검증 필수
</constraints>

<input_schema>
{
  "email": "string (이메일 형식)",
  "password": "string (8자 이상, 영문+숫자+특수문자)",
  "name": "string (2~50자)"
}
</input_schema>

<output>
- 성공: 201 Created + 사용자 정보(비밀번호 제외)
- 실패: 409 Conflict (이메일 중복) / 422 Validation Error
</output>
```

### 2.6 출력 형식 명시

```
✅ 좋은 예시:
"분석 결과를 아래 JSON 형식으로 반환해줘:
{
  "severity": "high | medium | low",
  "findings": [
    {
      "file": "파일 경로",
      "line": 줄번호,
      "issue": "문제 설명",
      "fix": "수정 제안"
    }
  ],
  "summary": "전체 요약 1~2문장"
}"
```

### 2.7 컨텍스트 압축 요청법

긴 배경을 AI에게 효율적으로 전달하는 방법:

```
✅ 좋은 예시:
"프로젝트 배경을 요약하면:
- Python 3.12 + FastAPI + PostgreSQL 기반 데이터 분석 API
- 은행 내부 직원 전용 (인터넷 차단 환경)
- 핵심 기능: 자연어 → SQL 변환 → 실행 → 결과 포맷팅
- 현재 상태: SQL 생성 노드까지 구현 완료, 검증 노드 작업 중

이 컨텍스트에서 SQL 검증 노드를 구현해줘. 검증 항목:
1. SELECT 문만 허용
2. 시스템 테이블 접근 차단
3. 결과 행 수 제한(기본 10,000건)"
```

## 3. Claude Code 실전 사용법

### 3.1 CLAUDE.md의 역할과 최적 구성

CLAUDE.md는 **모든 대화의 시작점에 자동 주입되는 프로젝트 컨텍스트**이다.
Claude Code가 프로젝트를 이해하는 가장 중요한 파일이다.

**배치 위치와 범위:**
- 프로젝트 루트 `CLAUDE.md`: 전체 프로젝트 공통 지침
- `.claude/rules/*.md`: 도메인별 세부 규칙 (보안, UI 규칙 등)
- 서브디렉토리 `CLAUDE.md`: 해당 모듈 특화 지침

### 3.2 CLAUDE.md 작성 템플릿

```markdown
# 프로젝트명

## Project Overview
[프로젝트의 목적과 핵심 기능을 2~3문장으로]

## Tech Stack
- Language: [예: Python 3.12]
- Framework: [예: FastAPI, LangGraph]
- Database: [예: PostgreSQL]
- [기타 주요 의존성]

## Project Structure
[디렉토리 구조를 tree 형태로]

## Key Conventions
- [코딩 컨벤션 1: 예) async/await 패턴 사용]
- [코딩 컨벤션 2: 예) Pydantic v2 모델로 입출력 정의]
- [코딩 컨벤션 3: 예) 한국어 docstring + 영어 변수명]
- [테스트 컨벤션: 예) pytest + 파일명 test_*.py]

## Security Rules
- [보안 규칙 1]
- [보안 규칙 2]

## 금지 사항
- [절대 하지 말아야 할 것 1]
- [절대 하지 말아야 할 것 2]
```

### 3.3 주요 슬래시 명령어 실전 활용

| 명령어       | 용도                              | 실전 활용 타이밍                      |
|------------|----------------------------------|-----------------------------------|
| `/init`    | CLAUDE.md 자동 생성                | 새 프로젝트 시작 시 최초 1회            |
| `/memory`  | 영구 메모리에 정보 저장              | 사용자 선호, 반복 피드백 저장 시          |
| `/compact` | 대화 컨텍스트 압축                  | 토큰 소비가 70% 이상일 때              |
| `/clear`   | 대화 초기화                        | 주제가 완전히 바뀔 때                  |
| `/review`  | 코드 리뷰 요청                     | 기능 구현 완료 후                     |
| `/cost`    | 현재 세션 비용 확인                  | 주기적 비용 모니터링                   |

### 3.4 도구 허용 권한(Tool Permission) 설정 전략

```
┌─────────────────────────────────────────────────────────┐
│              권한 수준별 트레이드오프                     │
├──────────────┬──────────────────┬───────────────────────┤
│    수준      │    허용 범위      │    적합한 상황        │
├──────────────┼──────────────────┼───────────────────────┤
│ 읽기 전용    │ Read, Glob, Grep │ 코드 분석, 리뷰       │
│ 파일 편집    │ + Write, Edit    │ 일반 구현 작업        │
│ 명령 실행    │ + Bash           │ 테스트, 빌드 실행     │
│ 전체 허용    │ 모든 도구        │ 자율 모드 (신뢰도 ↑)  │
└──────────────┴──────────────────┴───────────────────────┘
```

**권장 전략:**
- 초기 탐색/분석: 읽기 전용으로 시작
- 구현 단계: 파일 편집 허용
- 테스트 실행: Bash 허용 (특정 명령만)
- 자율 모드: 충분한 신뢰가 쌓인 후, CLAUDE.md에 안전장치를 명시한 상태에서 사용

### 3.5 자율 실행 모드 vs 수동 승인 모드

**자율 모드 적합 상황:**
- CLAUDE.md에 명확한 제약 조건이 설정됨
- 테스트 코드가 충분하여 자동 검증 가능
- 반복적이고 패턴화된 작업 (예: CRUD 엔드포인트 일괄 생성)

**수동 승인 적합 상황:**
- 아키텍처 수준의 변경
- 외부 시스템 연동 (DB 마이그레이션, API 호출 등)
- 보안 민감 코드 (인증, 권한, 암호화)
- Git push, 브랜치 삭제 등 되돌리기 어려운 작업

### 3.6 비용(Token) 소비 모니터링 및 최적화

**비용 최적화 전략:**

1. **컨텍스트 사전 압축**: 긴 배경을 요약하여 전달
2. **CLAUDE.md 활용**: 반복되는 컨텍스트는 파일로 분리
3. **서브에이전트 활용**: 탐색 작업은 서브에이전트에 위임 (메인 컨텍스트 보호)
4. **적시 /compact**: 토큰 소비가 누적될 때 대화 압축
5. **세션 분리**: 독립적인 작업은 새 세션에서 시작
6. **haiku 모델 활용**: 단순 탐색이나 포맷 변환은 경량 모델로 위임

### 3.7 민감 정보 보호

## 4. 요구사항 정의

### 4.1 효과적인 요구사항 작성법

Claude가 실행 가능한 단위로 분해되려면, 요구사항이 **구체적이고 검증 가능**해야 한다.

**SMART 원칙 적용:**
- **S**(Specific): "빠르게" → "응답 시간 200ms 이내"
- **M**(Measurable): "안전하게" → "OWASP Top 10 항목 모두 대응"
- **A**(Actionable): "좋은 코드" → "mypy --strict 통과, 테스트 커버리지 80%+"
- **R**(Relevant): 프로젝트 목표에 부합
- **T**(Testable): 완료 여부를 코드로 검증 가능

### 4.2 기능 요구사항(FR) / 비기능 요구사항(NFR) 분류

| 분류   | 예시                                                |
|------|---------------------------------------------------|
| FR   | "사용자가 자연어로 질문하면 SQL을 생성하여 결과를 반환한다"  |
| FR   | "로그인한 사용자만 API에 접근할 수 있다"                  |
| NFR  | "API 응답 시간은 p95 기준 500ms 이내"                   |
| NFR  | "동시 접속 100명 처리 가능"                             |
| NFR  | "PII 데이터는 마스킹 처리"                              |

### 4.3 요구사항 오해 방지 체크리스트

- [ ] 각 요구사항에 입력/출력이 명시되어 있는가?
- [ ] "등", "기타", "필요 시"와 같은 모호한 표현이 없는가?
- [ ] 예외 상황(에러, 빈 데이터, 권한 없음)이 정의되어 있는가?
- [ ] 기술 스택 제약이 명시되어 있는가?
- [ ] 완료 기준(Done Criteria)이 검증 가능한 형태인가?
- [ ] 우선순위가 명시되어 있는가?

### 4.4 MoSCoW 우선순위와 Claude 연동

```
Must Have    : 이것 없으면 릴리즈 불가 → 가장 먼저 구현 요청
Should Have  : 중요하지만 대안 존재   → Must 완료 후 구현
Could Have   : 있으면 좋지만 없어도 됨 → 시간이 남을 때
Won't Have   : 이번 범위에서 제외     → CLAUDE.md에 "구현하지 말 것"으로 명시
```

### 4.5 요구사항 문서 템플릿


## 5. 서브에이전트 설계 및 오케스트레이션

### 5.1 오케스트레이터와 서브에이전트 역할 분리

```
┌──────────────────────────────────────────────────────────────┐
│                오케스트레이터 (메인 세션)                      │
│                                                              │
│  역할: 전체 흐름 관리, 의사결정, 결과 통합, 사용자 소통        │
│                                                              │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐         │
│  │ 태스크 분배  │→│ 결과 검증    │→│ 다음 단계    │         │
│  │              │ │              │ │ 결정         │         │
│  └──────┬───────┘ └──────▲───────┘ └──────────────┘         │
│         │                │                                   │
│         ▼                │                                   │
│  ┌──────────────────────────────────────────────────┐       │
│  │              서브에이전트 레이어                   │       │
│  │                                                    │       │
│  │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐    │       │
│  │  │탐색    │ │설계    │ │구현    │ │리뷰    │    │       │
│  │  │Explore │ │Plan    │ │general │ │code-   │    │       │
│  │  │        │ │        │ │purpose │ │reviewer│    │       │
│  │  └────────┘ └────────┘ └────────┘ └────────┘    │       │
│  │                                                    │       │
│  │  ┌────────┐ ┌────────┐ ┌────────┐                │       │
│  │  │문서화  │ │테스트  │ │보안    │                │       │
│  │  │doc-   │ │test-   │ │security│                │       │
│  │  │writer │ │generator│ │-guard │                │       │
│  │  └────────┘ └────────┘ └────────┘                │       │
│  └──────────────────────────────────────────────────┘       │
└──────────────────────────────────────────────────────────────┘
```

**핵심 원칙:**
- 오케스트레이터는 **"무엇을 할지"** 결정하고, 서브에이전트는 **"어떻게 할지"** 실행
- 서브에이전트끼리는 직접 통신 불가 → 반드시 오케스트레이터를 경유
- 한 서브에이전트의 출력을 다음 서브에이전트의 입력으로 전달하는 것은 오케스트레이터의 역할

### 5.2 전형적인 서브에이전트 유형 정의

| 에이전트 유형       | Claude Code 매핑       | 핵심 역할                      |
|------------------|----------------------|------------------------------|
| 코드 탐색·분석     | Explore              | 코드베이스 구조 파악, 파일 검색    |
| 아키텍처 설계      | Plan                 | 구현 전략 수립, 파일 식별         |
| 범용 구현          | general-purpose      | 코드 작성, 복잡한 멀티스텝 태스크  |
| 코드 리뷰          | code-reviewer        | 보안·성능·타입·에러 처리 검토     |
| 문서 작성          | doc-writer           | README, API 문서, 가이드 작성    |
| 테스트 생성        | test-generator       | 테스트 케이스 생성, 엣지 케이스    |
| 보안 검토          | security-guard       | SQL 인젝션, PII 유출 등 분석     |
| 설계 비평          | design-critic        | 가정 검증, 실패 시나리오 분석     |

### 5.3 에이전트 유형별 시스템 프롬프트 작성 원칙

**좋은 에이전트 프롬프트의 4요소:**
1. **역할(Role)**: 에이전트의 전문성과 관점
2. **목표(Goal)**: 이 에이전트가 달성해야 할 결과
3. **제약(Constraints)**: 하지 말아야 할 것, 범위 제한
4. **출력 형식(Output Format)**: 결과를 어떤 구조로 반환할지

```
✅ 서브에이전트 프롬프트 예시 (보안 리뷰):

"당신은 금융 도메인 보안 전문가입니다.

목표: src/agents/nodes/ 디렉토리의 SQL 생성 관련 코드를 검토하여
보안 취약점을 식별하고 수정안을 제시하세요.

검토 관점:
1. SQL 인젝션 가능성 (사용자 입력이 SQL에 직접 삽입되는 경로)
2. PII 컬럼 직접 노출 여부
3. SELECT 외 DML 실행 가능성
4. 시스템 카탈로그 접근 가능성

제약:
- 코드를 수정하지 말고 분석 결과만 반환
- 실제 취약점만 보고 (이론적 가능성만으로 보고하지 않음)

출력 형식:
각 취약점에 대해 파일명, 줄번호, 위험도(상/중/하),
설명, 수정 제안 코드를 포함하여 보고"
```

### 5.4 에이전트 간 컨텍스트 전달(핸드오프) 프로토콜

서브에이전트의 결과를 다음 에이전트에게 전달할 때 **구조화된 형식**을 사용한다.

```markdown
## 핸드오프 문서 형식

### 이전 에이전트: [에이전트명]
### 완료된 작업: [무엇을 했는지]
### 산출물:
- 생성/수정된 파일 목록: [파일 경로]
- 핵심 결정 사항: [왜 이렇게 했는지]
- 주의 사항: [다음 에이전트가 알아야 할 것]

### 다음 에이전트에게 요청:
[구체적인 다음 작업 지시]
```

### 5.5 병렬 vs 순차 실행 구분 기준

**병렬 실행 가능 (동시에 Agent 호출):**
- 서로 다른 파일/모듈에 대한 독립적 구현
- 코드 리뷰 + 문서 작성 (같은 코드를 읽기만 할 때)
- 여러 파일 탐색/검색
- 독립적인 테스트 케이스 생성

**순차 실행 필수:**
- 설계 → 구현 (설계 결과가 구현의 입력)
- 구현 → 테스트 (구현 코드가 있어야 테스트 작성)
- 구현 → 리뷰 (코드가 있어야 리뷰)
- 리뷰 → 수정 (리뷰 결과에 따라 수정)

### 5.6 병렬 서브에이전트 호출 패턴

Claude Code에서 병렬 호출은 **하나의 메시지에 여러 Agent 도구를 동시 호출**하여 수행한다.

```
✅ 병렬 호출 요청 예시:

"아래 3가지를 병렬로 진행해줘:
1. src/agents/nodes/sql_generator.py의 보안 리뷰
2. src/agents/nodes/query_executor.py의 성능 분석
3. docs/architecture/architecture.md 최신화

각각 적절한 서브에이전트를 사용해서 동시에 처리해줘."
```

## 6. 계획 문서(Planning Doc) 작성

### 6.1 계획 문서의 목적

계획 문서는 **Claude Code가 전체 맥락 없이도 각 태스크를 자율적으로 실행할 수 있게 하는 자율 지침서**이다. 세션이 바뀌거나 컨텍스트가 압축되어도, 계획 문서가 있으면 작업을 이어갈 수 있다.

### 6.2 좋은 계획 문서의 5가지 조건

1. **자기 완결적(Self-contained)**: 외부 참조 없이 문서만으로 작업 가능
2. **실행 가능(Actionable)**: 각 태스크가 구체적 행동으로 변환 가능
3. **검증 가능(Verifiable)**: 완료 기준이 명확하여 성공/실패 판별 가능
4. **순서 명확(Ordered)**: 의존성과 우선순위가 명시
5. **범위 제한(Bounded)**: 무엇을 하지 않을지도 명시

### 6.3 계획 문서 구성 요소

| 구성 요소      | 설명                                   |
|--------------|--------------------------------------|
| 목표          | 이 계획이 달성하려는 최종 결과              |
| 배경          | 왜 이 작업이 필요한지 (2~3문장)            |
| 제약 조건      | 기술 스택, 환경, 보안, 성능 제약            |
| 태스크 목록    | 체크리스트 형태, 각 항목에 완료 기준 포함     |
| 의존성        | 태스크 간 선후 관계                       |
| 금지 사항      | 명시적으로 하지 말아야 할 것                |
| 완료 기준      | 전체 계획이 "완료"가 되려면 충족할 조건       |

### 6.4 Claude에게 계획 수립을 위임하는 패턴

```
아래 요구사항을 바탕으로 구현 계획 문서를 작성해줘.

<requirements>
[요구사항 문서 또는 요약]
</requirements>

<project_context>
[현재 프로젝트 상태, 기존 코드 구조 요약]
</project_context>

<plan_requirements>
- 각 태스크는 단일 Claude 세션에서 완료 가능한 크기로 분해
- 태스크 간 의존성 그래프를 명시
- 병렬 실행 가능한 태스크 그룹핑
- 각 태스크에 사용할 서브에이전트 유형 지정
- 위험 요소와 대응 방안 포함
- 완료 기준은 코드로 검증 가능한 형태로
</plan_requirements>
```

### 6.5 계획 문서 템플릿

```markdown
# [프로젝트/기능명] 구현 계획

## 1. 목표
[달성하려는 최종 결과를 1~2문장으로]

## 2. 배경
[왜 이 작업이 필요한지, 현재 상태는 어떤지]

## 3. 제약 조건
```

## 9. 버전 관리(Git) 연동 전략

### 9.1 바이브코딩에서 Git이 안전망인 이유

AI가 생성한 코드는 예측 불가능한 방향으로 갈 수 있다. Git은:
- **롤백 지점**: 잘못된 구현을 즉시 되돌릴 수 있다
- **변경 추적**: AI가 무엇을 변경했는지 diff로 정확히 확인
- **실험 격리**: 브랜치로 위험한 시도를 안전하게 수행
- **진행 기록**: 각 단계의 스냅샷이 자동으로 남음

### 9.2 커밋 전략 및 단위 기준

**커밋 단위 기준:**
- 하나의 논리적 변경 = 하나의 커밋
- "이 커밋을 revert해도 다른 기능에 영향이 없다"가 기준
- AI에게 한 번에 요청한 작업 단위 = 커밋 단위 (대략적)

**권장 커밋 타이밍:**
```
1. 기능 하나 완료 → 커밋
2. 리팩터링 완료 → 커밋
3. 테스트 추가 → 커밋
4. 버그 수정 → 커밋
5. 설정 변경 → 커밋
```

### 9.3 커밋 메시지 위임 프롬프트

```
"현재 staged 변경사항에 대해 Conventional Commits 형식으로
커밋 메시지를 작성해서 커밋해줘.

형식: <type>(<scope>): <description>

type: feat, fix, refactor, test, docs, chore, perf
scope: 변경된 모듈/기능명
description: 영문, 현재시제, 소문자 시작, 마침표 없음

body가 필요하면:
- 무엇을 변경했는지 (What)
- 왜 변경했는지 (Why)
를 간결하게 작성"
```

### 9.4 브랜치 전략

**1인 개발 권장 전략:**
```
main ─────────────────────────────────────────────
  │
  ├── feat/user-auth ──── (커밋, 커밋) ──── merge
  │
  ├── feat/sql-validator ── (커밋) ──── merge
  │
  └── fix/pii-masking ── (커밋) ──── merge
```

**기능별 브랜치가 최적인 이유:**
- 기능 단위 롤백 가능
- AI의 실험적 구현을 main에서 격리
- PR로 변경 내역 정리 가능

### 9.5 롤백 체크포인트 설정 습관

```bash
# 위험한 리팩터링 전에 태그 설정
git tag checkpoint/before-refactor-auth

# AI에게 대규모 변경을 요청하기 전
git stash push -m "before-ai-restructure"

# 실험적 구현 시도 전
```

### 14.7 Step 7: 핵심 기능 구현

**프롬프트 #7 - CRUD API 구현:**

```
Todo CRUD API 엔드포인트를 구현해줘.

<endpoints>
POST   /api/todos          - 할 일 생성
GET    /api/todos          - 할 일 목록 조회 (필터, 페이지네이션)
GET    /api/todos/{id}     - 할 일 상세 조회
PUT    /api/todos/{id}     - 할 일 수정
DELETE /api/todos/{id}     - 할 일 삭제
PATCH  /api/todos/{id}/complete - 완료 토글
</endpoints>

<rules>
- 인증된 사용자만 접근 (JWT)
- 자신의 할 일만 접근 가능 (다른 사용자의 todo 접근 시 404)
- Pydantic v2 스키마로 입출력 검증
- 페이지네이션: offset + limit (기본 20건)
- 필터: is_completed, priority, due_date 범위

</rules>

점진적으로 구현해줘:
1단계: 기본 CRUD (생성, 조회, 수정, 삭제)
2단계: 인증 연동 + 권한 검증
3단계: 필터링 + 페이지네이션
```
