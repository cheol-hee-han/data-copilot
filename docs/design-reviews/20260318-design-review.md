## 총평

설계의 핵심 강점은 **다중 소스 컨텍스트 수집(Multi-Source RAG)**, **도메인 사전을 통한 코드값 직접 매핑**, **3중 SQL 검증 체계**이다. 특히 은행 도메인의 불완전한 IT 메타를 보고서 SQL + 과거 이력 + 업무 매뉴얼로 보완하는 설계는 실무적으로 탁월하며, 도메인 사전이 LLM의 코드값 환각을 사전 차단하는 메커니즘도 매우 적절하다.

그러나 다음 5가지 구조적 우려가 있다:

1. **SQL 검증 실패 시 재생성 루프가 없어 단일 실패가 곧 최종 실패**가 된다.
2. **컨텍스트 수집이 5개 소스를 순차 호출**하여 응답 지연이 누적된다.
3. **의도 분류 저신뢰도(< 0.7) 시 라우팅이 구현되어 있지 않다**.
4. **폐쇄망 로컬 LLM 전환 시 프롬프트 전략 전면 재설계가 불가피**하다.
5. **PII 검증이 컬럼명 하드코딩에 의존**하여 실제 정보계 DB 스키마 변경에 취약하다.

아래에서 각 항목을 근거와 함께 상세히 분석하고 대안을 제시한다.

## 주요 비판 사항

### [P0] SQL 인젝션 방어의 구조적 허점: LLM 생성 SQL에 대한 파라미터 바인딩 미사용

**문제:** 현재 SQL 실행 경로에서 LLM이 생성한 SQL 문자열을 `text(query)`로 직접 실행한다(`postgres_connector.py` L193). SQL 검증 노드가 금지 패턴과 PII를 검사하지만, **LLM이 프롬프트 인젝션에 의해 교묘하게 우회하는 SQL을 생성할 경우** 검증을 통과할 수 있다.

**근거:**
- 전처리 노드의 인젝션 감지는 4개 정규식 패턴뿐이다(`preprocessor.py` L31-36). `;DROP`, `UNION SELECT`, `--`, `/* */`만 검사하며, `'; TRUNCATE`(앞에 따옴표가 있는 경우), `COPY TO`, `pg_read_file()`, `lo_import()` 등 PostgreSQL 고유 공격 벡터는 미검출.
- sql_validator의 FORBIDDEN_PATTERNS도 `pg_\w+`를 차단하지만, `pg_read_file`, `pg_sleep` 같은 함수 호출은 시스템 카탈로그 "접근"이 아닌 "함수 호출"이므로 패턴에 걸리지 않을 수 있다.
- 금융감독원 전자금융감독규정 제17조에 따르면, 금융회사는 SQL 인젝션 방어를 위해 prepared statement 사용을 의무화하고 있다.

**대안:**
1. **DB 계정 권한을 애플리케이션이 아닌 DB 레벨에서 강제**: PostgreSQL `REVOKE ALL`후 `GRANT SELECT ON` 특정 테이블만 허용. `pg_read_file`, `COPY` 등 위험 함수 실행 권한도 제거.
2. **SQL 검증기에 PostgreSQL 위험 함수 블랙리스트 추가**: `pg_read_file`, `pg_sleep`, `lo_import`, `dblink`, `COPY`, `SET ROLE` 등.
3. **쿼리 실행 시 타임아웃 설정**: `statement_timeout`을 DB 세션 레벨에서 강제(예: 30초)하여 `pg_sleep()` 기반 blind injection 방어.
4. **장기적으로 Parameterized View 또는 DB Function 래핑** 검토: LLM이 raw SQL 대신 사전 정의된 함수/뷰를 호출하도록 설계하면 공격 표면이 대폭 축소됨.

### [P1] SQL 검증 실패 시 재생성 루프 부재 — "한 번 틀리면 끝"

**문제:** `pipeline.py` L108-112에서 `validate_sql` 실패 시 곧바로 `error_end`로 분기한다. LLM의 SQL 생성은 확률적이므로 한 번의 시도에서 구문 오류나 LIMIT 누락이 발생할 수 있으나, 검증 오류를 피드백하여 재생성을 시도하는 경로가 없다.

**근거:**
- MAC-SQL(Wang et al., 2024, arXiv:2312.11242)은 self-correction 루프를 도입하여 BIRD 벤치마크 실행 정확도를 단일 패스 대비 +8.2%p 향상시켰다. 특히 구문 오류와 실행 오류의 자동 수정률이 각각 76%, 62%였다.
- 현재 아키텍처 문서 Section 7에서도 "검증 오류를 피드백하여 LLM에게 재생성 요청 (retry)"을 고도화 방향으로 명시하고 있어, 팀도 이 문제를 인지하고 있다.
- 실측 예상: SQL 검증 실패율이 10~20%라면(BIRD 벤치마크 기준 LLM 생성 SQL의 구문 오류율), 재시도 1회만으로도 최종 실패율을 3~6%로 낮출 수 있다.

**대안:**
```
validate_sql ──┬── 검증 통과 → execute_sql
               └── 검증 실패 (retry_count < 2) → generate_sql (오류 메시지를 state에 추가)
               └── 검증 실패 (retry_count >= 2) → error_end
```
구현 시 `PipelineState`에 `retry_count: int = 0`과 `validation_feedback: str = ""`를 추가하고, SQL 생성 프롬프트에 "이전 시도에서 발생한 오류: {feedback}" 섹션을 조건부 주입한다. 최대 재시도 횟수는 2회로 제한하여 비용과 지연 시간을 통제한다.

### [P1] 컨텍스트 수집의 순차 실행 — 불필요한 응답 지연

**문제:** `search_context_assembler.py`에서 5개 소스(ES 메타, 보고서 SQL, 이력 DB, Qdrant, 코드 메타)를 순차적으로 `await`한다(L27~74). 각 소스 간 데이터 의존성이 없음에도 순차 실행하여 총 지연 시간이 각 소스의 합이 된다.

**근거:**
- 실제 ES 검색 1회 ~50~200ms, PostgreSQL 쿼리 ~30~100ms, Qdrant 벡터 검색 ~50~150ms으로 추산하면, 순차 실행 시 5건 합산 약 300~800ms. 병렬 실행 시 max(개별 지연) 기준 ~100~200ms로 단축 가능.
- Python asyncio의 `asyncio.gather()`를 사용하면 코드 변경이 최소화된다.
- 사용자 체감 응답시간에서 컨텍스트 수집 단계는 LLM 호출(의도분류 ~1~2초, SQL생성 ~2~5초) 다음으로 큰 비중을 차지한다.

**대안:**
```python
# search_context_assembler.py 수정
import asyncio

async def collect_context(query: str) -> ContextInfo:
    manager = get_connector_manager()

    # 5개 소스 병렬 수집
    table_meta_task = manager.es.search_table_meta(query)
    report_task = manager.es.search_report_sql(query)
    history_task = manager.history_db.search_similar_sql(query)
    manual_task = manager.qdrant.search_manual(query)
    code_task = manager.es.search_code_meta("")

    results = await asyncio.gather(
        table_meta_task, report_task, history_task, manual_task, code_task,
        return_exceptions=True  # 개별 실패가 전체를 차단하지 않도록
    )
    # ... 각 결과 처리, 실패한 소스는 빈 결과로 대체
```

### [P1] 명확화 이후 멀티턴 재진입 미구현 — 명확화가 사실상 "거부"와 동일

**문제:** `clarify` 노드 실행 후 `workflow.add_edge("clarify", END)`로 파이프라인이 종료된다. 사용자가 명확화 질문에 응답해도 이를 받아 파이프라인을 재시작하는 메커니즘이 없다.

**근거:**
- `state.py`에 `clarification_response` 필드가 정의되어 있으나(`L102`), 이를 읽는 노드가 전혀 없다.
- `_route_after_intent()`에서 `intent_confidence < 0.7` 조건 검사도 없다. 아키텍처 문서(Section 3.6)에서는 "intent_confidence가 낮으면(< 0.7) 명확화 질문으로 분기"라고 명시했으나, 실제 `pipeline.py` L41-47의 `_route_after_intent()`는 `intent` 값만 보고 분기하며 confidence 임계값 검사가 구현되지 않았다.
- Ambig-NL2SQL(Bhaskar et al., 2023, arXiv:2310.05177)에 따르면 실제 사용자 질의의 약 38%가 모호하거나 불완전하다. 이 비율만큼의 요청이 명확화 후 재시도 없이 종료된다면 사용자 이탈률이 매우 높을 것이다.

**대안:**
1. **단기**: FastAPI 세션 레이어에서 명확화 응답을 받으면 `conversation_history`에 추가한 후 파이프라인을 재실행하는 방식 (그래프 외부 루프).
2. **중기**: LangGraph의 `interrupt` 기능을 사용하여 그래프 내부에서 사용자 응답을 대기하고, 응답 수신 후 `collect_context`로 분기하는 방식.
3. `_route_after_intent()`에 `state.intent_confidence < 0.7` 조건을 추가하여 설계 문서와 구현을 일치시킬 것.

### [P1] 도메인 사전 하드코딩 — 확장성 및 운영 유지보수 병목

**문제:** `finance_terms.py`의 도메인 사전이 Python 소스코드에 하드코딩되어 있다. 용어 추가/수정 시 코드 변경 + 배포가 필요하다.

**근거:**
- 현재 22개 용어. 은행 실무에서 최소 200~500개 이상의 업무 용어가 활발히 사용된다(여신, 수신, 외환, 신탁, 카드, 보험, 투자 등 각 업무별 수십 개).
- Gartner(2023) "AI in BI" 보고서에서 엔터프라이즈 NLP 시스템의 가장 큰 유지보수 비용은 도메인 지식 업데이트(전체 운영 비용의 약 40% 이상)로 보고.
- 은행은 신상품 출시, 규정 변경, 조직 개편이 빈번하여 용어 사전의 갱신 주기가 짧다.

**대안:**
1. **도메인 사전을 외부 저장소(JSON/YAML 파일 또는 DB 테이블)로 분리**하여 코드 배포 없이 갱신 가능하게 한다.
2. **관리자 UI(어드민 페이지)를 통해 비개발자(업무 담당자)가 용어를 직접 관리**할 수 있도록 한다.
3. **용어 매칭 알고리즘 개선**: 현재 `lookup_terms()`는 단순 문자열 포함 검사(`in` 연산자)로, "담보"를 검색하면 "담보대출"과 "유담보대출"이 모두 매칭된다. 형태소 분석 기반 매칭이나 최소한 longest-match-first 정렬을 적용해야 한다.

### [P1] 폐쇄망 로컬 LLM(ChatGPT 3.5급) 전환 시 구조적 문제

**문제:** 아키텍처 문서 Section 7에서 "폐쇄망 로컬 LLM (ChatGPT 3.5급) 대응 프롬프트"를 고도화 방향으로 명시하나, 현재 설계는 Claude Sonnet 수준의 LLM 성능에 강하게 의존하고 있다.

**근거:**
- BIRD 벤치마크(Li et al., 2023)에서 GPT-4의 실행 정확도 ~54.9% vs GPT-3.5-turbo ~37.2%로 약 17.7%p 차이. 로컬 7B~13B 모델은 이보다 더 낮아 ~25~30% 수준.
- 현재 프롬프트가 Claude Sonnet에 최적화된 구조(긴 시스템 프롬프트, 복잡한 규칙 8개, 다량의 컨텍스트 주입)로, 소형 모델은 이 분량의 지시사항을 제대로 따르지 못할 가능성이 높다.
- SQL 생성 프롬프트(`sql_generator.py`)의 시스템 프롬프트만 해도 컨텍스트 주입 후 수천 토큰에 달하며, 소형 모델의 컨텍스트 윈도우(2K~4K)를 초과할 수 있다.

**구체적 위험:**
| 영역 | Claude Sonnet 기대 성능 | 로컬 7B 모델 예상 | 영향 |
|------|----------------------|-----------------|------|
| 의도 분류 | ~95% | ~75~80% | 오분류 증가, 불필요한 명확화 질문 빈발 |
| SQL 생성 (단순) | ~85% | ~55~65% | 단순 쿼리도 실패 빈발 |
| SQL 생성 (복잡 JOIN) | ~60% | ~20~30% | 사실상 사용 불가 |
| JSON 구조 응답 | 안정적 | 불안정 (형식 위반 빈발) | 분석 노드 파싱 실패 |
| 한국어 이해 | 양호 | 모델 의존 (대부분 취약) | 전반적 품질 저하 |

**대안:**
1. **모델 계층화 전략**: 의도 분류는 로컬 모델(가벼운 작업), SQL 생성은 가능한 한 큰 모델(또는 fine-tuned NL2SQL 전용 모델 예: SQLCoder 기반). 단일 모델로 전 노드를 커버하지 않는다.
2. **프롬프트 간소화 전략 사전 준비**: 소형 모델용 축약 프롬프트 세트를 별도 관리. 규칙을 8개에서 핵심 3개로 줄이고, 퓨샷 예제를 2개 이내로 제한.
3. **도메인 사전 의존도 강화**: 소형 모델일수록 LLM의 추론 능력이 떨어지므로, 도메인 사전이 SQL 조건을 더 직접적으로 제공(현재 방향과 일치하나 커버리지 확대 필수).
4. **SQL 템플릿 기반 하이브리드**: 자주 사용되는 쿼리 패턴(월간 집계, 유형별 GROUP BY 등)은 템플릿으로 사전 정의하고, LLM은 템플릿 선택 + 파라미터 채우기만 담당. 이 방식은 Codex 등 소형 모델에서도 높은 정확도를 유지할 수 있다(C3-SQL, Dong et al., 2023에서 템플릿 기반 접근이 단순 생성 대비 +12%p 향상 보고).

### [P2] AsyncAnthropic 클라이언트 매 호출마다 재생성 — 커넥션 풀 낭비

**문제:** `intent_classifier.py` L43, `sql_generator.py` L118, `clarifier.py` L38, `analyzer.py` L57, `formatter.py` L53 각각에서 `AsyncAnthropic(api_key=...)` 를 매 노드 호출마다 새로 생성한다.

- 단일 파이프라인에서 최대 4회 LLM 호출(의도분류 + SQL생성 + 분석 + 포맷팅) 시 불필요한 커넥션 생성 200~600ms.

**대안:** `ConnectorManager`에 `AsyncAnthropic` 클라이언트를 싱글턴으로 추가하거나, 의존성 주입 방식으로 노드에 전달.

```python
# config.py 또는 별도 모듈
_anthropic_client: AsyncAnthropic | None = None

def get_anthropic_client() -> AsyncAnthropic:
    global _anthropic_client
    if _anthropic_client is None:
        _anthropic_client = AsyncAnthropic(api_key=settings.anthropic_api_key)
    return _anthropic_client
```

### [P2] 골든셋 평가의 한계 — "통과"의 정의가 느슨

**문제:** `evaluator.py` L132-136의 종합 판정이 `intent_match AND table_match AND (pattern_match OR parseable)`이다. **SQL이 구문적으로 유효하기만 하면 패턴이 완전히 다르더라도 통과**할 수 있다.

**근거:**
- 예를 들어 GS004("현재 연체 중인 대출 건수와 총 연체 금액")에서 기대 패턴은 `OVERDUE_YN = 'Y'` 조건이지만, LLM이 `OVERDUE_DAYS > 0`으로 생성하면 패턴은 불일치하지만 `parseable=True`이므로 통과. 그러나 `OVERDUE_DAYS > 0`과 `OVERDUE_YN = 'Y'`의 결과는 데이터에 따라 다를 수 있다.
- **실행 정확도(Execution Accuracy)** 평가가 없다. BIRD, Spider 벤치마크의 표준 평가 방식은 "기대 SQL과 생성 SQL을 실제 DB에서 실행하여 결과가 동일한지"를 비교하는 것이다.

**대안:**
1. 종합 판정을 `intent_match AND table_match AND pattern_match AND parseable`로 강화 (AND 조건).
2. Dummy DB에서 기대 SQL과 생성 SQL을 모두 실행하여 결과 집합을 비교하는 **Execution Accuracy** 차원 추가.
3. 골든셋을 현재 15건에서 최소 50건으로 확대. 난이도별 분포도 easy:medium:hard = 30%:40%:30%로 재조정 권장.

### [P2] 분석 노드의 데이터 누락 — 결과 100행만 LLM에 전달

**문제:** `analyzer.py` L59: `result_str = "\n".join(str(row) for row in result.rows[:100])`. 최대 10,000행까지 조회 가능하나 분석에는 100행만 전달되어, 나머지 9,900행의 데이터가 분석에서 누락된다.

**근거:**
- "지점별 연체율 추이"처럼 지점 수가 100개 이상인 경우, 100행으로 잘리면 일부 지점 데이터가 누락되어 분석 결과가 왜곡된다.
- `data_analyzer.py`의 `compute_basic_statistics()`는 전체 rows를 대상으로 계산하지만, LLM 분석과 통계 분석의 대상 데이터가 불일치한다(LLM은 100행, 통계 엔진은 전체).

**대안:**
1. LLM에는 100행 샘플 + **전체 데이터의 요약 통계**(compute_basic_statistics 결과)를 함께 전달.
2. 프롬프트에 "아래는 전체 N건 중 상위 100건의 샘플입니다. 전체 통계는 별도로 제공합니다."를 명시.
3. 전체 데이터 기반 통계를 `data_analyzer.py`에서 계산한 후, 이를 LLM 분석 프롬프트의 컨텍스트로 주입.

## 실패 시나리오

### 시나리오 F1: 도메인 사전 미등록 용어로 인한 잘못된 SQL [P1]

**상황:** 사용자가 "마통 한도 현황 보여줘"라고 입력. "마통"(마이너스통장)은 도메인 사전에 미등록.

**예상 결과:** 도메인 사전 매칭 실패 → LLM이 "마통"을 자체 해석 → 잘못된 테이블/조건으로 SQL 생성. `TB_LOAN_INFO`에서 `LOAN_TYPE_CD`를 추론해야 하나, "마이너스통장"에 해당하는 코드값을 모르므로 잘못된 코드(예: '01')를 사용하거나 아예 WHERE 조건 없이 전체 대출을 조회.

**대안:** 도메인 사전에 매칭되지 않은 핵심 명사를 감지하면, SQL 생성 전에 "혹시 '마통'은 마이너스 통장을 말씀하시는 건가요?"와 같은 확인 루프를 추가. `lookup_terms()` 결과가 비어있고, 의도가 `data_extraction`/`data_analysis`인 경우를 트리거 조건으로 활용.

### 시나리오 F2: 컨텍스트 윈도우 초과 [P2]

**상황:** 실제 정보계 DB에 테이블 50개 이상, ES 검색이 관련 테이블 10개 반환, 보고서 SQL 5건, 과거 이력 5건, 매뉴얼 3건을 모두 프롬프트에 주입.

**예상 토큰 수:**
- 테이블 10개 x 평균 8컬럼 x 50토큰/컬럼 = ~4,000토큰
- 보고서 SQL 5건 x ~200토큰 = ~1,000토큰
- 과거 SQL 5건 x ~150토큰 = ~750토큰
- 매뉴얼 3건 x ~300토큰 = ~900토큰
- 도메인 용어 + 코드 메타 = ~500토큰
- 시스템 프롬프트 규칙 = ~500토큰
- 합계: ~7,650토큰 (시스템 프롬프트만)

Claude Sonnet은 200K 컨텍스트이므로 문제없으나, **로컬 LLM 전환 시 4K~8K 컨텍스트에서 이 프롬프트가 완전히 잘린다**.

**대안:**
- `_build_table_info()`에 토큰 예산 상한(예: 3,000토큰)을 설정하고, 초과 시 도메인 사전 매칭 점수가 높은 테이블만 우선 포함.
- 과거 SQL, 보고서 SQL도 유사도 상위 N건으로 제한(현재 각 5건, 3건 제한은 있으나 토큰 기준이 아님).

### 시나리오 F3: 유사 테이블 오선택으로 인한 정합성 오류 [P1]

**상황:** "이번 달 연체 현황"이라는 요청에서 `TB_LOAN_INFO`(건별 현재 상태)와 `TB_LOAN_OVERDUE_STAT`(월말 기준 집계) 중 어떤 것이 적절한지 모호.

**문제:** "현황"이 "현재 시점의 건별 목록"인지 "월말 기준 통계 수치"인지에 따라 완전히 다른 SQL이 필요하다. 도메인 사전에서 "연체"는 `TB_LOAN_INFO`로 매핑되고, "연체율"만 `TB_LOAN_OVERDUE_STAT`로 매핑되어 있어, LLM이 잘못된 테이블을 선택할 수 있다.

**대안:**
- 도메인 사전에 "연체 현황"이라는 별도 용어를 추가하고, description에 "건별 현재 연체 상태는 TB_LOAN_INFO, 월말 기준 집계는 TB_LOAN_OVERDUE_STAT" 명시.
- 테이블 선택이 모호한 경우를 감지하는 로직 추가(같은 카테고리의 2개 이상 테이블이 매칭될 때 사용자에게 확인).

### 시나리오 F4: DB 쿼리 실행 타임아웃 및 대용량 결과 [P2]

**상황:** 사용자가 "올해 전체 거래 내역 보여줘"라고 입력. `TB_TRANSACTION`은 실시간 갱신 대용량 테이블.

**문제:** 프롬프트 규칙에 "TB_TRANSACTION 테이블은 반드시 TXN_DT 날짜 조건을 포함해야 함"이 있지만, 이는 LLM에 대한 **soft constraint**일 뿐이다. LLM이 규칙을 무시하면 SQL 검증 노드에서도 이 특정 테이블의 날짜 조건을 검사하는 로직이 없다.

**대안:**
- SQL 검증 노드에 **테이블별 필수 조건 검사** 추가: `TB_TRANSACTION`이 FROM/JOIN에 포함되면 WHERE에 `TXN_DT` 조건이 있는지 sqlglot AST로 검증.
- 이 로직을 일반화하여, 설정 파일에 `{"table": "TB_TRANSACTION", "required_columns": ["TXN_DT"]}`와 같은 규칙을 정의할 수 있도록 설계.

### 시나리오 F5: 동시 사용자 요청 시 싱글턴 상태 오염 [P2]

**상황:** 2명 이상의 사용자가 동시에 요청을 보냈을 때, `ConnectorManager` 싱글턴이 상태를 공유.

**문제:** `ConnectorManager` 자체는 stateless이므로 직접적 문제는 없으나, `get_connector_manager()` 싱글턴의 `use_dummy` 인자가 최초 호출 시에만 적용된다(`manager.py` L56-61). 이후 호출에서 `use_dummy=False`로 전환하려 해도 기존 `True` 인스턴스가 반환되는 버그가 잠재.

**대안:** 싱글턴 패턴을 유지하되, `use_dummy` 변경 시 기존 인스턴스를 교체하는 `reset()` 메서드 추가. 또는 `use_dummy`를 Settings에서 일원화 관리.

## 아키텍처 대안 비교

### 현재 설계: 단일 LLM 호출 + RAG 컨텍스트 주입

| 항목 | 평가 |
|------|------|
| 장점 | 구현 단순, 응답 지연 최소(LLM 1회), 프롬프트에 모든 정보를 집약 |
| 단점 | 복잡 쿼리 정확도 한계, 실패 시 재시도 불가, 소형 모델 전환 어려움 |

### 대안 A: Self-Correction Loop (자기 교정 루프)

| 항목 | 평가 |
|------|------|
| 방식 | SQL 생성 → 검증 → 실패 시 오류 피드백 포함 재생성 (최대 2회) |
| 장점 | 구문/실행 오류 자동 수정. MAC-SQL 기준 +8.2%p 정확도 향상 |
| 단점 | 평균 응답시간 재시도 발생 시 +2~5초 증가 |
| 채택 권고 | **강력 권고**. 구현 비용 낮고 효과 높음. `validate_sql → generate_sql` 역방향 엣지 1개 추가 |

### 대안 B: Decomposed SQL Generation (분해 생성)

| 항목 | 평가 |
|------|------|
| 방식 | 복잡 쿼리를 서브쿼리로 분해 → 각각 생성 → 조합 (DIN-SQL 방식) |
| 장점 | 복잡 쿼리(3-way JOIN 이상) 정확도 +15~20%p |
| 단점 | 구현 복잡도 높음, LLM 호출 2~3배 증가, 응답시간 +3~8초 |
| 채택 권고 | **현재 단계에서 불채택**. 골든셋 hard 쿼리가 4건(27%)이며, self-correction으로 대부분 커버 가능. 정확도 목표 미달 시 2차 이터레이션에서 도입 검토 |

### 대안 C: SQL 템플릿 + 슬롯 필링 하이브리드

| 항목 | 평가 |
|------|------|
| 방식 | 자주 사용되는 쿼리 패턴을 템플릿으로 정의, LLM은 템플릿 선택 + 파라미터 채우기 |
| 장점 | 소형 모델에서도 높은 정확도, SQL 안전성 보장 (템플릿이 이미 검증됨) |
| 단점 | 템플릿에 없는 쿼리는 처리 불가, 초기 템플릿 구축 비용 |
| 채택 권고 | **폐쇄망 로컬 LLM 전환 시 강력 권고**. 현재 보고서 SQL + 과거 SQL 이력을 활용하면 주요 패턴의 템플릿 추출이 가능 |

| 감사/컴플라이언스 요구사항 강화 | 내부 감사에서 SQL 실행 로깅 미흡 지적 | 감사 추적 로그 정교화, 실행 SQL + 결과 건수 + 사용자 ID 풀 로깅 |

## 금융 도메인 특수성 검토

### [P1] 기준일자(Base Date) 개념 미반영

**문제:** 은행 정보계에서는 거의 모든 조회가 **"기준일자"** 를 전제로 한다. "이번 달 대출 잔액"이라 하면, "오늘 기준" 잔액인지 "월말 확정 기준" 잔액인지에 따라 테이블과 SQL이 완전히 달라진다. 현재 설계에서 기준일자 개념이 프롬프트에도, 도메인 사전에도 없다.

**대안:**
- 도메인 사전의 시간 카테고리에 "기준일", "영업일", "월말 기준", "전일 기준" 등을 추가.
- SQL 생성 프롬프트에 "정보계 DB는 일배치 기준이므로, 현재 시점의 데이터는 전일(T-1) 기준입니다" 규칙 추가.

### [P2] 금액 단위 처리 미흡

**문제:** 정보계 DB의 금액은 보통 "원" 단위로 저장되나, 사용자는 "억원", "만원" 단위로 말한다. "100억 이상 대출 건수"라는 요청에서 LLM이 `LOAN_AMT >= 100`이라고 생성할 위험이 있다.

**대안:** 도메인 사전에 금액 관련 용어 추가. "억원" → "* 100000000", "만원" → "* 10000". SQL 생성 프롬프트에 "금액 컬럼은 원(KRW) 단위입니다. 1억원 = 100,000,000" 규칙 명시.

### [P2] 휴일/영업일 처리 부재

**문제:** "지난주 금요일 기준"이나 "직전 영업일"과 같은 요청에서, 공휴일과 영업일 캘린더가 반영되지 않으면 잘못된 날짜 조건이 생성된다.

**대안:** 영업일 캘린더 테이블(TB_BIZ_CALENDAR)을 참조하거나, 도메인 사전에 "직전 영업일" 등의 SQL 패턴을 등록.

## 재조사 요청 사항

research-analyst에게 추가 조사를 요청하는 항목:

- [ ] **항목 1**: 폐쇄망에서 사용 가능한 한국어 NL2SQL 특화 모델(SQLCoder 한국어 버전, 한국어 fine-tuned CodeLlama 등)의 현재 성능 및 도입 사례. 로컬 7B/13B 모델로 은행 도메인 SQL을 생성한 사례가 있는지 조사 필요.
- [ ] **항목 2**: PostgreSQL의 Row-Level Security(RLS)나 Column-Level Security를 활용하여 LLM 생성 SQL의 보안을 DB 레벨에서 강제하는 방안. 현재 애플리케이션 레벨 검증만으로 충분한지.
- [ ] **항목 3**: 은행 정보계 DB의 실제 테이블 수, 평균 컬럼 수, 코드값 종류 수에 대한 현황 파악. 이를 기반으로 컨텍스트 윈도우 토큰 예산을 정밀 산정 필요.
- [ ] **항목 4**: LangGraph의 `interrupt` / `resume` 기능을 활용한 멀티턴 대화 구현 패턴. 세션 상태 지속 방안 포함.
- [ ] **항목 5**: 금융감독원 전자금융감독규정 및 내부통제 요건에서 AI 기반 SQL 생성/실행 시스템에 대한 규제 요건(로깅, 감사 추적, 승인 프로세스 등).

## 수용 불가 항목 (재설계 권고)

이 항목들이 해소되지 않으면 다음 단계(실환경 연동) 진행 불가:

1. **SQL 인젝션 방어 강화 [P0]**: PostgreSQL 위험 함수 블랙리스트 추가, DB 계정 권한 최소화 확인, 쿼리 타임아웃 설정. 금융 시스템에서 보안 결함은 서비스 출시를 차단하는 수준의 이슈.
2. **명확화 후 재진입 경로 구현 [P1]**: 사용자 질의의 30~40%가 명확화를 거칠 것으로 예상되는데, 재진입이 없으면 이 비율만큼의 요청이 실패로 종결됨.
3. **intent_confidence 임계값 검사 구현 [P1]**: 설계 문서에 명시된 0.7 임계값 로직이 코드에 누락되어 있어 설계-구현 불일치. 의도 오분류가 곧바로 잘못된 SQL 생성으로 이어짐.

## 수용 가능 항목 (개선 권고)

진행은 가능하나 이후 이터레이션에서 개선 권고:

1. **컨텍스트 수집 병렬화 [P2]**: `asyncio.gather()` 적용으로 300~600ms 절약 가능. 코드 변경 최소.
2. **AsyncAnthropic 클라이언트 싱글턴화 [P2]**: 노드마다 재생성 → 공유 인스턴스로 변경.
3. **도메인 사전 외부 저장소 분리 [P1]**: 현재 22개 용어로 시작 가능하나, 실환경 투입 전 확장 체계 필요.
4. **골든셋 확대 및 Execution Accuracy 도입 [P2]**: 15건 → 50건+, 실행 결과 비교 추가.
5. **SQL 재생성 루프 추가 [P1]**: validate_sql → generate_sql 역방향 엣지 + retry_count 관리.
6. **기준일자/금액단위/영업일 도메인 규칙 추가 [P2]**: 프롬프트 및 도메인 사전 보강.

## 합의 추천 설계 방향

현재 설계의 근간(LangGraph 기반 파이프라인, Multi-Source RAG, 도메인 사전)은 유지하되, 다음 우선순위로 개선을 진행할 것을 권고한다:

**1순위 (즉시)**
- SQL 인젝션 방어 강화 (DB 권한 확인 + 위험 함수 블랙리스트)
- `_route_after_intent()`에 confidence 임계값 검사 추가
- `clarify → END` 이후 재진입 메커니즘 구현 (FastAPI 레이어)

**2순위 (1~2주 내)**
- SQL 재생성 루프 (validate_sql 실패 → generate_sql 재시도, 최대 2회)
- 컨텍스트 수집 병렬화 (`asyncio.gather`)
- AsyncAnthropic 클라이언트 싱글턴화

**3순위 (1개월 내)**
- 도메인 사전 외부 저장소 분리 + 관리 UI
- 골든셋 확대 (50건+) + Execution Accuracy 도입
- 기준일자, 금액 단위, 영업일 등 금융 도메인 규칙 보강

**4순위 (폐쇄망 전환 준비)**
- SQL 템플릿 하이브리드 아키텍처 설계
- 소형 모델용 축약 프롬프트 세트 작성
- 의도 분류 로컬 모델(fine-tuned classifier) 평가
