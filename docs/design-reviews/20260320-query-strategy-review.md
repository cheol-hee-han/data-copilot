- **검토일**: 2026-03-20
- **검토 대상**: `src/services/search_query_builder.py`, `tests/test_search_query_builder.py`, `search_context_assembler.py` 통합부
- **검토 범위**: 전략 설계, 커넥터 호환성, 테스트 신뢰성, 운영 리스크

---

## 총평

기존에 `preprocessed_input`을 4개 소스에 동일하게 전달하던 구조에서, 소스별 특화 쿼리를 생성하는 계층을 추가한 것은 **올바른 방향**이다.
불용어 제거, 동의어 확장, 테이블명 부스트 등 각 소스의 검색 메커니즘 특성을 고려한 설계 의도는 적절하다.

다만, 아래에서 식별한 **P1 2건, P2 4건**은 실서비스 투입 전 반드시 해결하거나 의식적으로 수용해야 한다.
특히 테스트가 100% 통과하는 것은 **전략이 완벽해서가 아니라, 테스트가 실제 검색 품질을 측정하지 않기 때문**이다.

## 주요 비판 사항

### [P1-1] `lookup_terms()` 부분 문자열 매칭의 false-positive 폭발

**현상**: `lookup_terms()`는 공백 제거 후 `in` 연산으로 부분 일치한다.

```python
# finance_terms.py:929
if expr.replace(" ", "").lower() in query_lower:
```

이 로직은 다음과 같은 false-positive를 발생시킨다:

| 입력 | 의도하지 않은 매칭 | 이유 |
|------|-----------------|------|
| "고정금리 대출 현황" | `DomainTerm(term="고정")` (자산건전성 3단계) | "고정금리"에 "고정"이 부분 포함 |
| "CD금리 추이" | `DomainTerm(term="CD")` (양도성예금증서) | 의도는 CD금리인데 상품 자체가 매칭 |
| "일시불 결제 현황" | `DomainTerm(term="할부")` | "일시불" 매칭은 맞지만 "할부"의 alias "분할납부"와 같은 수준에서 오동작 가능 |
| "입금 이력 조회" | `DomainTerm(term="입금")` + `DomainTerm(term="이체")` 동시 매칭 가능 | "이"가 포함되어 "이체"가 매칭되지는 않지만, 공백 제거 후 "입금이력조회"에서 향후 "이력" 관련 term 추가 시 오매칭 |

**영향**: `search_query_builder.py`가 `lookup_terms()`에 전적으로 의존하므로, false-positive가 발생하면 잘못된 테이블명·컬럼명·카테고리가 4개 소스 쿼리에 모두 전파된다.

**근거**: 실제로 "고정금리 대출 현황"을 입력하면 `ASSET_HLTH_CD = '30'`(자산건전성 고정)이 매칭되어, ES 테이블 검색에 `ASSET_HLTH_CD`가 주입되고, 이력 DB에 "고정이하여신", "부실여신" 등이 확장 키워드로 들어간다. 이는 완전히 다른 검색 결과를 유발한다.

**대안**:
- 단기: `lookup_terms()`에 **단어 경계(word boundary) 매칭** 또는 **최장 일치 우선(longest match first)** 로직 추가
- 중기: 매칭 결과에 **confidence score**를 부여하고, 쿼리 전략에서 threshold 이하는 제외
- 장기: 형태소 분석기(Mecab/Kiwi) 기반 토큰화 후 정확 매칭

### [P1-2] 테스트가 "검색 품질"이 아닌 "쿼리 문자열 포함 여부"만 검증한다

**현상**: 67개 테스트 전부 **`build_source_queries()`의 출력 문자열에 특정 토큰이 포함되는지**만 검증한다. 이는 "올바른 쿼리를 만들었는지"가 아니라 "문자열 조합 함수가 문자열을 제대로 조합하는지"를 테스트하는 것이다.

**핵심 문제**: 생성된 쿼리가 **실제 ES/Qdrant/PostgreSQL에서 원하는 결과를 가져오는지**는 전혀 검증하지 않는다.

```python
# 현재 테스트: 단순 문자열 포함 검사
assert "TB_LOAN_INFO" in result.es_table_query  # ← 쿼리에 들어가기만 하면 통과
```

이것은 마치 SQL을 생성한 뒤 "SQL에 SELECT가 포함되어 있는가?"만 검증하는 것과 같다. 핵심 질문은 **"이 쿼리로 ES를 검색하면 관련 테이블이 상위에 나오는가?"**이다.

**100% 통과의 함정**: 테스트가 `build_source_queries()` 내부 로직의 기계적 동작만 검증하므로, 구현이 정상이면 당연히 100%다. 이것은 검색 품질과 무관하다.

**대안**:
- 단기: Dummy 커넥터를 활용한 **end-to-end 통합 테스트** 추가 — `collect_context()`를 호출하여 반환된 `ContextInfo.table_metas`에 기대 테이블이 포함되는지 검증
- 중기: 기존 골든셋(`evaluation/`)과 연동하여, 각 골든셋 케이스에 대해 **"전략 적용 전/후 컨텍스트 수집 결과 차이"**를 측정하는 회귀 테스트 구성
- 장기: ES/Qdrant 테스트 인스턴스를 활용한 실제 검색 품질(nDCG, MRR) 측정 파이프라인

### [P2-1] 공백 기준 토큰화의 한계

**현상**: `_extract_core_keywords()`는 `text.split()`으로 토큰화한다. 한국어는 교착어(조사가 단어에 붙음)이므로 공백 split만으로는 정확한 키워드 추출이 불가능하다.

| 입력 | split 결과 | 실제 필요한 키워드 |
|------|-----------|-----------------|
| "연체대출의 현황을" | ["연체대출의", "현황을"] | ["연체", "대출", "현황"] |
| "지점별수신잔액" | ["지점별수신잔액"] | ["지점", "수신", "잔액"] |

현재 `_PARTICLE_PATTERN`이 어미 "의", "을"을 제거하지만, "연체대출"을 "연체"+"대출"로 분리하지는 못한다.

**완화 요인**: `lookup_terms()`의 부분 문자열 매칭이 "연체대출의현황을"에서도 "연체", "대출" 등을 찾아내므로, 도메인 사전에 등록된 용어는 문제가 적다.

**대안**:
- 경량 형태소 분석 라이브러리(예: `kiwipiepy`, 약 50ms) 도입으로 토큰화 정밀도 향상
- 또는 도메인 사전의 커버리지가 충분하다면, 현 수준을 의식적으로 수용하고 사전 미등록 용어에 대한 폴백 전략 문서화

### [P2-2] ES 테이블명 "2회 반복 부스트"는 실제 효과가 불확실

**현상**: `_build_es_table_query()`가 테이블명을 2회 반복한다.

```python
for table in tables:
    parts.append(table)
    parts.append(table)  # "부스트"
```

**근거**: ES `multi_match`의 기본 타입은 `best_fields`이다. 이 모드에서 쿼리 문자열에 동일 토큰을 반복해도 **TF(Term Frequency)가 쿼리 내에서 올라가는 것이 아니라**, ES는 각 필드별로 "TB_LOAN_INFO" 토큰의 문서 내 TF를 계산한다. 쿼리에 2번 써도 문서 내 TF는 변하지 않으므로 점수 부스트 효과는 거의 없다.

**대안**:
- ES 쿼리를 `multi_match` 대신 `bool` + `should` 구조로 변경하고, `table_name` 필드에 `boost: 3.0` 적용
- 또는 `search_query_builder.py`에서 부스트를 시도하지 말고, 커넥터 레이어에서 필드별 가중치를 제어

---

### [P2-3] Qdrant 쿼리에 description을 concat하면 벡터가 dilute될 수 있다

**현상**: `_build_qdrant_query()`가 원본 입력에 도메인 용어 설명(최대 80자 x 6개 = 480자)을 붙인다.

```python
parts = [original_input]
# ... 도메인 설명 추가 ...
return " ".join(parts)  # 최종 길이: 원본 + 최대 ~500자
```

**근거**: `intfloat/multilingual-e5-small`은 **쿼리 텍스트가 짧을수록** 의미가 집중된 벡터를 생성한다. 긴 텍스트를 임베딩하면 다양한 토픽이 평균화되어 벡터가 dilute(희석)된다. Sentence-BERT 계열 논문(Reimers & Gurevych, 2019)에서도 문장 길이와 임베딩 품질의 역상관 관계가 보고된 바 있다.

특히 "NIM 추이 보여줘"에 "순이자마진. 산출식: (이자수익 - 이자비용) / 이자수익창출자산 평잔 × 100"을 붙이면, 임베딩이 "NIM"이 아니라 "산출식"이나 "이자수익" 쪽으로 끌려갈 수 있다.

**대안**:
- Qdrant 검색을 **2단계**로 분리: (1) 원본 입력으로 1차 검색, (2) 도메인 설명으로 rerank
- 또는 description을 쿼리에 넣지 않고, Qdrant의 **filter 조건**으로 카테고리를 제한하여 검색 범위를 좁히는 방식

---

### [P2-4] `_build_es_report_query()`의 시간 표현 제거가 불완전

**현상**: 정규식으로 "이번 달", "지난 분기" 등을 제거하지만, 패턴 목록이 하드코딩되어 있고 도메인 사전의 시간 카테고리와 동기화되지 않는다.

```python
time_patterns = re.compile(
    r"(이번\s*달|지난\s*달|올해|전월|당월|금월|이달|작달"
    r"|지난\s*분기|이번\s*분기|전년|작년)",
)
```

도메인 사전에는 "전년동기", "직전영업일", "상반기", "하반기", "회계연도" 등 더 많은 시간 표현이 있으나 이 정규식에는 포함되지 않는다.

**대안**: 도메인 사전의 `category == "시간"` 용어에서 term + aliases를 자동 수집하여 패턴을 동적 생성. 이렇게 하면 사전에 시간 표현을 추가할 때 자동으로 반영된다.

## 아키텍처 대안 비교

| 측면 | 현재 설계 (규칙 기반) | 대안 A: LLM 기반 쿼리 리라이팅 | 대안 B: 하이브리드 (규칙 + 경량 LLM) |
|------|---------------------|---------------------------|--------------------------------|
| 레이턴시 | <1ms (즉시) | +500~2000ms (LLM 호출) | +50~200ms (경량 모델) |
| 정확도 | 사전 커버리지에 의존 | 높음 (문맥 이해) | 중~높 |
| 사전 미등록 용어 | 대응 불가 (폴백만) | 대응 가능 | 부분 대응 |
| 비용 | 0원 | API 호출당 과금 | 로컬 모델이면 0원 |
| 유지보수 | 사전 수동 관리 필요 | 프롬프트 관리 | 둘 다 필요 |

**판정**: 현재 단계(개발 초기, 더미 커넥터)에서 규칙 기반 전략은 합리적. 단, 실서비스 전환 시 F1/F3 같은 false-positive 해결을 위해 **대안 B(규칙 + 경량 리랭킹)로 진화 경로**를 열어두는 것이 바람직하다.

## 합의 추천 설계 방향

1. **즉시**: [P1-2] Dummy 커넥터 기반 end-to-end 테스트 추가 → 전략이 실제 컨텍스트 수집 결과에 미치는 영향을 측정
2. **단기**: [P1-1] `lookup_terms()`에 최장 일치 우선 + 매칭 신뢰도 score 도입
3. **단기**: [P2-4] 시간 표현 패턴을 도메인 사전에서 동적 생성
4. **중기**: ES 실연동 시 `multi_match` → `bool` + 필드별 `boost` 쿼리 구조로 커넥터 개선
5. **중기**: Qdrant 실연동 시 쿼리 길이별 A/B 테스트로 최적 전략 선택
