# Data Copilot Graph 흐름 설계 종합 평가

> **평가 일시**: 2026-03-21

> **평가 관점**: 데이터 분석 전문가 — 테이블 탐색부터 SQL 작성까지의 실무 프로세스 기준

> **요청받은 내용**: 데이터 분석 전문가의 시선에서, 현업으로부터 데이터 추출/분석 요구사항은 받았는데 관련 업무에 대한 인사이트나 기존에 해본 경험이 없는 경우 
어떤 테이블을 써서 데이터를 어떻게 추출해야 하는지도 모르는 상태일 때,
테이블을 탐색하고, 탐색한 테이블이 요구사항 해결을 위해 적합한 데이터인지 판단하며,
매뉴얼, 관련 사례 등 추가 자료를 참고하여 디테일한 SQL 작성할 때 까지 
다양한 챌린지들을 해결하는 과정(프로세스)을 다각도로 다양하게 구상해보고
본 프로젝트의 Graph 흐름 설계와 상세한 전략(아이디어)이 잘 설계 되었는지 평가해주세요.
정보를 얻는데에 미흡한 부분이 있거나, 또는 잘못된 정보를 습득할 가능성이 있는 경우 등 
다양한 측면에서 개선사항을 분석하고 평가해주세요.

## 1. 전체 파이프라인 흐름 요약

```
preprocess → classify_intent → [clarify | collect_context]
                                         ↓
                                collect_context → generate_sql → validate_sql
                                                                      ↓
                                [retry generate_sql | execute_sql | clarify | error_end]
                                                           ↓
                                execute_sql → [analyze_data | format_response]
                                                    ↓
                                          format_response → END
```

**9개 노드**, 조건부 라우팅 기반 LangGraph 워크플로우:

| 노드 | 역할 |
|------|------|
| `preprocess` | 입력 정규화, SQL/프롬프트 인젝션 탐지, PII 마스킹 |
| `classify_intent` | 의도 분류 (추출/분석/명확화/일반질문) |
| `clarify` | 멀티턴 명확화 질문 생성 |
| `collect_context` | 병렬 다중 소스 컨텍스트 수집 |
| `generate_sql` | LLM 기반 SQL 생성 (재시도 지원) |
| `validate_sql` | 보안·문법·PII·테이블선택 6계층 검증 |
| `execute_sql` | 읽기 전용 DB에서 안전 실행 |
| `analyze_data` | 데이터 분석 + 시각화 판단 |
| `format_response` | 비전문가 대상 결과 포맷팅 |

## 2. 강점 분석

### 2.1 도메인 지식 기반 다중 소스 병렬 탐색

`collect_context`에서 `asyncio.gather`로 **4개 소스를 병렬 탐색**하는 설계는 핵심 강점이다.

| 소스 | 역할 | 해결하는 문제 |
|------|------|-------------|
| ES 테이블 메타 | 테이블/컬럼 구조 파악 | "어떤 테이블이 있는지 모름" |
| ES 보고서 SQL | 검증된 기존 SQL 참조 | "어떻게 작성해야 하는지 모름" |
| PostgreSQL 이력 | 과거 유사 쿼리 활용 | "비슷한 요구사항 처리 경험 없음" |
| Qdrant 업무 매뉴얼 | 계수산출식/업무규정 | "금융 용어의 정확한 정의 모름" |

데이터 분석가가 실무에서 "이 테이블이 맞나?" 판단할 때 활용하는 참조 경로(메타 → 기존 사례 → 매뉴얼)를 정확히 반영하고 있다.

### 2.2 유사 테이블 판별 메커니즘

`similar_table_resolver.py`의 **Similar Table Group** 설계:

- `TB_LOAN_INFO`(건별 현재 상태) vs `TB_LOAN_OVERDUE_STAT`(월말 집계 통계)
- 각 테이블별 `suitable_for`, `unsuitable_for`, `signal_keywords` 정의
- **3단계 판정**: PASS → WARNING(재생성) → AMBIGUOUS(사용자 확인)

정보계 DB에서 가장 흔한 실수인 "유사 테이블 오선택"을 구조적으로 방어한다.

### 2.3 검증 실패 → 피드백 루프

`sql_validator.py`에서 검증 실패 시 **에러 내용을 구체적 피드백으로 변환**하여 SQL Generator에 재주입:

```
validate_sql(실패) → validation_feedback 생성 → generate_sql에 재주입 → 재검증
```

단순 재시도가 아니라 "왜 틀렸는지"를 LLM에 알려주므로 수정 성공률이 높다.

### 2.4 소형 LLM 대응 설계

`llm_retry.py`의 **parse retry with format hints** 전략은 폐쇄망 소형 모델 배포를 고려한 현실적인 설계이다. 모든 구조화 출력 파싱에 재시도 + 힌트 주입 + 최종 fallback이 적용된다.

### 2.5 보안 3중 방어

입력(전처리) → 처리(SQL 검증 6계층) → 실행(재검증) 구조로, 금융 환경에 적합한 깊이 있는 보안 설계이다.

## 3. 취약점 분석 및 개선 제안

### 3.1 컨텍스트 수집의 "적합성 판단" 부재

**문제**: `collect_context`에서 ES로부터 테이블 메타 10건, 보고서 SQL 5건 등을 가져오지만, **가져온 결과가 실제로 사용자 요구사항에 적합한지 판단하는 단계가 없다.**

현재 흐름:
```
collect_context(검색 결과 수집) → 바로 generate_sql(SQL 생성)
```

있어야 하는 흐름:
```
collect_context → evaluate_context_relevance → [충분 → generate_sql | 부족 → refine_search 또는 clarify]
```

**실제 시나리오**: "지점별 외화예금 잔액 추이를 보여줘"
- ES 검색이 `외화예금`을 키워드로 테이블을 찾지만, 정작 필요한 `TB_FX_DEPOSIT_BALANCE_STAT` 대신 `TB_FX_RATE`(환율)만 반환될 수 있음
- 현재는 이 부적합한 결과를 그대로 SQL Generator에 넘김 → 엉뚱한 SQL 생성

**개선안**: `context_evaluator` 노드 추가
- 수집된 테이블이 사용자 질의의 핵심 엔티티를 커버하는지 검증
- 커버되지 않는 엔티티가 있으면 키워드를 변형하여 재검색 또는 사용자에게 확인

---

### 3.2 Query Strategy의 키워드 확장 한계

**문제**: `search_query_builder.py`에서 도메인 사전 기반 키워드 확장을 하지만, **사전에 등록되지 않은 용어나 복합 표현**에 취약하다.

**예시**:
- "연체율 추이" → 도메인 사전에 "연체율"은 있지만, "추이"가 시계열 분석을 의미한다는 매핑 없음
- "3개월 이상 미거래 고객" → "미거래"가 "거래 없음"이란 조건임을 사전이 커버하지 못함
- "카드론 vs 신용대출 비교" → 비교 분석 패턴 인식 없음

**개선안**:
1. **의도 패턴 사전** 추가: "추이"→시계열, "비교"→GROUP BY, "분포"→히스토그램 등 분석 패턴 매핑
2. **LLM 기반 query expansion**: 키워드 추출을 규칙 기반이 아닌 LLM에 위임하여 의미적 확장 수행
3. **Qdrant semantic search 강화**: 현재 manual만 검색하는데, 테이블 메타도 벡터 검색 대상에 포함

---

### 3.3 컨텍스트 토큰 예산 관리 없음

**문제**: SQL Generator의 시스템 프롬프트에 테이블 메타 10건 + 보고서 SQL 3건 + 과거 SQL 5건 + 매뉴얼 3건 + 도메인 사전이 모두 주입된다. **토큰 예산 관리 없이 전부 넣으면**:

- 소형 모델(7B~13B)에서 컨텍스트 윈도우 초과 가능
- 관련성 낮은 정보가 관련성 높은 정보를 희석 (noise injection)
- LLM이 가장 관련성 높은 테이블 대신 프롬프트 뒷부분의 테이블을 선택하는 **position bias** 발생

**개선안**:
1. **관련성 점수 기반 정렬/필터링**: 각 컨텍스트 항목에 relevance score를 부여하고 상위 N개만 주입
2. **토큰 예산 할당**: 예) 테이블 메타 40%, 보고서 SQL 25%, 과거 이력 20%, 매뉴얼 15%
3. **컨텍스트 압축**: 관련 컬럼만 발췌, 불필요한 메타데이터 제거

---

### 3.4 JOIN 경로 탐색 없음

**문제**: 복잡한 요구사항은 여러 테이블을 JOIN해야 하는데, **테이블 간 관계(FK, 공통 키)를 탐색하는 로직이 없다.**

**시나리오**: "VIP 고객의 연체 대출 건수"
- 필요 테이블: `TB_CUST_INFO` (VIP 여부) + `TB_LOAN_INFO` (연체 여부)
- JOIN 키: `CUST_NO`

현재는 LLM이 컬럼명을 보고 암묵적으로 JOIN 키를 추론하는데, 이는:
- 컬럼명이 테이블마다 다를 때 실패 (`CUST_NO` vs `CUSTOMER_ID`)
- 중간 테이블이 필요한 경우 탐색 불가

**개선안**:
1. **테이블 관계 그래프** 구축: FK 관계 또는 공통 키 기반 adjacency 정보를 ES에 인덱싱
2. **JOIN 경로 추천**: 선택된 테이블 집합에 대해 최적 JOIN 경로 제안
3. **보고서 SQL에서 JOIN 패턴 추출**: 기존 SQL의 JOIN 패턴을 별도로 인덱싱하여 참조

---

### 3.5 실행 결과 검증 부재

**문제**: SQL 실행 후 **결과의 합리성을 검증하지 않는다.**

```
execute_sql → (결과 그대로) → analyze_data 또는 format_response
```

**위험 시나리오**:
- 0건 반환: WHERE 조건 오류인지, 실제로 데이터가 없는지 구분 불가
- 비정상적 수치: 연체율 150%, 마이너스 잔액 등 비즈니스 논리 위반
- 예상과 다른 집계 단위: 월별을 요청했는데 일별 데이터 반환

**개선안**: `result_validator` 노드 추가
1. **빈 결과 처리**: 0건이면 조건 완화 제안 또는 원인 설명
2. **범위 검증**: 금융 지표별 합리적 범위 체크 (연체율 0~100%, 금액 양수 등)
3. **집계 수준 확인**: 요청한 시간 단위(월/분기/연)와 결과 정합성 확인

---

### 3.6 Multi-hop 질의 미지원

**문제**: 단일 SQL로 해결할 수 없는 **다단계 분석 요구사항**에 대한 설계가 없다.

**예시**:
- "연체율이 가장 높은 지점의 고객 특성을 분석해줘"
  1. Step 1: 연체율이 가장 높은 지점 식별
  2. Step 2: 해당 지점 고객의 특성 분석
- "전년 동기 대비 수신 잔액이 감소한 지점들의 공통점은?"
  1. Step 1: 전년/금년 수신 잔액 비교
  2. Step 2: 감소 지점 필터링
  3. Step 3: 공통 특성 분석

현재는 하나의 SQL로 처리하려 하므로 복잡도가 올라가면 품질이 급락한다.

**개선안**: `query_planner` 노드 추가
- 복합 질의를 **서브 쿼리 단계로 분해**
- 각 단계별로 SQL 생성 → 실행 → 결과를 다음 단계에 전달
- CTE(Common Table Expression) 활용 또는 순차 실행 전략

---

### 3.7 테이블 Enrichment의 환각 위험

**문제**: `table_meta_enricher.py`에서 메타 설명이 20자 미만이면 **LLM으로 설명을 생성**한다. 이는 **잘못된 테이블 설명이 생성되어 후속 SQL 생성을 오염**시킬 위험이 있다.

**시나리오**: `TB_CARD_STAT`의 설명이 빈약할 때
- LLM이 "카드 통계 테이블"로 추론 → 실제로는 "카드 실적 일배치 테이블"
- 잘못된 설명 기반으로 부적합한 SQL 생성

**현재 대응**: "추정:" 접두사를 붙이도록 프롬프트에 명시

**추가 개선안**:
1. **Enrichment 결과를 SQL 생성 프롬프트에서 원본/추정 구분하여 표시**
2. **보고서 SQL에서 해당 테이블의 실제 사용 패턴과 교차 검증**
3. **Enrichment confidence score** 부여: 컬럼명·관련 SQL·코드값 근거가 많을수록 높은 점수

---

### 3.8 코드값 매핑의 불완전성

**문제**: 금융 DB에는 코드값이 광범위하게 사용된다 (`CUST_TYPE_CD = '01'`이 "개인"인지 "기업"인지). 현재 도메인 사전에 일부 코드값 매핑이 있지만:

- ES 코드 메타 검색이 **모든 코드 테이블을 커버하지 못함**
- LLM이 코드값을 추론할 때 **오류 가능성** (예: 대출상태 '01'을 "정상"으로 추론했지만 실제로는 "신규")
- 코드값 오류는 WHERE 조건 오류로 이어져 **완전히 잘못된 결과**를 생산

**개선안**:
1. **코드 테이블 전용 인덱스**: ES에 `{테이블명}_{컬럼명} → 코드값:설명` 매핑 인덱스
2. **코드값 확인 단계**: SQL 생성 시 WHERE 조건의 코드값을 자동으로 코드 테이블과 대조
3. **불확실한 코드값 사용 시 사용자 확인**: "고객유형 '01'은 개인고객을 의미하는데, 맞으시겠습니까?"

## 5. 권장 개선 로드맵

### P0 — 즉시 개선 (잘못된 결과 생산 방지)

1. **컨텍스트 적합성 평가 노드** (`context_evaluator`)
   - 수집 결과가 질의의 핵심 엔티티를 커버하는지 검증
   - 부족 시 키워드 변형 재검색 또는 사용자 확인 분기

2. **실행 결과 검증 노드** (`result_validator`)
   - 빈 결과 원인 분석, 비정상 수치 탐지, 집계 단위 불일치 경고

3. **코드값 대조 로직**
   - SQL 생성 시 WHERE 조건의 코드값을 코드 테이블과 자동 대조

### P1 — 단기 개선 (SQL 품질 향상)

4. **JOIN 경로 탐색**
   - 테이블 관계 그래프 또는 보고서 SQL JOIN 패턴 참조

5. **컨텍스트 토큰 예산 관리**
   - relevance 기반 필터링 + 소스별 토큰 할당

6. **LLM 기반 query expansion**
   - 규칙 기반 키워드 추출의 한계를 의미적 확장으로 보완

### P2 — 중기 개선 (고도화)

7. **Multi-hop 쿼리 플래너**
   - 복합 질의를 단계별로 분해 실행

8. **Enrichment 교차 검증**
   - LLM 생성 설명을 실제 SQL 사용 패턴과 대조

9. **의도 패턴 사전**
   - "추이", "비교", "분포" 등 분석 유형 인식 매핑

---

## 6. 총평

전체적으로 **기본 파이프라인 설계가 매우 견고**하다. 특히 다중 소스 병렬 탐색, 유사 테이블 판별, 검증 피드백 루프, 소형 LLM 대응은 실무에서 검증된 패턴을 잘 반영하고 있다.

가장 큰 아쉬움은 **"가져온 정보의 품질 평가"와 "생성된 결과의 사후 검증"이 약하다**는 점이다. 현실에서 데이터 분석가가 SQL을 작성할 때:

1. 테이블을 찾고 → **"이게 진짜 맞나?" 교차 확인** → SQL 작성
2. SQL 실행 후 → **"결과가 합리적인가?" 직감적 검증** → 보고

이 두 가지 **인간의 판단 단계**가 현재 파이프라인에서는 약하므로, 이 부분을 보강하면 잘못된 SQL 생성과 잘못된 결과 전달이라는 두 가지 핵심 리스크를 크게 줄일 수 있다.
