- 검토일: 2026-03-19
- 검토자: design-critic
- 검토 대상: `docs/architecture.md`
- 비교 대상: 실제 구현 코드 (src/, src/agents/nodes/prompts/)

## 총평

설계 문서는 전반적으로 실제 구현과 **높은 수준의 일관성**을 유지하고 있으며,
특히 3.4.1절 테이블 설명 보강 전략, 3.3절 유사 테이블 구분 전략, SQL 재생성 루프
등 핵심 메커니즘이 코드와 잘 정렬되어 있다. 첫 번째 검토(2026-03-18)에서 지적된
P0/P1 항목 대부분이 구현에 반영되었음을 확인했다.

다만, **설계 문서가 구현을 따라가지 못한 부분**이 여럿 존재하며,
특히 5절(노드별 상세 설계)에서 최근 구현된 기능(테이블 보강, 유사 테이블 검증,
SQL 재생성 루프, 멀티턴 명확화 상세)에 대한 기술이 빠져 있어
**문서만 읽는 사람이 실제 시스템의 동작을 오해할 가능성**이 있다.

## 1. 구현과의 불일치 사항

### [P1] 1-1. PipelineState 필드 누락 — 문서 vs 코드 (state.py)

- **문제**: 설계 문서 2.4절의 PipelineState 정의(L124~L166)에 다음 필드가 누락됨:
  - `awaiting_clarification: bool` (L122, state.py)
  - `clarification_turns: int` (L123, state.py)
  - `sql_retry_count: int` (L132, state.py)
  - `validation_feedback: str` (L133, state.py)
  - `table_selection_verdict: str` (L136, state.py)
  - `table_selection_warnings: list[str]` (L137, state.py)
  - `IntentType.UNKNOWN` 값 (L18, state.py)
  - `QueryStatus.AWAITING_CLARIFICATION`, `SQL_RETRY` (L27, L31, state.py)

- **근거**: 설계 문서의 PipelineState는 11개 상태(status)를 언급하지만(L164),
  실제 구현은 13개(PENDING~ERROR). 또한 멀티턴/재생성 루프가 핵심 아키텍처인데
  그 제어 필드가 문서에 없으면, 신규 팀원이 상태 전이를 이해할 수 없다.
- **대안**: 2.4절 PipelineState 코드 블록에 빠진 필드를 모두 추가하고,
  각 필드의 역할을 주석으로 명시. 특히 `sql_retry_count`, `validation_feedback`,
  `table_selection_verdict`는 각각 관련 절(3절, 4절)로 크로스레퍼런스.

### [P1] 1-2. 분기 포인트 수 불일치 — "4곳" vs 실제 5곳

- **문제**: L115에서 "분기 포인트 4곳"이라고 명시하지만, 실제 구현(pipeline.py)에는
  조건부 분기가 **4곳** 등록되어 있으나 `validate_sql` 이후 분기에서 `clarify`로의
  테이블 모호성 분기가 추가되어 있음(pipeline.py L206-L214). 문서 L118에서는
  "재생성 루프(최대 2회) 또는 테이블 모호성 시 명확화 분기"를 언급하고 있으나,
  2.3절 ASCII 다이어그램(L94~L113)에는 이 경로가 표현되지 않음.
- **근거**: 2.3절 다이어그램에서 `validate_sql` 이후 경로는 "검증 실패 → error_end"와
  "검증 통과 → execute_sql" 두 가지만 표시. 실제로는 4가지 경로:
  (1) `generate_sql` 재시도, (2) `execute_sql`, (3) `clarify` 테이블 확인, (4) `error_end`.
- **대안**: 2.3절 다이어그램을 실제 분기 4경로로 업데이트.

### [P2] 1-3. SQL 검증 상세 — 금지 패턴 수 불일치

- **문제**: 설계 문서 4.1절(L443)에서 "금지 패턴 검사 (DML/DDL 9개 키워드)"라고 기술.
  5.6절(L598)에서는 "금지패턴(5)"라고 기술. 실제 sql_validator.py의
  `FORBIDDEN_PATTERNS`에는 **15개 패턴**이 등록되어 있음(L33~L111).
- **근거**: 문서의 "9개" → "5개" → 실제 "15개"로 세 곳이 모두 다른 숫자를 보여주고 있어,
  어느 것이 정확한지 혼란을 줌.
- **대안**: 4.1절에서 정확한 패턴 수를 업데이트하고, 카테고리별로 분류하여 기술
  (DML/DDL 1패턴 + 프로시저 2 + 시스템 카탈로그 1 + 다중 쿼리 1 + 파일 I/O 4 +
  시간 인젝션 4 + 주석 2 + xp_ 1 + UNION 1 = 17개 조건 15개 패턴).

### [P2] 1-4. PII 컬럼 수 불일치 — "6개" vs 실제 28개

- **문제**: 설계 문서 4.1절(L445)과 5.6절(L598)에서 "PII 컬럼(6개)"라고 기술.
  실제 sql_validator.py의 `PII_COLUMNS` 집합에는 **28개 컬럼명**이 등록되어 있음
  (L114~L128). 또한 `MASKING_COLUMNS`(L131~L142)로 별도 14개 마스킹 대상이 존재.
- **근거**: 6개 카테고리(주민번호, 카드번호, 계좌번호, 비밀번호, CVC, 외국인등록번호)는
  맞지만 각 카테고리에 여러 변형 컬럼명이 등록된 것. "6개"는 카테고리 수이지 컬럼 수가
  아님. 문서를 읽는 사람이 "6개 컬럼만 검사하면 되는구나"로 오해할 수 있음.
- **대안**: "6개 카테고리, 28개 컬럼명 변형"으로 정정. 마스킹 대상도 별도 언급.

### [P2] 1-5. SQL 인젝션 패턴 수 불일치 — "4패턴" vs 실제 12패턴

- **문제**: 설계 문서 5.1절(L550)에서 전처리 노드의 기능을 "SQL 인젝션 패턴 감지 (4패턴)"
  이라고 기술. 실제 preprocessor.py의 `_SUSPICIOUS_PATTERNS`에는 **12개 패턴**이
  등록되어 있으며(L31~L53), 이에 더해 `detect_prompt_injection`으로 30+개의 프롬프트
  인젝션 패턴도 추가 검사함.
- **근거**: 첫 번째 리뷰(2026-03-18)에서 P0으로 지적된 보안 강화가 코드에는 반영되었지만
  문서 업데이트가 누락됨.
- **대안**: 5.1절을 "SQL 인젝션 (12패턴) + 프롬프트 인젝션 (30+패턴) + 유니코드 정규화"
  로 업데이트.

### [P2] 1-6. 커넥터 아키텍처 다이어그램 불일치 — "Dummy 데이터 (6 테이블)" 수치 미확인

- **문제**: 설계 문서 6절(L644)에서 Dummy ES 데이터를 "(6 테이블)"이라고 기술하지만,
  실제 더미 데이터의 테이블 수를 확인할 필요가 있음. 또한 "Dummy 이력 (5건 SQL)",
  "Dummy 매뉴얼 (5건 문서)" 수치에서, postgres_connector.py의 `DUMMY_SQL_HISTORY`는
  실제 5건(L94~L125)으로 일치하나, Qdrant와 ES의 더미 데이터 건수는 별도 확인 필요.
- **대안**: 커넥터별 더미 데이터 건수를 확인 후 정확히 반영하거나 "N건"으로 동적 표현.

## 2. 구현되었으나 설계 문서에 누락된 내용

### [P1] 2-1. 5.4절 context_collector 노드에 보강 단계 미기술

- **문제**: 5.4절(L572~L579) context_collector 노드 설명에서 수집 소스 5가지만
  나열하고 있으나, 실제 `search_context_assembler.py`의 `collect_context()`에서는

  ```
  |       | Stage 2: 유사 테이블 그룹 감지 + 구분 가이드 생성 (similar_table_resolver.py) |
  ```

### [P1] 2-2. 3.7절 SQL 생성 프롬프트에 enriched_description 반영 미기술

- **문제**: 3.7절(L386~L424)의 프롬프트 구조 다이어그램에서 "2. 테이블 정보"

- **근거**: 이 보강 설명이 SQL 정확도에 직접 영향을 미치는 핵심 요소인데,

### [P1] 2-3. SQL 재생성 루프 메커니즘 상세 누락

- **문제**: 2.3절(L118)에서 "검증 실패 시 재생성 루프(최대 2회)"를 한 줄로 언급하지만,
  실제 메커니즘의 핵심 요소들이 설명되지 않음:
  - `validation_feedback` 생성 (sql_validator.py L211~L221)
  - `SQL_VALIDATION_FEEDBACK_SECTION` 프롬프트 주입 (system_prompts.py L216~L221)
  - `sql_retry_count` 증가 타이밍 (sql_generator.py L122)
  - 재시도 시 이전 검증 오류/피드백 초기화 (sql_generator.py L184~L185)
- **근거**: 이 루프는 첫 번째 리뷰에서 P1로 지적되어 구현된 핵심 기능.
  MAC-SQL (Wang et al., 2024)의 iterative refinement과 유사한 패턴으로,
  피드백 주입이 정확도에 직접 기여하는 핵심 메커니즘임.
- **대안**: 별도 소절 "4.6 SQL 재생성 루프" 또는 2.3절 확장으로 상세 흐름을 추가:
  ```
  validate_sql 실패
    → validation_feedback 생성 (실패 SQL + 오류 목록)
    → sql_retry_count < 2 이면 generate_sql 재호출
    → generate_sql 진입 시 retry_count 증가
    → 프롬프트에 [이전 시도 오류] 섹션 주입
    → 새 SQL 생성 → validate_sql 재검증
    → 2회 초과 시 error_end (사용자 친화적 안내)
  ```

### [P2] 2-5. 유사 테이블 구분 전략(3.3절)에 점수 메커니즘 미기술

### [P2] 2-6. 유니코드 정규화(NFKC) 방어 전략 미기술
