## 총평

전체적으로 **학술 근거와 프레임워크 제약을 잘 반영한 설계**다. 특히 다음 3가지가 강점이다:

1. 시그널 수집(분산)과 판정(집중)의 분리 — 단일 책임 원칙을 명확화 시스템에 적용
2. 오답 비용 기반 3단계 분류 — "무조건 질문"에서 "선택적 질문"으로의 전환
3. auto_resolved + 정정 피드백 루프 — 추론 실패 시 복구 경로 확보

그러나 **6건의 검증되지 않은 가정, 4건의 실패 시나리오, 3건의 구현 실현성 문제**가 발견되었다. 이 중 P0 1건, P1 3건은 구현 전 해결이 필요하다.

## 가정 검증 결과

### 가정 A1: "오답 비용을 높음/중간/낮음으로 사전 분류할 수 있다"

**검증 결과: 미검증 — [P0] 치명적**

설계의 핵심 축인 오답 비용 3단계(높음/중간/낮음)가 **누가, 어떤 시점에, 어떤 기준으로** 판정하는지 정의되어 있지 않다.

- 설계 문서는 "산출식 선택, 테이블 선택 → 높음", "기간 기준 → 중간", "SELECT 컬럼 → 낮음"이라는 예시를 제시하지만 이것은 **정적 매핑 예시**이지 판정 로직이 아니다
- 실제로는 동일한 모호성 유형이 맥락에 따라 오답 비용이 달라진다:
  - "기간 기준" 모호성이 단순 조회면 → 중간 (틀려도 재조회 가능)
  - "기간 기준" 모호성이 연체율 산출식의 기준일이면 → **높음** (데이터 자체가 완전히 달라짐)
- 따라서 오답 비용은 모호성 유형 단독으로 결정할 수 없고, **모호성 유형 × 질의 맥락(사용 목적)**의 조합이 필요하다

**대안**:

```
오답 비용 판정 = f(모호성 유형, 질의 맥락)

판정 규칙 예시:
- AmbiSchema (테이블 선택)        → 항상 높음 (데이터 원천이 달라짐)
- AmbiIntent (연산 방식)           → 항상 높음 (잔액 vs 건수는 완전히 다른 결과)
- AmbiValue (코드값)              → 높음 (해당 코드의 존재 여부가 결과 건수를 좌우)
- AmbiRef (기간) + 단순 조회       → 중간 (기본값 제안)
- AmbiRef (기간) + 산출식 포함     → 높음 (산출 결과가 완전히 달라짐)
- AmbiSource (산출식 출처)         → 항상 높음 (금융 지표 정확성)
- Ambig SELECT/WHERE Column       → 낮음 (포괄 조회로 해소)
```

핵심: **"중간" 등급은 사실상 위험한 편의적 분류**다. 금융 도메인에서 "틀려도 결과에서 알아챌 수 있음"이라는 가정은 위험하다 — 사용자가 IT 비전문가이기 때문에 결과가 틀려도 알아채지 못할 가능성이 높다. 가능하면 **높음/낮음 이진 분류**로 단순화하고, 낮음이 아닌 것은 모두 질문하는 것이 안전하다.

### 가정 A2: "도메인 기본값 사전이 충분한 커버리지를 가질 수 있다"

**검증 결과: 부분적 타당 — [P2] 개선 필요**

도메인 기본값의 3가지 출처(업무 매뉴얼 RAG, 과거 SQL 이력, 수동 yaml)는 합리적이나, 커버리지 문제가 있다:

- **업무 매뉴얼(Qdrant)**: 매뉴얼은 규정·절차 중심이라 "여신 실적 = 실행 금액"과 같은 **암묵적 업무 관행**이 명시되어 있을 가능성이 낮다
- **과거 SQL 이력**: "80% 이상이 동일 해석이면 기본값"이라는 기준이 있지만, SQL 이력이 편향되어 있을 수 있다 (특정 부서가 대량 사용한 경우)
- **수동 yaml**: 이것이 결국 핵심 출처가 될 가능성이 높으나, **누가 유지보수하는가?** 가 정의되어 있지 않다

**대안**: 도메인 기본값 사전의 초기 구축 방법을 명시한다. 제안:
1. 골든셋에서 명확화 없이 정답이 도출된 케이스를 자동 추출하여 초기 사전 시딩
2. 사용자 정정 이력(auto_resolved → 정정)을 기록하여 사전 자동 보강
3. 사전 유지보수 책임자/주기를 운영 가이드에 명시

### 가정 A3: "사용자 정정을 자동으로 감지하여 interrupt resume 경로로 라우팅할 수 있다"

**검증 결과: 미검증 — [P1] 중대**

"아니, 전년 전체 대비로 해줘"가 들어왔을 때, 이것이 **새로운 질의인지 이전 결과에 대한 정정인지** 어떻게 판별하는가?

- 현재 history_resolver는 CONTINUE/SKIP/UNSURE로 분류하는데, "정정"이라는 분류가 없다
- LLM이 "이전 결과에 대한 정정인지" 판단해야 하는데, 이것 자체가 추가 LLM 호출이다
- 오분류 시 위험:
  - 정정인데 새 질의로 처리 → 전체 재실행 (비효율이지만 정확도 손실 없음)
  - 새 질의인데 정정으로 처리 → **이전 체크포인트에서 부분 재개하여 엉뚱한 결과 생성** (P1)

**대안**: 정정 감지를 history_resolver에 CORRECTION 판정을 추가하되, **false positive를 "새 질의 처리"로 폴백**시킨다. 즉, 정정 판정에 실패하면 안전하게 전체 재실행한다. 이렇게 하면 오분류의 최악 케이스가 "비효율"이지 "오답"이 아니다.

### 가정 A4: "auto_resolved 항목의 추론 근거를 사용자가 읽고 필요 시 정정할 것이다"

**검증 결과: 낙관적 — [P2] 개선 필요**

user-interaction.md의 사용자 프로필: "IT 관련 지식이 없는 은행 일반 직원". 이 사용자들이 "전년 동월 기준으로 조회했습니다"라는 안내를 읽고, 그것이 자신의 의도와 다른지 판단하여 능동적으로 정정할 가능성은 높지 않다.

**근거**: Uber QueryGPT 블로그에서도 "중간 결과 확인"을 구현했으나, 사용자가 테이블 목록을 보고 편집하는 비율이 낮았다고 암시한다 (정확 수치 미공개).

**대안**:
- auto_resolved 안내를 단순 텍스트가 아닌 **확인 버튼(CONFIRM 형태)**으로 제시 — 사용자가 "맞아요/아니요"를 클릭하는 능동적 확인 유도
- 단, 이것은 사실상 "추론"이 아닌 "질문"이 되므로 사용자 피로도와의 트레이드오프
- **절충안**: 오답 비용 "높음"인 auto_resolved만 CONFIRM 형태로 제시, "낮음"은 텍스트 안내만

### 가정 A5: "시그널을 AmbiSQL 7종으로 매핑하는 것이 폐쇄망 LLM에서 안정적으로 작동한다"

**검증 결과: 미검증 — [P1] 중대**

현재 설계에서 시그널의 모호성 유형 분류는 **LLM이 수행해야** 한다 (각 노드에서 시그널을 생성할 때 유형을 판정). Solar Pro 2 70B 또는 Qwen3.5 397B에서 7종 분류의 정확도가 검증되지 않았다.

- AmbiSQL 논문은 GPT-4o 기반 In-context Learning을 사용했고, 모호성 탐지 정밀도 87.2%
- 70B급 모델에서는 이보다 낮을 가능성이 높다
- 분류 오류 → PolicyEngine의 판정이 잘못됨 → 질문해야 할 때 질문 안 함 또는 그 반대

**대안**:
1. 7종 분류를 LLM에만 의존하지 않고, **규칙 기반 사전 분류 + LLM 보완** 하이브리드로 구현
   - AmbiSchema: 후보 테이블 2개 이상 → 규칙으로 감지 가능
   - AmbiValue: ES 코드 메타에 매칭 실패 → 규칙으로 감지 가능
   - AmbiRef: 날짜/기간 키워드 있으나 구체적 값 없음 → NER/패턴 매칭으로 감지 가능
   - AmbiIntent: 여러 해석 가능한 키워드 → LLM 의존 불가피
2. 분류 실패 시 폴백: 유형 불분명 → 질문 (안전한 방향)

### 가정 A6: "각 노드가 시그널만 추가하고 판정하지 않는 것이 기존 설계 변경을 최소화한다"

**검증 결과: 부분적 타당 — [P3] 제안**

현재 01-strategy.md의 설계는 각 노드가 `pending_clarification`을 **직접 세팅**한다. 제안된 2계층 구조는 이를 `uncertainty_signals`로 변경하므로, 01-strategy.md의 Phase 2 변경사항(5개 트리거 노드 마이그레이션)과 충돌한다.

기존 설계에서 이미 HandlerRegistry가 유형별 처리를 담당하므로, PolicyEngine은 HandlerRegistry와 역할이 겹칠 수 있다:
- HandlerRegistry: 응답 **검증/정규화** (응답 후)
- PolicyEngine: **질문 여부 판정** (응답 전)

**대안**: PolicyEngine을 별도 모듈이 아닌 `clarification_handler` 노드의 **진입부 로직**으로 통합한다. 즉:

```python
async def clarification_handler_node(state):
    signals = state["uncertainty_signals"]

    # PolicyEngine 로직 (진입부)
    resolved, remaining = policy_engine.evaluate(signals, state)

    # 자동 해소된 시그널 기록
    if resolved:
        state["auto_resolved"].extend(resolved)

    # 질문이 필요한 시그널이 남아있으면 interrupt
    if remaining:
        best_signal = select_highest_value(remaining)
        request = build_clarification_request(best_signal)
        answer = interrupt(request)
        ...
```

이렇게 하면 새 모듈이 아닌 기존 clarification_handler 노드의 확장으로 구현 가능하다.

## 주요 비판 사항

### [P0] 오답 비용 판정 기준의 부재

**비판**: 설계의 핵심 메커니즘인 오답 비용 3단계 분류에 **판정 주체와 판정 로직**이 정의되어 있지 않다. 예시만 있고 알고리즘이 없다.

**근거**: 가정 A1 참조. 동일한 AmbiRef(기간 모호성)가 맥락에 따라 높음/중간으로 갈린다.

**대안**:
- 단기: 모호성 유형 × 질의 맥락의 2차원 매트릭스를 정적 규칙으로 정의하고, 금융 도메인 전문가와 검증
- 중기: 골든셋 평가 결과에서 "추론으로 진행했으나 오답이 된 케이스"를 추적하여 규칙 자동 보강
- **핵심 권고**: "중간" 등급을 폐지하고 높음/낮음 이진 분류로 단순화. 금융 도메인에서 "어느 정도 맞을 것"이라는 추론은 위험하다.

### [P1] 정정 감지의 오분류 위험

**비판**: 사용자의 후속 입력이 "정정"인지 "새 질의"인지의 판별이 설계에서 누락. 오분류 시 이전 체크포인트 기반 부분 재개로 엉뚱한 결과가 생성될 수 있다.

**근거**: 가정 A3 참조.

**대안**: CORRECTION 분류를 추가하되, 확신도가 낮으면 안전하게 새 질의로 폴백. 오분류의 worst case를 "비효율"로 제한한다.

### [P1] 폐쇄망 LLM의 7종 모호성 분류 정확도 미검증

**비판**: AmbiSQL 7종 분류가 GPT-4o 기준 87.2%인데, Solar Pro 2 70B에서의 정확도가 불명. 분류 오류가 PolicyEngine 전체의 판정 품질을 좌우한다.

**근거**: 가정 A5 참조.

**대안**: 규칙 기반 사전 분류(AmbiSchema, AmbiValue, AmbiRef 3종은 규칙으로 커버 가능) + LLM은 AmbiIntent, AmbiSource 등 규칙으로 커버 불가능한 유형만 담당.

### [P1] 복수 시그널 간 의존 관계 미고려

**비판**: "최고 정보가치 시그널 1개 선택"이라고 했으나, 시그널 간에 **의존 관계**가 있을 수 있다. 예: AmbiIntent("잔액 vs 건수") 해소 후에야 AmbiSchema("어떤 테이블")가 결정 가능한 경우. 이때 AmbiSchema를 먼저 물어보면 의미가 없다.

**근거**: EIG 시스템(arXiv 2507.06467)은 후보 SQL 분포 위에서 정보이득을 계산하여 이 문제를 처리하지만, 설계에서는 "규칙 기반 우선순위"로 근사한다고만 언급. 의존 관계를 반영하는 구체적 규칙이 없다.

**대안**: 시그널 의존 관계를 반영한 정적 우선순위를 명시한다:

```
우선순위 (의존 관계 반영):
1. AmbiIntent (의도) — 의도가 확정되어야 나머지가 의미 있음
2. AmbiSource (산출식 출처) — 산출식이 확정되어야 테이블/기간이 결정됨
3. AmbiSchema (테이블) — 테이블이 확정되어야 컬럼/기간이 결정됨
4. AmbiValue (코드값)
5. AmbiRef (기간)
6. Ambig SELECT/WHERE Column (포괄 조회)
```

### [P2] auto_resolved의 감사 추적 형식 미정의

**비판**: 금융 도메인에서 "시스템이 자동으로 판단한 것"은 감사 시 특히 주목받는 영역이다. auto_resolved의 감사 로그 형식이 정의되어 있지 않다. 특히 "추론으로 진행했다가 사용자가 정정한 케이스"는 시스템 판단 오류의 증거로 규제 감사에서 요구될 수 있다.

**대안**: auto_resolved를 ClarificationEntry와 동일한 감사 로그 체계에 통합한다:

```python
class AuditEntry(BaseModel):
    entry_type: Literal["clarification", "auto_resolved", "correction"]
    timestamp: datetime
    ambiguity_type: str
    resolution: str
    resolution_source: str   # "user_answer" | "domain_default" | "inferred" | "user_correction"
    original_auto_value: str | None = None  # 정정 시: 원래 추론값
```

### [P2] PolicyEngine의 상태 의존성으로 인한 테스트 복잡도

**비판**: PolicyEngine이 `state` 전체를 참조하여 오답 비용을 평가한다면 (예: "산출식 포함 여부"를 판단하려면 `normalized_query`와 `knowledge_items`를 참조해야 함), 단위 테스트가 복잡해진다.

**대안**: PolicyEngine의 입력을 `uncertainty_signals` + `query_context_summary`(필요한 맥락의 요약)로 제한한다. 전체 state가 아닌 명시적 인터페이스를 통해 필요한 정보만 전달.

## 실패 시나리오

### 시나리오 F1: 오답 비용 "낮음"으로 분류된 추론이 실제로는 치명적 오답

**상황**: "주요 여신 지표 보여줘" → Ambig SELECT로 분류 → 포괄 조회 → 그런데 "주요"가 특정 KPI 3개를 의미하는 부서별 관행이 있었고, 다른 지표가 포함되어 보고서에 잘못된 수치가 사용됨.

**영향**: 금융 보고서 정확성 문제 → 규제 리스크

**완화**: "낮음" 등급 항목도 auto_resolved에 기록하고, 결과에 "포함된 지표: A, B, C, D, E (특정 지표만 필요하시면 말씀해 주세요)" 안내를 명시적으로 포함. 이 안내가 **결과 테이블 상단에 bold로** 노출되어야 한다.

### 시나리오 F2: 도메인 기본값 사전의 오래된 항목

**상황**: "여신 실적 = 실행 금액"이 과거에는 맞았으나, 내부 정책 변경으로 "실적 = 실행 건수 + 금액 합산"으로 변경. 사전이 업데이트되지 않아 사용자가 모르는 사이에 과거 기준으로 조회.

**영향**: 지속적으로 잘못된 데이터 제공

**완화**: 도메인 기본값에 `valid_until` 또는 `last_verified` 필드를 추가하고, 일정 기간 미검증 항목은 자동으로 비활성화하거나 CONFIRM 형태로 전환.

### 시나리오 F3: 시그널 폭증 — 매우 모호한 질의

**상황**: "작년 실적 전체 다 보여줘" → AmbiIntent + AmbiRef + AmbiSchema + Ambig SELECT → 4개 시그널 동시 발생

**영향**: PolicyEngine이 1개만 선택하여 질문 → 답변 → 다시 시그널 3개 → 질문 → ... → 3~4회 왕복으로 사용자 피로

**완화**: 시그널 3개 이상 시 "질문 1개"가 아닌 **"현재 이해한 내용 요약 + 부족한 정보 2~3개를 한 번에 묻는 복합 질문"** 형태로 전환. PRACTIQ의 4-turn 구조가 이를 지원한다.

### 시나리오 F4: 추론 → 정정 → 추론 → 정정 반복

**상황**: 사용자가 auto_resolved 안내를 보고 정정 → 시스템이 다른 측면을 다시 추론 → 사용자가 또 정정 → "차라리 처음부터 물어봐" 상황

**영향**: 사용자 신뢰도 하락

**완화**: auto_resolved 정정이 **2회 이상 발생**하면, 해당 세션의 남은 모호성은 모두 질문 모드로 전환. 이 임계값을 설정값으로 관리.

## 아키텍처 대안 비교

### 대안 1: DASG 비용 모델 공식 적용 (VoC > CoD)

**장점**: 오답 비용을 수학적으로 정의 (VoC = 정확도 향상 기대값, CoD = 사용자 부담)
**단점**: VoC 계산에 후보 SQL 생성이 필요 → LLM 호출 2~3회 추가. 폐쇄망 모델에서 비용 과다.
**판정**: 현 설계(규칙 기반)가 폐쇄망 제약에서 더 실용적. 단, 온라인 환경(Claude API)에서는 DASG 비용 모델 적용을 장기 옵션으로 열어두는 것을 권고.

### 대안 2: 오답 비용 분류 없이, 무조건 "추론 + 안내" 전략

**장점**: PolicyEngine 복잡도 대폭 감소. 항상 추론하고 항상 안내.
**단점**: 테이블 선택, 산출식 선택 같은 치명적 모호성도 추론으로 넘어감 → 금융 보고 정확도 위험.
**판정**: 금융 도메인에서 기각. AmbiSchema, AmbiSource는 반드시 질문해야 한다.

### 대안 3: 오답 비용을 높음/낮음 이진 분류로 단순화

**장점**: "중간" 등급의 모호한 판정 기준 제거. 높음이 아니면 추론.
**단점**: 일부 "질문했으면 더 정확했을" 케이스를 놓칠 수 있음.
**판정**: **권고 대안**. 금융 도메인에서 "중간"은 판단자에 따라 높음이 될 수도 있어 위험. 이진 분류 + auto_resolved 안내로 충분히 커버 가능.

## 합의 추천 설계 방향

> **참고**: 이 리뷰 이후 추가 논의를 거쳐 최종 설계가 확정되었다.
> 최종 설계: `docs/research/20260331-clarification-judgment-architecture.md`

### 본 리뷰의 권고 (원본 유지)

1. **오답 비용을 높음/낮음 이진 분류로 단순화**한다. "중간"을 없앤다. 높음이 아닌 것은 추론 + auto_resolved 안내.

2. **높음의 기준**: 결과 데이터의 원천(테이블), 구조(연산 방식), 지표 정의(산출식)가 달라지는 모호성. 즉, AmbiSchema, AmbiIntent, AmbiValue, AmbiSource는 높음. AmbiRef는 맥락에 따라 판정하되, 산출식 연관 시 높음.

3. **auto_resolved 안내는 결과 상단에 반드시 포함**하고, 정정 2회 이상 시 남은 모호성은 질문 모드 전환.

4. **7종 분류는 규칙 기반 + LLM 하이브리드**로 구현하여 폐쇄망 LLM 의존도를 낮춘다.

5. **정정 감지는 안전한 방향으로 폴백** — 확신도 낮으면 새 질의로 처리.

6. **PolicyEngine은 clarification_handler 노드의 진입부 로직으로 통합** — 별도 모듈이 아닌 기존 설계의 자연스러운 확장으로 구현.

| 본 리뷰 권고 | 최종 확정 | 변경 사유 |
| --- | --- | --- |
| 오답 비용 이진 분류 (유형 기반) | ASK/INFER 이진 (LLM 맥락 판정) | 유형만으로는 맥락 손실. LLM이 전체 맥락 보유 |
