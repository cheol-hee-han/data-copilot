## 1. 사이드바 (세션 목록) -- localStorage에서 REST API 전환

### REQ-SB-01: 세션 목록 API 연동

- **설명**: 현재 SB 모듈(line 1449~1517)은 localStorage에서 세션 배열을 읽고 저장한다. 이를 `GET /api/sessions` 호출로 교체해야 한다. init() 시 API를 호출하여 세션 목록을 받아오고, renderList()로 렌더링한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 _sessions는 동기적으로 localStorage에서 로드되지만(line 1452), API 호출은 비동기이므로 init()을 async로 전환하거나 콜백 패턴을 적용해야 한다. 또한 현재는 최대 20개 세션만 저장하는 제한(line 1515)이 클라이언트에 있으나, API 전환 후에는 서버 측 페이지네이션/제한으로 이동한다.
- **구현 방향**: _save() 함수를 제거하고, 세션 생성/삭제/업데이트 시 개별 API를 호출한 후 목록을 갱신하는 방식으로 변경.

### REQ-SB-02: 세션 제목 표시 형식 변경

- **설명**: 현재 세션 제목은 사용자 첫 메시지의 앞 30자를 잘라서 사용한다(line 1463). 새 설계에서는 서버가 첫 질의 앞 50자를 title로 저장한다. 클라이언트는 서버가 제공하는 title을 그대로 사용한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 제목 생성 로직이 클라이언트에서 서버로 이동. updateTitle() 함수는 서버 응답의 title 필드를 반영하는 것으로 단순화.

### REQ-SB-03: 세션 목록에 last_active 표시

- **설명**: 새 데이터 모델에 last_active 필드가 포함된다. 사이드바의 각 세션 항목에 "방금 전", "5분 전", "어제" 등 상대 시간을 표시하여 사용자가 최근 대화를 쉽게 식별할 수 있도록 한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 세션 항목(line 1494~1499)에는 시간 정보가 표시되지 않고 제목만 보인다.
- **UX 근거**: 은행 직원이 여러 분석 요청을 병행할 때, 어떤 대화가 가장 최근인지 시각적으로 구분할 수 있어야 한다. 상대 시간은 절대 타임스탬프보다 인지 부하가 낮다.

### REQ-SB-04: 세션 목록 로딩 상태 표시

- **설명**: API 호출 중 사이드바에 로딩 스켈레톤 또는 스피너를 표시한다. 현재는 localStorage 동기 로드이므로 로딩 상태가 불필요했지만, 네트워크 호출로 전환되면 빈 목록이 잠시 보이는 문제가 발생한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 init()(line 1451~1453)은 동기적이므로 로딩 상태가 없다.
- **구현 방향**: chatList 영역에 3~4개의 스켈레톤 chat-item을 표시한 후 API 응답 시 실제 데이터로 교체.

### REQ-SB-05: 세션 목록 새로고침/폴링

- **설명**: 다른 탭이나 디바이스에서 생성된 세션을 반영하기 위해, 주기적 폴링(30초~1분) 또는 포커스 복귀 시 갱신 전략을 적용한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: localStorage 기반에서는 동일 브라우저 내 탭 간 동기화만 가능했다.
- **UX 근거**: 은행 직원이 여러 브라우저 탭을 열어두고 작업하는 것은 흔한 시나리오이다. visibilitychange 이벤트로 탭 복귀 시 목록을 갱신하면 자연스러운 동기화가 가능하다.

## 2. 대화 복원 -- 과거 세션 로드 시 2-tier 전략

### REQ-CR-01: Tier 1 즉시 로드 구현

- **설명**: 사이드바에서 세션 클릭 시 `GET /api/sessions/{session_id}`를 호출하여 전체 턴의 Tier 1 데이터(turn_id, turn_seq, role, content, turn_type, status, is_liked, is_downloaded, has_metadata, created_at)를 받아 메시지를 렌더링한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 loadSession()(line 1469~1476)은 localStorage의 msgs 배열을 순회하며 RD.render()를 호출한다. 메시지 데이터가 {role, text, time} 3개 필드뿐이지만, 새 모델에서는 turn_type, status, is_liked 등 추가 필드를 처리해야 한다.
- **구현 방향**: MS.create() 호출 시 서버 턴 데이터의 필드를 매핑하는 어댑터 함수 필요. turn_type=clarification이면 명확화 질문 UI로, turn_type=error이면 에러 표시로 분기.

### REQ-CR-02: Tier 2 지연 로드 (metadata)

- **설명**: 턴에 has_metadata=true인 경우, 해당 턴의 분석 과정 보기 버튼 클릭 시 `GET /api/turns/{turn_id}/metadata`를 호출하여 insight, visualization, sql_result, executed_sql, trace_log, clarification 데이터를 받아온다. SVG 차트(100~500KB/개)와 trace_log는 사용자가 명시적으로 요청할 때만 로드한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 insight/visualization은 WebSocket 스트림에서 실시간으로 받아 msg.insight, msg.visualization에 저장된다(line 1238~1239). 과거 세션 복원 시에는 이 데이터가 없으므로, 지연 로드 메커니즘이 새로 필요하다.
- **구현 방향**: insight 버튼(line 747) 클릭 핸들러를 확장하여, msg.insight가 null이고 has_metadata=true이면 API 호출 후 renderInsight()를 실행. 로딩 중에는 insight-slot에 스피너 표시.

### REQ-CR-03: 대화 복원 시 로딩 UX

- **설명**: 과거 세션 로드 시 채팅 영역에 로딩 표시를 하고, 턴이 순차적으로 나타나는 애니메이션을 적용한다. 대량의 턴(20개 이상)이 있는 경우 배치 렌더링 또는 가상 스크롤을 고려한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 loadSession()은 forEach로 즉시 모든 메시지를 렌더링한다(line 1475).
- **UX 근거**: 네트워크 지연(100~500ms)이 발생하는 동안 빈 채팅 영역이 보이면 사용자는 오류로 인식할 수 있다. skeleton 메시지 버블 패턴이 체감 속도를 높인다.

### REQ-CR-04: 복원된 대화의 스크롤 위치

- **설명**: 과거 세션 로드 완료 후 가장 마지막 메시지(최신 턴)로 자동 스크롤한다. 사용자가 수동으로 스크롤 중이면 자동 스크롤을 억제한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: autoScroll()(line 1548)이 존재하지만, 과거 세션 로드 시에는 모든 메시지 렌더 후 한 번만 호출하면 된다. _userScrolledUp 플래그를 resetAutoScroll()로 초기화.

### REQ-CR-05: 복원된 대화에서 이어서 질문하기

- **설명**: 과거 세션을 로드한 후, 사용자가 새 메시지를 입력하면 해당 세션의 연속된 대화로 처리되어야 한다. WebSocket 세션 ID를 서버의 session_id와 연결하여, 서버가 대화 컨텍스트를 유지할 수 있도록 한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 WebSocket 세션 ID는 클라이언트에서 timestamp 기반으로 생성되며(line 1343), 서버의 세션과 무관하다.
- **구현 방향**: CN.reconnect() 확장 또는 WebSocket URL에 session_id 쿼리 파라미터 추가.

## 3. 좋아요/싫어요 -- 새로운 기능 추가

### REQ-LK-01: 3-state 좋아요/싫어요 버튼 추가

- **설명**: assistant 메시지의 msg-actions 영역(line 744~748)에 좋아요(thumbs up)와 싫어요(thumbs down) 버튼을 추가한다. 상태는 3가지: null(미평가), true(좋아요), false(싫어요). 같은 버튼을 다시 클릭하면 null로 토글된다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 msg-actions에는 복사(copy), 재생성(regen), insight 3개 버튼만 있다. 좋아요/싫어요는 완전히 새로운 기능이다.
- **구현 방향**: 복사 버튼 뒤에 thumbs-up, thumbs-down 아이콘 버튼 2개를 추가. 클릭 시 `PATCH /api/turns/{turn_id}/like` 호출. 활성 상태는 CSS 클래스로 시각적 피드백.

### REQ-LK-02: 좋아요 상태 복원

- **설명**: 과거 세션 로드 시 Tier 1 데이터의 is_liked 필드를 읽어 버튼의 초기 상태를 설정한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 메시지 모델(MS.create(), line 691~700)에 is_liked 필드가 없다. 메시지 모델 확장 필요.

### REQ-LK-03: 좋아요 시 선택적 피드백 입력

- **설명**: 싫어요(thumbs down) 클릭 시, 선택적으로 피드백 텍스트 입력을 받는 소형 팝오버를 표시한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 완전히 새로운 UI 요소.
- **UX 근거**: 단순 좋아요/싫어요만으로는 구체적 피드백을 얻기 어렵다. 싫어요에 이유를 첨부하면 프롬프트/파이프라인 개선의 핵심 데이터가 된다. ChatGPT, Claude 등 주요 AI 서비스도 동일한 패턴을 사용한다.

## 4. 다운로드 기록 -- 기존 다운로드와 연동

### REQ-DL-01: 다운로드 시 서버 기록 API 호출

- **설명**: 기존 downloadCSV/SVG/PNG 함수 실행 성공 후 `PATCH /api/turns/{turn_id}/download`를 호출하여 다운로드 이력을 서버에 기록한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 다운로드 함수들은 클라이언트 측에서 Blob 생성 후 즉시 다운로드하며, 서버에 기록하지 않는다.
- **구현 방향**: 각 다운로드 함수의 성공 콜백에서 PATCH API 호출 추가. turn_id는 메시지 모델에 서버 turn_id를 매핑하여 보관해야 한다.

### REQ-DL-02: 다운로드 완료 상태 표시

- **설명**: is_downloaded=true인 턴에 대해 다운로드 바(line 1098~1110)에 이전 다운로드 이력 표시를 추가한다. 재다운로드는 여전히 가능하지만, 이전에 다운로드했음을 시각적으로 안내한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 download-bar는 다운로드 가능 여부만 표시하고 이력은 추적하지 않는다.
- **UX 근거**: 은행 직원이 동일한 데이터를 중복 다운로드하는 것을 방지하여 업무 효율성을 높인다.

## 5. 세션 삭제 -- soft delete로 전환

### REQ-SD-01: 삭제 API 연동 (soft delete)

- **설명**: 현재 deleteSession()(line 1480~1484)은 _sessions 배열에서 필터링하여 localStorage에 저장한다. 이를 `DELETE /api/sessions/{session_id}` 호출로 교체한다. 서버는 soft delete(아카이브)를 수행하므로 클라이언트에서는 목록에서 제거하되, 삭제 취소 가능성을 열어둔다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재는 클라이언트 측 즉시 삭제(hard delete). 새 설계는 서버 측 soft delete.

### REQ-SD-02: 삭제 취소(Undo) 토스트

- **설명**: 세션 삭제 후 하단에 되돌리기 가능한 토스트를 5초간 표시한다. 클릭 시 삭제를 취소하는 API를 호출하고 세션 목록을 복원한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재는 confirm 모달(line 1509~1511)로 삭제 전 확인만 하고, 삭제 후 되돌리기 기능은 없다.
- **UX 근거**: soft delete 아키텍처의 이점을 UX에 반영한다. confirm 모달은 사용자 흐름을 중단시키지만, undo 토스트는 실수를 바로잡을 수 있으면서도 흐름을 유지한다. Gmail, Slack 등 검증된 패턴이다.

### REQ-SD-03: 삭제 중 로딩 상태

- **설명**: DELETE API 호출 중 해당 세션 항목에 opacity 감소 또는 스피너를 표시하여 처리 중임을 안내한다. 네트워크 오류 시 실패 토스트를 표시하고 세션을 목록에 유지한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재는 동기적 localStorage 삭제이므로 로딩 상태가 불필요했다.

## 6. 에러/누락 표시 -- 이력 누락, 에러 상태 표시

### REQ-ER-01: 턴 누락 안내 표시

- **설명**: 과거 세션 로드 시 일부 턴의 content가 null이거나 누락된 경우, 해당 위치에 안내 메시지를 회색 시스템 버블로 표시한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재는 localStorage 기반이므로 데이터 누락 시나리오가 존재하지 않는다. 서버 DB 전환 시 마이그레이션 누락, 저장 실패 등으로 빈 턴이 발생할 수 있다.

### REQ-ER-02: 세션 전체 이력 로드 실패 처리

- **설명**: `GET /api/sessions/{session_id}` 응답이 빈 배열이거나 404인 경우, 채팅 영역에 안내 메시지와 새 대화 시작 버튼을 표시한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 loadSession()(line 1474)은 msgs가 비어있으면 welcome 화면을 표시한다. 서버 오류/빈 응답에 대한 별도 처리가 없다.

### REQ-ER-03: API 연결 실패 시 폴백

- **설명**: REST API 호출 실패(네트워크 오류, 5xx) 시 재시도 버튼이 포함된 에러 배너를 표시한다. 자동 재시도는 3회까지 지수 백오프로 수행한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 WebSocket 연결 실패 처리(line 1350)는 있으나, REST API 실패 처리는 downloadCSV()의 catch 외에는 없다.
- **구현 방향**: 공통 API 호출 래퍼 함수를 작성하여 에러 핸들링을 통일.

### REQ-ER-04: 턴 상태별 시각적 구분

- **설명**: 턴의 status 필드(success/failure/cancelled/timeout)에 따라 메시지 버블의 시각적 스타일을 분화한다. success는 기존 스타일, failure는 좌측 빨간 보더와 에러 텍스트, cancelled는 회색 이탤릭과 취소 표시, timeout은 주황 보더와 시간초과 표시.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 메시지 모델의 status는 streaming/done 2가지뿐(line 694). 서버 모델의 4가지 상태를 모두 표현해야 한다.

### REQ-ER-05: 명확화 질문 턴 구분 표시

- **설명**: turn_type=clarification인 턴은 일반 assistant 버블과 시각적으로 구분한다. 좌측에 ? 아이콘, 또는 버블 배경색을 미세하게 변경.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 모든 assistant 메시지는 동일한 bot-bubble 스타일을 사용한다.
- **UX 근거**: 과거 대화를 다시 볼 때, 어떤 부분이 명확화 질문이었는지 한눈에 파악할 수 있으면 대화 흐름 이해가 빨라진다.

## 7. 기타 UX 개선 -- 설계에 명시되지 않았지만 포함되면 좋을 것들

### REQ-UX-01: 세션 목록 검색/필터

- **설명**: 사이드바 상단에 검색 입력 필드를 추가하여 세션 제목으로 필터링할 수 있게 한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재는 최대 20개 세션만 저장하므로 검색이 불필요했다.
- **UX 근거**: 서버 기반으로 전환하면 세션 수가 크게 증가한다. 긴 목록을 스크롤하는 것보다 검색이 효율적이다.

### REQ-UX-02: 세션 목록 무한 스크롤 또는 더 보기

- **설명**: 서버에 많은 세션이 있을 경우 초기 로드는 최근 20개로 제한하고, 스크롤 하단 도달 시 추가 세션을 로드한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 localStorage는 20개 제한으로 문제 없었다.
- **UX 근거**: 서버에 수백 개의 세션이 쌓일 수 있으므로, 점진적 로딩이 필요하다.

### REQ-UX-03: 오프라인/네트워크 단절 대응

- **설명**: REST API와 WebSocket 모두 끊어진 상태에서, 입력 영역을 비활성화하고 상단에 네트워크 오류 배너를 표시한다. 복구 시 자동 재연결.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 WebSocket onclose에서 재연결을 시도하지만, REST API 실패와 통합된 오프라인 감지는 없다.
- **UX 근거**: 폐쇄망 환경에서는 네트워크 불안정이 빈번할 수 있다. 현재 topbar의 status-dot을 확장하면 된다.

### REQ-UX-04: 메시지별 타임스탬프 표시

- **설명**: 각 메시지 버블 하단 또는 옆에 전송/수신 시각을 작은 글씨로 표시한다. 기본적으로는 숨기고, 메시지 호버 시 표시한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 메시지에 타임스탬프가 표시되지 않는다.
- **UX 근거**: 서버에 created_at이 저장되므로 활용 가능. 업무 맥락 파악과 감사(audit) 목적으로 유용하다.

### REQ-UX-05: 세션 이름 변경 (인라인 편집)

- **설명**: 사이드바 세션 항목을 더블클릭하면 제목을 인라인 편집할 수 있게 한다. Enter로 저장, Esc로 취소.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 세션 제목은 첫 메시지에서 자동 생성되며 수정 불가.
- **UX 근거**: 자동 생성 제목보다 사용자 지정 제목이 나중에 찾기 쉽다.

### REQ-UX-06: 키보드 단축키 안내 및 확장

- **설명**: Ctrl+K(검색), Ctrl+N(새 대화) 등을 지원하고, ? 키로 단축키 도움말 오버레이를 표시한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 키보드 지원은 모달 내 Esc/Enter와 명령어 팝업 내 Arrow/Tab에 한정.
- **UX 근거**: 은행 업무 특성상 키보드를 선호하는 사용자가 있다. 파워 유저를 위한 단축키는 업무 효율을 높인다.

### REQ-UX-07: Optimistic UI 패턴 적용

- **설명**: 좋아요/싫어요, 세션 삭제 등 서버 반영이 필요한 액션에서, API 응답을 기다리지 않고 즉시 UI를 업데이트한 후, 실패 시에만 롤백한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재 localStorage 기반에서는 동기적으로 즉시 반영. API 전환 시 반응 지연 문제가 발생할 수 있다.
- **UX 근거**: 네트워크 지연이 100~300ms라도 반응이 없으면 사용자는 재클릭할 수 있다. Optimistic UI는 이 문제를 해결하는 표준 패턴이다.

### REQ-UX-08: 세션 그룹핑 (날짜별)

- **설명**: 사이드바의 세션 목록을 "오늘", "어제", "지난 7일", "지난 30일" 등 날짜 그룹으로 분류하여 표시한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 현재는 단순 리스트. 서버 데이터의 created_at/last_active를 활용하면 날짜 그룹핑이 가능하다.
- **UX 근거**: ChatGPT가 채택한 검증된 패턴. 세션 수가 많아질수록 시간 기반 그룹핑은 탐색 효율을 크게 높인다.

### REQ-UX-09: API 호출 통합 레이어

- **설명**: 현재 WebSocket(CN 모듈)과 별개로, REST API 호출을 위한 통합 모듈을 신규 추가한다. 인증 헤더 주입, 에러 핸들링, 재시도 로직, 요청 취소(AbortController)를 공통으로 처리한다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 REST 호출은 downloadCSV() 내 fetch() 1곳뿐이다. 새 설계에서는 6개 이상의 REST 엔드포인트를 호출해야 하므로 공통 레이어가 필수.
- **구현 방향**: `var API = (function(){ ... })()` 로 새 모듈 추가. API.get(url), API.patch(url, body), API.delete(url) 메서드 제공.

### REQ-UX-10: 메시지 ID 체계 변경

- **설명**: 현재 메시지 ID는 클라이언트에서 생성된다(line 693). 서버 연동 후에는 서버의 turn_id를 기본 식별자로 사용해야 한다. 실시간 스트리밍 중에는 임시 클라이언트 ID를 사용하고, 서버 저장 완료 후 turn_id로 교체하는 2단계 ID 매핑이 필요하다.
- **우선순위**: 필수
- **현재 구현과의 차이점**: 현재 ID는 순수 클라이언트 생성이며 서버와 공유되지 않는다.
- **구현 방향**: MS.create()의 반환 메시지에 turnId: null 필드를 추가하고, 서버 응답 시 매핑. 좋아요/다운로드 API 호출 시 turnId를 사용.

### REQ-UX-11: 복원 시 새 메시지 구분선

- **설명**: 과거 세션을 복원한 후 사용자가 새 질문을 시작하면, 기존 복원된 메시지와 새 메시지 사이에 시각적 구분선을 삽입한다.
- **우선순위**: 권고
- **현재 구현과의 차이점**: 완전히 새로운 기능.
- **UX 근거**: 과거 맥락과 현재 대화를 시각적으로 구분하면 인지적 혼란을 방지한다.
